# 테스트 룸에 봇을 넣는 계획

> **상태: Phase 0~4 구현 완료(2026-08-04).** 실행 방법은 `readme.md` 의 "혼자 확인하기 — 정적 룸의
> 봇" 절에, 밟은 함정은 `conventions.md` 에 옮겨 두었다. 이 문서는 **왜 그렇게 만들었는지**를
> 남긴다. 열린 항목은 §7 의 5번 하나이고, 3번은 (a) 로 결정해 구현했다.

개발 인원이 한 명이므로 지금은 매치를 끝까지 돌릴 수 없다. **정적 룸(`test`)에 한정해 봇 참가자를 만들어, 사람 한 명으로 시작·판정·종료까지 지나가게 한다.**

배경은 `architecture.md`(설계 원칙·금지 목록·신뢰 경계), `structure.md`(파일 배치 8문 표), `conventions.md`(함정 목록), 그리고 규칙 판정을 서버로 옮기는 진행 중인 계획 `match-authority-plan.md` 다. **이 문서는 규칙을 바꾸지 않는다** — 봇은 사람과 같은 판정 경로를 지나가는 참가자여야 하고, 그렇지 않으면 봇으로 확인한 것이 사람에게 성립하지 않는다.

---

## 1. 지금 왜 막혀 있는가

| 벽 | 근거 |
|---|---|
| 매치 시작에 2명이 필요하다 | `RealtimeConstants.Rooms.MinPlayersToStart = 2` — Seeker 하나와 Runner 하나가 없으면 술래잡기가 성립하지 않는다 |
| 명단에 들어가는 유일한 경로가 WebSocket 접속이다 | `RealtimeEndpoints.HandleAsync` 만 `RoomCommand.Join` 을 만든다 |
| 그래서 두 번째 참가자는 두 번째 프로세스다 | **Tools ▸ NV ▸ Build and Launch 2 Clients** 가 그 경로이고, 사람 하나가 두 창을 동시에 조작할 수 없다 |

지금 사람 하나로 확인할 수 있는 것은 로비·방 만들기·접속·맵 해시까지다. 시작 버튼 뒤의 전부 — 역할 공개, 매치 시계, 목표물 배치, 열쇠 습득·삽입, 문 개방, 탈출, 발사·피격·출혈·순간이동·사망, 종료 판정 — 는 두 번째 몸이 없으면 한 번도 돌지 않는다. 서버가 이미 판정을 갖고 있는 부분(IG-0xx 로 옮겨 온 것들)이 **테스트로만 검증되고 실제로 화면과 함께 돌아간 적이 없는** 상태다.

## 2. 선택지와 결정

| 방식 | 얻는 것 | 비용 | 판정 |
|---|---|---|---|
| **A. 소켓 없는 서버 봇** — 룸 안에 세션 없는 참가자를 만든다 | 클라이언트 변경 0, 프로토콜 변경 0. 봇이 사람과 **같은** 이동·판정 경로를 지난다 | 룸이 "참가자에게는 항상 세션이 있다" 는 전제를 잃는다 (§4 의 함정 표) | **채택** |
| B. 헤드리스 클라이언트 프로세스 — 콘솔 앱이 `/ws` 로 붙는다 | 전송 계층과 프로토콜까지 검증한다. 가장 현실에 가깝다 | 새 프로젝트가 프로젝트 그래프에 붙는다(`architecture.md` 의 물어봐야 하는 항목). 그러면서도 **입력 생성기는 어차피 새로 써야 한다** — 이동 판정은 이미 서버에 있으므로 추가로 얻는 것은 소켓 경로뿐 | 나중에 부하·프로토콜 시험이 필요해지면 A 위에 얹는다 |
| C. Unity 클라이언트를 자동 조작 | 클라이언트 표현까지 함께 돈다 | 창 두 개와 프로세스 두 개가 여전히 필요하다. 지금 문제가 그것이다 | 기각 |

**A 의 핵심 규칙: 봇은 `InputFrame` 을 만드는 것까지만 한다.** 위치를 직접 옮기거나 열쇠 수를 직접 만지는 봇은 서버 판정을 우회하므로, "봇으로 확인했다" 가 아무것도 보증하지 않는다. 봇이 만든 프레임은 사람의 프레임과 같은 `InputValidator.Sanitize` → `PlayerMovement.Step` → 목표물·전투 판정을 지난다.

**정적 룸에 한정한다.** 이유는 편의가 아니라 두 가지 구조다.

- `RoomRegistry.Sweep` 은 `PlayerCount > 0` 인 룸을 회수하지 않는다. 봇이 사람처럼 세어지므로, **초대 코드 룸에 봇이 남으면 그 룸은 영구히 회수되지 않는다.** 정적 룸은 애초에 회수 대상이 아니라 이 문제가 없다.
- `Room.IsAuthorized` 는 정적 룸에서 전원에게 시작 권한을 준다. 봇 추가·역할 강제 같은 개발용 훅이 이 경계 안에만 있으면, 실제 매치의 판정에는 그 훅이 닿지 않는다 — `architecture.md` 의 신뢰 경계를 넓히지 않고 개발 편의를 얻는 유일한 자리다.

## 3. 설계

### 3.1 봇은 세션 id 가 음수인 참가자다

`_players` 는 `sessionId` 로 키가 잡히므로 봇에게도 유일한 id 가 필요하다. **룸이 `-1` 부터 감소시켜 발급한다.**

- `SessionRegistry.AllocateSessionId` 는 `Interlocked.Increment` 로 1 이상만 낸다 → 절대 겹치지 않는다.
- `WebSocketServerTransport.TrySend` 는 없는 세션에 `false` 를 돌려주므로 잘못 보내도 조용히 실패한다. 그래도 **보내지 않는다**(§3.4) — 인코딩 비용이 헛되고, "봇에게 전문이 갔다" 가 표현 가능한 상태로 남으면 안 된다.
- `IsAuthorized` 는 `sessionId == _hostSessionId` 를 요구하고 방장 id 는 항상 양수다 → 봇이 방장 자격을 얻는 경로가 없다.

`PlayerEntity.IsBot => SessionId < 0` 으로 **유도한다.** 별도 필드를 두면 "세션이 있는데 봇" 이 표현 가능해지고, 그것은 `Bleeding` 을 `Hits` 에서 유도한 것과 같은 이유로 두지 않는다.

이름은 `BOT 1`, `BOT 2` … 로 서버가 붙인다. `DisplayName.Sanitize` 규칙(출력 가능 ASCII, `ProtocolInfo.MaxDisplayNameBytes`) 안에 들어가므로 코덱이 그대로 싣고, **클라이언트는 아무 변경 없이 명단에 이 이름을 그린다.**

### 3.2 봇의 두뇌

`Modules/Realtime/Simulation/Bots/BotBrain.cs`. `structure.md` 8문 표의 1번("클라이언트도 같은 계산을 하는가")에 걸리지 않는다 — 클라이언트는 봇의 다음 입력을 예측할 필요가 없고 스냅샷으로 결과만 받는다. 그래서 `Shared` 가 아니라 모듈이다.

**인터페이스를 두지 않는다.** 구현이 하나인 인터페이스는 `architecture.md` 의 물어봐야 하는 항목이므로, 행동은 `enum BotBehavior { Idle, Wander, Objective }` 로 가른다.

```
BotBrain.Think(in BotSenses senses, ref DeterministicSequence rng) → InputFrame
```

`BotSenses` 는 룸이 채워 넘기는 읽기 전용 묶음(자기 상태, 역할, 매치 단계, 목표물, 다른 몸들, 콜리전, 격자)이다. 두뇌가 룸을 직접 만지지 못하게 하는 것이 요점 — 두뇌가 `PlayerEntity` 를 쓸 수 있으면 언젠가 위치를 직접 옮긴다.

난수는 **룸당 하나의 `DeterministicSequence` 를 봇 전용으로 따로 둔다.** 배치(`_placementSeed`)와 피격(`_hitRandom`)이 이미 분리되어 있는 것과 같은 이유다 — 수열을 나눠 쓰면 봇이 한 번 더 뽑는 변경이 열쇠 배치를 바꾼다. 씨드를 고정할 수 있게 두면 "같은 씨드에 같은 궤적" 이 테스트로 고정된다.

### 3.3 봇의 입력은 버퍼를 지나지 않는다

`Room.StepPlayer` 에 갈래를 하나 만든다.

```
if (player.IsBot) { frame = brain.Think(...); apply(frame); return; }
```

사람의 경로(입력 버퍼 → 따라잡기 상한 → 반복 → 중립)를 봇이 지날 이유가 없다. 봇은 매 틱 정확히 한 프레임을 만들고 그것이 유실될 경로가 없다. 다만 **적용 자체는 사람과 같은 함수를 부른다** — `InputValidator.Sanitize`, `_match.MovementLocked` 일 때의 중립화, `ButtonFlags.Interact` 엣지 수집, `Simulate`. 이 갈래에서 그 순서를 다시 쓰지 않고 공통 함수로 뽑는다. 갈라 두면 잠금 규칙이 두 곳에 생기고, 증상은 "리빌 중에 봇만 움직인다" 가 된다.

### 3.4 봇에게는 아무것도 보내지 않는다

`Broadcast*` 네 곳(`Snapshot`, `RoomState`, `MatchState`, `ObjectiveState`)과 `BroadcastFireEvents` 의 수신자 순회에서 봇을 건너뛴다. 명단·엔티티 목록에는 **들어간다** — 사람들이 봇을 봐야 하므로 그쪽은 그대로다. 건너뛰는 것은 수신자 쪽뿐이며, 그 둘이 같은 `foreach` 로 겹쳐 있는 곳(`BroadcastRoomState`)이 있으니 순회를 나눠야 한다.

### 3.5 봇을 넣는 경로는 자동 채움 하나다

**결정: HTTP 엔드포인트를 두지 않는다.** 정적 룸이 `Waiting` 이고 사람이 한 명 이상 있는데 참가자가 `MinPlayersToStart` 보다 적으면, 룸이 부족한 만큼 봇을 만든다. `Room.Advance` 의 대기 갈래에서 돈다(룸이 `_players` 의 소유자다).

이 경로의 값은 **새 공개 표면이 0, 클라이언트 작업이 0** 이라는 것이다. 에디터에서 Play → `test` 방 접속 → 봇이 채워짐 → **게임 시작**(정적 룸이라 전원에게 권한이 있다) → 매치가 끝까지 돈다. 요청을 보내는 단계가 없으므로 개발 루프에 손이 하나도 더 들지 않는다.

사람이 아무도 없을 때는 채우지 않는다. 그러지 않으면 서버가 기동하자마자 빈 방에서 봇끼리 매치가 도는 상태가 되고, 로그가 그것으로 덮인다. 그리고 §4 의 함정 2(사람이 나가면 봇도 지운다)와 합쳐져야 규칙이 닫힌다 — 지우지 않으면 자동 채움의 조건이 계속 참이다.

**조절은 설정으로 한다.** `appsettings.Development.json` 의 `Realtime:Bots` 절이다.

| 키 | 뜻 | 기본값 |
|---|---|---|
| `Enabled` | 봇 기능 자체 | `false` (`appsettings.json`), `true` (`Development`) |
| `FillTo` | 몇 명까지 채우는가 | `MinPlayersToStart`(2). 상한은 `MaxPlayers` |
| `Behavior` | `Idle` / `Wander` / `Objective` | `Idle` |
| `Role` | 봇이 맡을 역할 희망 — `Runner` / `Seeker` / `Any` | `Runner` (사람이 총을 든다) |
| `Seed` | 봇 난수 씨드. 0 이면 매번 다르다 | 0 |

무엇을 볼 것인지에 따라 `Behavior` 를 고른다 — 더 움직이는 것이 늘 더 나은 것이 아니다. 그 대응표는 `readme.md` 에 있다.

**프로덕션 설정에서 기본값이 꺼짐인 것이 이 기능의 유일한 방어선이다.** 정적 룸 한정이라는 조건과 겹쳐 두 겹이 된다 — `Game:StaticRooms` 가 비어 있는 배포에서는 `Enabled` 가 참이어도 봇이 생길 룸이 없다. `NetworkConditionsEnabled` 가 이미 같은 규칙을 쓰고 있으므로(`RealtimeOptions` 의 주석) 기동 로그에 경고를 남기는 방식도 그쪽을 따른다.

봇 추가는 `RoomCommand.AddBot` / `RemoveBots` 로 둔다 — 지금은 틱 루프가 스스로 부르지만, 커맨드를 지나게 해 두면 나중에 다른 스레드에서 부르는 경로(수동 조작, 관리 도구)가 붙을 때 `_players` 를 직접 만지는 코드가 생기지 않는다.

### 3.6 역할 강제

`Room.PickSeeker` 는 무작위다. 사람 1 + 봇 1 이면 절반의 확률로 사람이 Runner 가 되어, 총을 확인하려던 회차가 버려진다. **정적 룸에서만 역할 희망을 지킨다.**

`Bots:Role` 은 *봇이* 맡을 역할이다. `Runner` 면 `PickSeeker` 가 사람 중에서 고르고, `Seeker` 면 봇 중에서 고른다. `Any` 면 지금과 같은 무작위다.

희망을 지킬 수 없으면(예: `Runner` 인데 사람이 없다) **무작위로 떨어지고 그 사실을 로그로 남긴다.** 조용히 무작위가 되면 "역할 강제가 동작하지 않는다" 를 찾는 데 시간이 걸린다.

정적 룸 한정이라는 조건이 이 훅의 전부다. 룸 판정에 개발용 갈래가 하나 들어가는 일이지만, 그 갈래가 초대 코드 룸에 닿지 않으므로 실제 매치의 역할 배정은 지금과 완전히 같다. 테스트가 그것을 고정한다(§6 의 10번).

### 3.7 봇의 행동 — 단계별

| 단계 | 행동 | 그것으로 검증되는 것 |
|---|---|---|
| `Idle` | 중립 프레임만 만든다. 서 있고, 중력을 받고, 총에 맞는다 | 시작·역할 공개·시계·종료, 스냅샷·보간·원격 몸, **발사 → 피격 → 출혈 → 순간이동 → 2방 사망 → 열쇠 흘리기**, HUD 의 탄약·피격·명단 |
| `Wander` | 격자에서 목표점을 뽑아(`MapGrid.TryRandomFreeFloor`) 그 방향으로 걷는다. 진행이 멈추면 목표를 다시 뽑는다 | 속도 상한, 이동 예측·보정, 발소리·애니메이션, 움직이는 표적에 대한 발사체 스윕 |
| `Objective` | Runner 봇: 가장 가까운 열쇠로 걸어가 줍고(습득은 거리 폴링이라 걷는 것으로 끝난다) 문으로 가서 `Interact` 를 누른다 → 문이 열리면 문간에 머문다. Seeker 봇: 가장 가까운 Runner 를 향해 걷고, 시선이 닿으면 `Fire` | 열쇠 습득·삽입·문 개방·**탈출**·승리 조건, Seeker 쪽 판정 전부 |

**경로 탐색을 넣지 않는다.** 지금 `MapGrid` 가 내주는 것은 `TryRandomFreeFloor` 와 `TryNearestFreeFloor` 뿐이고, 격자 A\* 는 `match-authority-plan.md` §6 이 체인 견인을 위해 이미 검토 중인 항목이다. 두 곳이 같은 A\* 를 필요로 하므로 **그 작업이 들어올 때 봇이 그것을 쓴다.** 그때까지 봇은 직선으로 걷고 막히면 목표를 다시 뽑는다 — 미로에서 비효율적이지만, 검증하려는 것이 "봇이 영리한가" 가 아니라 "판정이 도는가" 이므로 충분하다. 다만 `Objective` 단계의 Runner 봇은 열쇠와 문에 실제로 도달해야 하므로, **거기서 A\* 부재가 처음으로 실질적 제약이 된다**(§7).

`Objective` 봇은 서버의 좌표를 그대로 읽는다. 즉 **문의 위치를 아는 치팅 봇이다.** 룰셋이 Seeker 에게 감추는 정보를 봇은 갖고 있고, 그것을 감추는 필터(`MessageCodec` 안의 역할별 필터)를 지나지 않는다. 개발 검증용이라는 것을 코드 주석과 로그에 적어 둔다 — 이것을 프로덕션 AI 로 승격하려면 시야 제약이 먼저 필요하다.

| 1 | 봇이 방장을 승계한다 | `Room.LowestRemainingSessionId` 는 가장 작은 `PlayerId` 를 고른다. 봇의 `PlayerId` 가 더 작을 수 있다 | 봇을 후보에서 뺀다. 정적 룸은 전원에게 권한이 있어 증상이 없지만, 방장 자리가 봇에게 가면 초대 코드 룸으로 확장할 때 시작이 막힌다 |
| 2 | 마지막 사람이 나간 방에 봇이 남는다 | `Leave` 의 `_players.Count == 0` 조건이 봇 때문에 성립하지 않는다 → 단계가 `Waiting` 으로 돌아가지 않고, 비정적 룸이면 **영구히 회수되지 않는다** | `Leave` 에서 사람 수를 세고, 0 이면 봇을 전부 지운 뒤 기존 규칙을 태운다 |
| 3 | 봇이 슬롯을 훔친다 | 두 번째 사람이 붙을 때 정원이 차 있으면 `/ws` 가 503 이다 | 자동 채움 기본값이 `MinPlayersToStart`(2)라 6칸이 남는다. `FillTo` 를 8 로 올리는 것은 설정한 사람의 선택이며, **`/ws` 가 봇을 밀어내는 양보 로직은 넣지 않는다** — 슬롯 반납이 틱 경계라 그 접속은 어차피 실패하고, 재시도로 들어온다 |
| 4 | 온라인 인원이 봇으로 부풀려진다 | 로비의 헤드카운트와 방 목록이 `PlayerCount` 를 그대로 쓴다 | `RoomSummary`·`RoomInfoResponse` 에 `botCount` 를 더한다. HTTP JSON 이라 필드 추가는 하위 호환이고 **프로토콜 버전은 3 그대로다.** 클라이언트가 빼는 것은 나중 작업 |
| 5 | 봇에게 전문이 나간다 | `Broadcast*` 가 `_players` 를 그대로 순회한다 | §3.4. 명단 순회와 수신자 순회를 나눈다 |
| 6 | 리빌 중에 봇만 움직인다 | `MovementLocked` 중립화가 사람 갈래에만 있다 | §3.3 — 적용 함수를 공유한다 |
| 7 | 봇이 벽을 통과하거나 속도 상한을 넘는다 | 두뇌가 프레임이 아니라 위치를 만들면 | 두뇌는 `InputFrame` 만 돌려준다. 테스트가 이것을 고정한다 |
| 8 | 봇 때문에 판정 결과가 재현되지 않는다 | 두뇌가 `Random.Shared` 를 쓰면 | 룸별 `DeterministicSequence`, 배치·피격과 분리 |
| 9 | 매치 중에 봇이 합류한다 | 자동 채움이 단계를 보지 않으면. `/ws` 는 진행 중 합류를 거부하지만(비대칭 매치에 중간 합류는 규칙이 성립하지 않는다) 자동 채움은 그 검사를 지나지 않는다 | `Waiting` 갈래에서만 돈다. 이것이 §3.5 가 `Room.Advance` 의 대기 갈래에 있는 이유이며, `Broadcast` 나 `Sweep` 쪽에 두면 이 조건이 사라진다 |

## 5. 단계

### Phase 0 — 골격 (봇 하나, 서 있는다, 사람이 총을 든다)

`Room` 에 봇 참가자·`AddBot`/`RemoveBots` 커맨드·자동 채움, `BotBrain` 의 `Idle`, **역할 강제**(§3.6), `RealtimeConstants.Bots`, `RealtimeOptions.Bots`(§3.5 의 표), 함정 1·2·5·6·9.

역할 강제를 이 단계에 넣는다. 뒤로 미루면 절반의 회차가 사람을 Runner 로 만들어, 이 Phase 가 열어 주는 가장 큰 것 — **서 있는 표적에 3발을 쏴서 출혈·순간이동·2방 사망·열쇠 흘리기를 화면으로 보는 것** — 이 동전 던지기가 된다.

**이 단계에서 이미 사람 하나로 매치가 끝까지 돈다.**

검증 — `dotnet build` 경고 0, 새 `BotTests` + 기존 394개 통과. 그리고 실제로: 에디터 Play → `test` 접속 → 명단에 `BOT 1` → 시작 → 사람이 Seeker, 리빌 뒤 봇이 서 있고 스냅샷이 온다 → 3발로 죽는다.

### Phase 1 — 노출 정리

함정 3·4, `botCount` 필드, 기동 로그의 경고(`Bots:Enabled` 가 켜져 있음을 `NetworkConditionsEnabled` 와 같은 방식으로 남긴다).

Phase 0 과 합쳐도 되는 크기이지만 나눠 둔다 — 이쪽은 HTTP 응답 형식이 바뀌는 유일한 변경(`botCount`)이고, §7 의 4번이 아직 열려 있다.

### Phase 2 — 배회

`BotBehavior.Wander`. 격자에서 목표점을 뽑아 걷는다. 함정 7·8 의 테스트가 여기서 의미를 갖는다.

검증 — 봇이 벽 안으로 들어가지 않는다(`_map.Collision` 질의로 단정), 수평 속도가 `Validation.MaxHorizontalSpeed` 를 넘지 않는다, 같은 씨드에 같은 궤적, 그리고 화면에서 원격 몸이 걷는 애니메이션과 발소리를 낸다.

### Phase 3 — 목표 수행

`BotBehavior.Objective`. Runner 봇이 열쇠를 줍고 문을 열고 탈출한다. Seeker 봇이 쫓고 쏜다.

**여기서 경로 탐색 부재가 실질적 제약이 된다.** 열쇠까지 직선으로 갈 수 없는 배치가 대부분이므로, `test-room`(방 하나, 벽 없음)에서는 동작하고 `backrooms`(미로)에서는 봇이 헤맨다. 선택은 셋이다 — (a) `test-room` 에서만 쓴다, (b) 격자 A\* 를 `Shared` 에 넣는다(`match-authority-plan.md` §6 과 같은 작업), (c) 개발 편의로 봇의 목표 도달을 순간이동으로 대신한다(**판정 우회이므로 권하지 않는다** — 이 계획의 전제를 깬다). §7 에서 확인을 요청한다.

검증 — 사람 없이 봇 2로 매치가 시작에서 종료까지 자기 힘으로 도달한다. 그것이 되면 `MatchRules` 전체가 통합 경로로 한 번 돌았다는 뜻이다.

### Phase 4 — 문서 (완료)

- `conventions.md` — 함정 표(§4)를 증상 → 원인 → 대응으로 옮긴다. 특히 2번(봇이 남은 룸이 회수되지 않는다)과 5번(봇에게 전문이 나간다)은 증상만 보고 원인을 찾기 어렵다.
- `architecture.md` 기본값 대체표 — "봇은 가짜 클라이언트를 소켓으로 붙인다 → 소켓 없는 참가자를 룸에 직접 넣고, 입력만 생성한다".
- `readme.md` — 1인 개발 루프를 실행 방법 절에 넣는다. 지금 문서는 "매치에는 두 명이 필요하다" 로 끝나 있다.
- `structure.md` — `Simulation/Bots/` 폴더.
- `../NVproject/CLAUDE.md` 는 **고치지 않는다.** 클라이언트 변경이 없다 — 봇은 이름이 `BOT n` 인 원격 플레이어일 뿐이다. 이것이 이 설계가 A 를 고른 가장 큰 이유다.

## 6. 테스트 (`tests/Modules.Tests/Realtime/BotTests.cs`)

룸은 전송도 인증도 모르므로 소켓 없이 전부 검사된다(`RoomFixture`).

1. 봇을 넣으면 명단과 `PlayerCount` 가 늘고, 이름이 `BOT 1` 이다
2. 사람 1 + 봇 1 로 매치가 시작된다
3. **봇 세션에는 단 한 프레임도 가지 않는다** (`RecordingTransport.CountFor(-1) == 0`)
4. 봇은 방장을 승계하지 않는다
5. 마지막 사람이 나가면 봇도 사라지고 룸이 `Waiting` 으로 돌아간다 (+ `RoomRegistryTests` 에 비정적 룸이 회수된다)
6. 정적이 아닌 룸에는 봇이 생기지 않는다. `Bots:Enabled` 가 꺼져 있으면 정적 룸에도 생기지 않는다
7. 리빌 중에 봇이 움직이지 않는다
8. 배회 봇이 벽 안으로 들어가지 않고 속도 상한을 넘지 않는다
9. 같은 씨드면 봇의 궤적이 같고, 봇을 넣어도 목표물 배치가 바뀌지 않는다 (수열 분리의 증거)
10. 역할 희망이 지켜지고, 지킬 수 없으면 무작위로 떨어진다. **초대 코드 룸에서는 희망이 무시된다** — 개발용 갈래가 실제 매치에 닿지 않는다는 증거
11. 매치가 진행 중인 정적 룸에는 봇이 추가되지 않는다
12. (Phase 3) Runner 봇이 열쇠를 줍고 문을 열고 탈출한다

`Architecture.Tests` 는 그대로 통과해야 한다 — 새 프로젝트도 새 참조도 NuGet 도 없고, 봇 관련 타입은 전부 모듈 내부의 `internal` 이다.

## 7. 결정된 것과 남은 것

`architecture.md` 는 문서화된 금지를 어기거나 판정에 손대기 전에 묻도록 정한다. 그중 둘은 답이 나왔다.

**결정 (2026-08-04)**

1. **HTTP 엔드포인트를 두지 않는다.** 봇을 넣는 경로는 자동 채움 하나이고, 조절은 `Realtime:Bots` 설정으로 한다(§3.5). 새 공개 표면이 0 이고, 자동 채움과 수동 제거가 싸우는 문제도 함께 사라진다. 실행 중에 봇 수를 바꿀 수 없다는 것이 값이며, 필요해지면 `RoomCommand.AddBot` 이 이미 그 자리를 비워 두고 있다.
2. **역할 강제를 넣는다.** 정적 룸 한정으로 `PickSeeker` 에 갈래를 하나 둔다(§3.6). 판정 코드에 개발용 조건이 늘어나는 대가를 치르지만, 없으면 총 관련 검증 회차의 절반이 버려진다. 초대 코드 룸에서는 무시된다는 것을 테스트가 고정한다.

**남은 것**

3. **Phase 3 의 경로 탐색** — **(a) `test-room` 한정으로 구현했다.** 직선으로 걷고 0.5초 동안 나아가지 못하면 다른 목표를 뽑는다. 열린 방에서는 목표에 도달하고 미로에서는 헤맨다. (b) 격자 A\* 는 체인 견인과 같은 자리를 공유하므로 그 작업이 들어올 때 `BotBrain.WalkToward` 가 경로의 다음 지점을 향하도록 바꾼다. (c) 순간이동은 판정 우회이므로 채택하지 않았다.
4. **`botCount` 노출** — **더했다.** HTTP JSON 필드 추가라 프로토콜은 3 그대로다. **인원에서 빼지 않는다** — 봇도 슬롯을 차지하므로 `PlayerCount` 는 정원 판정의 근거여야 한다. 로비가 이 값을 빼서 쓰는 것은 클라이언트 쪽 작업으로 남아 있다.

**남은 것**

5. **봇을 클라이언트가 구분해야 하는가.** 지금은 이름으로만 구분한다. 명단에 봇 표시가 필요하면 `RoomPlayerEntry` 에 비트가 필요하고 **그것은 프로토콜 4** 다 — 클라이언트 변경 0 이라는 이 설계의 장점이 사라진다. 이름 규칙(`BOT n`)으로 충분한지는 실제로 써 보고 판단한다.
