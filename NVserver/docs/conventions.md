# 규약

구현하면서 확정된 규칙을 누적한다. 미리 채우지 않는다.

아키텍처 결정은 `architecture.md`, 폴더와 네이밍은 `structure.md`에 있다. 이 문서는 **그 둘로 답이 안 나온 것을 실제로 겪고 정한 결과**만 담는다.

**추가 기준** — 아래 중 하나에 해당할 때만 적는다.

- 실제로 밟은 문제이고, 모르면 다시 밟는다
- 어겼을 때 증상이 원인과 멀어 추적이 어렵다
- 두 사람 이상이 다르게 해도 되는 선택이라 통일이 필요하다

추측이나 일반론은 적지 않는다. 틀린 것으로 밝혀지면 지운다.

**형식** — 항목당 규칙 한 줄, 필요하면 근거 한 줄, 코드는 잘못된 예 ↔ 올바른 예 대조가 필요할 때만.

**갱신** — 규칙을 확정했거나 30분 이상 걸린 문제를 해결했으면 해당 절에 추가한다. 절이 없으면 만든다. 나중에 틀린 것으로 밝혀지면 지운다.

## 협상 불가 제약

플랫폼이 강제하는 것들이라 검증 없이 확정할 수 있다. 나머지 절은 비어 있는 상태로 시작한다.

### `Shared` 컴파일

Unity(IL2CPP)와 .NET 양쪽에서 같은 `.cs` 파일을 컴파일한다.

| 제약 | 값 |
|---|---|
| 타겟 프레임워크 | `netstandard2.1;net10.0` |
| C# 버전 | 9.0 — Unity 6 상한. `netstandard2.1` 기본값이 8이므로 명시한다 |
| NuGet 참조 | 금지 |
| `UnityEngine` 참조 | 금지 |
| 벡터 타입 | `System.Numerics.Vector3` |
| `ImplicitUsings` | 끈다. 전역 using이 `obj/`에 생성되는데 Unity는 보지 않는다 |

`System.Text.Json`이 NuGet이므로 DTO에 `[JsonPropertyName]`을 붙일 수 없다. 순수 POCO로 두고 명명 규칙은 양쪽 직렬화 설정에서 맞춘다.

`Shared/obj/`가 생기면 Unity가 그 안의 `AssemblyInfo.cs`를 패키지 범위로 인식해 중복 정의 에러를 낸다. `Directory.Build.props`에서 출력 경로를 `artifacts/`로 리디렉션한다.

### WebGL 클라이언트

싱글 스레드다. `Task.Run`, `Thread`, `lock`을 쓸 수 없다. `System.Net.Sockets`도 없어 WebSocket은 `.jslib` 경유다.

HTTPS 페이지에서 `ws://`는 mixed content로 차단된다.

빌드가 디컴파일되므로 `Shared`에 들어간 값은 클라이언트가 안다고 가정한다.

### `SourceGenerator`

Roslyn 분석기와 소스 제너레이터는 `netstandard2.0`만 로드된다.

`Shared`에 적용하지 않는다. Unity에서 쓰려면 DLL을 패키지 안에 넣고 `RoslynAnalyzer` 라벨을 붙여야 하는데, 어긋나면 서버는 생성된 코드로 Unity는 원본으로 컴파일된다. 증상이 런타임 캐릭터 떨림으로만 나타나 추적이 어렵다.

### 틱 루프 예외

.NET 6부터 `BackgroundServiceExceptionBehavior` 기본값이 `StopHost`다. 틱 하나에서 튄 예외가 서버 전체를 내린다. 루프 안을 `try/catch`로 감싼다.

## 빌드

`Directory.Build.props`의 출력 경로 리디렉션은 SDK 내장 `UseArtifactsOutput`·`ArtifactsPath`를 쓴다. `BaseIntermediateOutputPath`를 직접 지정하면 `MSBuildProjectExtensionsPath` 유도 순서에 의존하게 된다.

패키지 버전 중앙 관리를 켠 상태에서는 `.csproj`의 `PackageReference`에 `Version` 속성을 쓸 수 없다. `dotnet new` 템플릿은 `Version`을 붙여서 만들므로 생성 직후 restore가 NU1008로 실패한다. 오류 메시지가 "복원하지 못했습니다"뿐이라 원인이 드러나지 않는다. 버전은 `Directory.Packages.props`의 `PackageVersion`으로 옮기고 `.csproj`에서는 이름만 남긴다.

모듈과 `Infrastructure`가 호스팅·로깅·라우팅 타입을 쓸 때는 `FrameworkReference Include="Microsoft.AspNetCore.App"`을 쓴다. 공유 프레임워크 참조이며 NuGet 패키지가 아니다. `Microsoft.Extensions.*` 패키지를 개별로 추가하지 않는다.

## 시뮬레이션

`MathF.Sin`·`Cos`·`Tan`을 쓰지 않는다. 정확도가 구현에 맡겨져 있어 Unity(IL2CPP)의 libm과 .NET 구현이 마지막 비트에서 갈릴 수 있다. `DeterministicMath`의 다항식 근사를 쓴다. 어겼을 때 증상은 리컨실리에이션 시 떨림으로만 나타난다.

`Vector3.Normalize`·`Length`·`Dot`·`Distance`를 쓰지 않는다. 구현이 SIMD·FMA 경로를 타면 라운딩이 달라진다. `Vector3`는 데이터 컨테이너로만 쓰고 연산은 `DeterministicMath`의 스칼라 구현을 쓴다.

`MathF.Sqrt`·`Floor`·`Abs`는 IEEE 754가 결과를 규정하므로 써도 된다.

서버도 입력을 `MoveIntent.FromInput`으로 역양자화해서 쓴다. 클라이언트가 예측에 쓰는 값은 양자화를 통과한 값이므로, 서버가 원본 부동소수점을 쓰면 양쪽 결과가 갈린다.

이동 함수에 `deltaTime` 파라미터를 두지 않는다. 파라미터가 있으면 호출자가 실제 경과 시간을 넣을 수 있게 되고, 그 순간 재적용 결과가 달라진다. `SimConstants.TickDelta`만 쓴다.

상태 해시에서 `-0.0`을 `0`으로 정규화한다. 비트 패턴이 달라 부호만 다른 0이 다른 해시를 만든다.

AABB 겹침 판정은 등호를 포함하지 않는다. 면이 맞닿은 상태를 겹침으로 보면 바닥에 서 있는 것만으로 매 틱 밀려난다.

**등호를 뺐어도 발밑에서 박스를 만들면 맞닿음이 침투로 바뀐다.** 박스는 중심에서 만들어지므로(`Aabb.FromCenter`) 하단이 `(feet + halfY) - halfY` 라는 왕복을 거치는데, float 에서 그 왕복은 값을 보존하지 않는다 — `(3.2f + 0.9f) - 0.9f` 는 `3.1999999` 이고 발밑보다 아래다. 그래서 바닥을 1e-7 만큼 파고들고 `Depenetrate` 가 밀어낸다. 발밑이 정확히 `0f` 인 1층만 오차가 0 이라 무사하고, **증상은 "위층에서만 안 된다" 로 나타난다.** 어느 지점에 설 수 있는지 판정할 때는 발밑을 `SimConstants.SkinWidth` 만큼 올려서 본다 — 임의의 여유가 아니라 서버가 접촉면에 정지할 때 실제로 띄우는 값이고(`CollisionWorld.MoveBox`), 왕복 오차보다 네 자리 크고 벽 침투보다 두 자리 작아서 두 경우를 갈라낸다. 실제로 `MapGridBuilder` 가 이것 없이 위층 `FreeFloor` 를 전부 0 으로 만들었고, 격자 크기·플래그 검증·맵 해시는 그때도 모두 통과했다.

이미 겹친 상태에서 스윕하면 진입 시점이 음수로 나와 이동이 그대로 통과한다. 이동 전에 관통이 가장 얕은 축으로 밀어내는 단계를 먼저 거친다.

**요·피치를 방향 벡터로 바꾸는 식을 두 곳에 쓰지 않는다.** 전방이 `(sin yaw, 0, cos yaw)` 라는 규약은 `PlayerMovement.ApplyHorizontal` 에 있었고, 총알 방향을 다른 파일에서 다시 세우면 한쪽을 고칠 때 다른 쪽이 남는다. 증상은 **총알이 조준한 곳과 다른 쪽으로 날아가는 것**이고, 이동은 정상이므로 원인을 이동에서 찾지 않는다. `PlayerMovement.Forward(yaw, pitch)` 하나만 쓴다.

**한 틱에 지나간 선분 전체를 검사한다.** 총알은 120m/s 로 한 틱에 4m 를 지나고 벽은 0.25m 다 — 도착 지점만 검사하면 즉시 관통한다. 지오메트리와 플레이어를 **같은 선분에서 함께** 보고 더 가까운 쪽이 이기게 한다. 따로 검사하면 벽 뒤의 사람이 맞는다.

**와이어 상태는 판정이 끝난 뒤에 만든다.** `PlayerEntity.Wire` 를 이동 안에서 만들면 같은 틱의 판정(탈출·피격)이 세운 플래그가 다음 틱 스냅샷에나 나간다. 33ms 지연이라 눈에 잘 안 띄지만 출혈 흔적과 사라지는 몸이 그만큼 늦고, **틱 N 의 스냅샷은 틱 N 이 끝난 상태여야 한다**는 불변식이 조용히 깨진다. `Room.Advance` 는 이동 → 목표물·전투 판정 → `ProjectWire` 순서다.

**매치 판정 결과를 `PlayerState.Flags` 에 넣지 않는다.** 그 구조체는 결정적 시뮬레이션 상태이고 `StateHash` 를 이룬다 — 클라이언트가 예측할 수 없는 비트(출혈·쓰러짐·역할)를 섞으면 리컨실리에이션 비교가 **영구히** 어긋난다. 서버는 그것을 `PlayerEntity.MatchFlags` 에 따로 들고 인코딩할 때 OR 로 합친다. 그래서 **판정으로 비트를 내릴 수는 없다** — 사망을 `EntityFlags.Alive` 를 지우는 것으로 표현할 수 없고, `Downed` 를 따로 세우게 되는 이유가 그것이다.

**틱으로 나누어지지 않는 시간 상수는 올림·내림을 값으로 적는다.** 0.15초 × 30Hz = 4.5, 0.75초 × 30Hz = 22.5 다. 나눗셈을 그대로 두면 C# 이 잘라 내려 선택이 코드에서 사라지므로, `const int` 로 적고 왜 그 방향인지 주석을 남긴다. **방향은 경우마다 다르다** — 연사 간격은 내리면 서버가 클라이언트보다 관대해지므로(신뢰 경계가 넓어진다) 올리고, 무적 창은 짧아지는 것이 곧 규칙이 깨지는 것이므로(연사가 순간이동을 관통한다) 올린다. 같은 "올림" 이어도 근거가 다르면 따로 적는다.

**씨드를 결정하는 식은 한 곳에만 두고, 매치당 한 번 부른다.** 폴백이 `Environment.TickCount` 나 시계인 경우 **같은 식을 두 번 부르면 두 개의 다른 값이 나온다** — 클라이언트의 `MatchManager` 가 `BeginMatch` 와 `PlaceObjectives` 에서 같은 5줄을 각각 돌리고 있었고, 기본 설정에서 목표물 배치와 로컬 `Random` 이 서로 다른 씨드를 받았다. 서로 다른 것을 먹이므로 눈에 보이는 고장은 없었지만 "한 매치 한 씨드" 가 거짓이었고, 씨드를 지정해 배치를 재현하려는 시도가 절반만 동작했다. 값을 인자로 넘겨 그 상태를 표현할 수 없게 만든다.

**게임플레이 난수는 용도별로 수열을 나눈다.** 배치와 피격 순간이동이 같은 `DeterministicSequence` 를 쓰면, 배치가 값을 한 번 더 뽑는 변경이 순간이동 착지점을 바꾼다. 씨드를 상수로 흩어(`seed ^ 0x9E3779B9`) 따로 만든다.

## 상수

상수를 쓰는 파일에 두지 않는다. 두 곳에 모은다 — 클라이언트도 같은 값으로 계산해야 하면 `Shared/Simulation/SimConstants.cs`, 서버가 혼자 정하는 판정과 용량이면 `Modules/{모듈}/{모듈}Constants.cs`다. 룸 정원·입력 상한·입력 버퍼·송신 채널 크기는 함께 조정해야 맞는 값들인데, 선언이 흩어져 있으면 하나만 바꾸고 나머지를 놓친다. 증상은 조정한 값이 아무 효과가 없거나, 정원만 늘려 스냅샷 버퍼가 모자란 형태로 나타난다.

모듈 상수 파일은 성격별 중첩 static 클래스로 나눈다(`Rooms`, `Players`, `Validation`, `Sessions`). 한 파일에 모으는 것과 이름이 무엇의 상한인지 드러나는 것은 둘 다 필요하다.

같은 값을 두 번 적지 않고 한쪽에서 유도한다. `InputValidator`의 최대 수평 속도는 `SimConstants.MoveSpeed * SprintMultiplier`다. 숫자를 다시 적으면 이동 속도를 바꿀 때 판정만 옛 값으로 남는다. "방장/Seeker 없음" 을 뜻하는 `0xFF` 도 `RoomStateHeader.NoPlayer` 한 곳에서만 나온다 — 클라이언트 코드에 다시 적으면 정원을 늘릴 때 그 상수만 옛 값으로 남는다.

용량 상수를 설정 파일로 빼지 않는다. 룸 정원은 스냅샷 버퍼 크기를 정하고 입력 상한은 클라이언트 재전송 폭과 맞물린다. 재기동 없이 바뀌면 안 되는 값이다. 런타임에 바뀌어야 하는 것만 `RealtimeOptions`로 간다.

## 모듈 경계

경계 검사는 `.csproj`의 `ProjectReference` 선언을 읽는다. `Assembly.GetReferencedAssemblies()`는 타입을 실제로 쓰지 않으면 참조를 보고하지 않아, 코드가 적은 단계에서 검사가 공허하게 통과한다.

경계 테스트가 실제로 위반을 잡는지 확인할 때 `Infrastructure → Modules/X` 참조만 추가하면 순환 종속이 되어 restore 단계에서 MSB4006으로 먼저 실패한다. 테스트가 실행되지 않으므로 `Modules/X → Infrastructure` 참조를 함께 제거해야 확인된다.

모듈이 0개일 때 공허하게 통과하는 것을 막는 검사를 함께 둔다. 프로젝트 탐색 기준이 바뀌면 모든 경계 검사가 조용히 무력화된다.

룸 커맨드에 세션 객체를 싣지 않고 식별자만 싣는다. 룸이 전송 계층을 알지 않아도 되고, 소켓 없이 룸을 테스트할 수 있다.

## 영속화

DB는 아직 없다. 상태는 전부 메모리다.

맵 파일 스키마에 `System.Numerics.Vector3`를 노출하지 않는다. `X`·`Y`·`Z`가 프로퍼티가 아니라 필드라 기본 설정의 `System.Text.Json`이 빈 객체로 직렬화한다. 증상이 "맵이 통째로 사라짐"으로만 나타난다. `MinX`…`MaxZ` 개별 프로퍼티로 두고 변환 메서드를 둔다.

맵을 못 읽으면 기동을 실패시킨다. 빈 콜리전으로 조용히 올라가면 플레이어가 지형을 통과하고 증상이 로직 버그처럼 보인다. `min > max`인 박스도 거부한다. 스윕에서 조용히 무시되어 벽이 사라진 것처럼 된다.

## 네트워크

브라우저는 WebSocket 핸드셰이크에 커스텀 헤더를 붙일 수 없다. 프로토콜 버전과 룸은 쿼리스트링으로 받고 업그레이드 전에 검사한다. 헤더로 설계하면 서버 테스트는 통과하고 브라우저에서만 실패한다.

`WebSocket`은 동시 `SendAsync`를 허용하지 않는다. 세션당 송신 채널 하나와 펌프 하나로 직렬화하고, `SendAsync` 호출 지점을 그 펌프 한 곳으로 제한한다.

브라우저는 JS에서 ping 프레임을 보낼 수 없다. 유휴 연결 유지는 서버의 `KeepAliveInterval`이 유일한 수단이다.

WebGL 클라이언트에서 `binaryType`을 `arraybuffer`로 지정하지 않으면 `Blob`으로 수신되어 동기 읽기가 불가능하다.

스냅샷 헤더의 `AckedInputTick`은 수신자마다 다르다. 본문이 같아도 세션별로 인코딩해야 하며, 하나를 만들어 공유할 수 없다.

클라이언트가 보내는 입력 틱 번호의 도약을 제한한다. 큰 값을 그대로 받아들이면 마지막 처리 틱이 튀어 이후 입력이 전부 거부되고 플레이어가 영구히 굳는다.

입력이 끊겼을 때 마지막 입력을 무제한 반복하지 않는다. 입력을 끊은 클라이언트가 계속 달린다.

네트워크 조건 주입기에서 지연을 밀리초에서 틱으로 환산할 때 절삭하지 않고 반올림한다. 30Hz에서 한 틱이 33.3ms이므로 절삭하면 30ms 지터가 0틱이 되어 설정이 조용히 무효가 된다.

손실 주입에서 신뢰 전송은 제외한다. `Welcome`이 사라지면 접속이 그대로 멈춘다.

**한 번짜리 알림 대신 상태 전문을 반복 송신한다.** 룸 단계·방장·명단·역할·배치 씨드를 2Hz 로 계속 보낸다. 세션 송신 채널은 `Bounded(32, DropOldest)` 라 밀리면 오래된 프레임을 버리는데, 스냅샷은 다음 틱이 대체하므로 괜찮지만 "매치가 시작됐다" 를 한 번만 보내면 그 프레임이 버려진 클라이언트는 로비 화면에 영구히 남는다. 멱등한 전문이면 ack 와 재전송 장치가 필요 없다.

자발적 퇴장을 제어 메시지로 보내지 않는다. WebSocket 정상 종료(`NormalClosure`) 프레임으로 서버 로그에서 이미 회선 절단과 구분되고, 둘을 다 보내면 같은 소켓에 두 송신이 겹친다.

클라이언트가 보낸 제어 요청의 자격을 수신 지점에서 미리 걸러내지 않는다. 방장 여부와 단계 전이 가능성은 틱 루프가 소유한 상태로만 판단할 수 있어서, 수신 시점에 본 값은 한 틱 뒤의 진실과 어긋날 수 있다. 요청은 큐에 넣고 룸이 판단한다.

와이어에 실리는 문자열은 서버가 걸러 저장한다. 길이(세션 버퍼 상한), 제어문자(로그·화면 파손), 비ASCII(코덱 거부) 세 가지를 한 곳에서 처리한다. 코덱은 비ASCII 를 조용히 자르지 않고 예외로 막는다 — 잘라 보내면 필터가 빠진 경로가 있다는 신호를 놓친다.

## 클라이언트 연동

서버 권위 모드에서 클라이언트의 `CharacterController`를 함께 움직이지 않는다. 둘이 같은 트랜스폼을 밀면 벽에 붙었을 때와 낙하할 때 결과가 갈리고, 증상이 예측 코드 결함처럼 보인다. 입력 샘플링과 시점 회전만 남긴다.

`CharacterController`를 움직이지 않으면 `isGrounded`가 계속 false다. 애니메이터의 착지·낙하 상태를 그 값에서 읽으면 서버 위에서 영구히 공중에 뜬 자세가 된다. 착지 여부는 스냅샷의 `EntityFlags.OnGround`에서 받는다.

원격 플레이어를 `PlayerBody` 레이어(9)에 두지 않는다. 로컬 카메라가 자기 몸을 감추려고 그 레이어를 컬링하므로 아무도 서로를 볼 수 없게 된다. 증상은 "접속은 되는데 상대가 안 보임" 하나뿐이다.

원격 플레이어의 이동 입력을 와이어에 싣지 않는다. 트랜스폼 변위에서 역산한다. 걸음걸이가 실제 변위에서 유도되는 구조라 그것만으로 보폭·스윙축·기울기가 전부 맞는다.

로컬 플레이어에게는 보간 버퍼를 적용하지 않는다. 왕복 지연 위에 100ms가 더 붙어 조작이 무거워진다. 원격만 보간하고 로컬은 최신 스냅샷으로 짧게 감쇠한다. 단 스폰·리스폰처럼 큰 보정은 감쇠하지 않고 순간이동시킨다 — 끌면 지형을 통과해 미끄러져 들어간다.

점프 입력을 래치한다. 틱은 30Hz인데 렌더 루프는 더 빠르므로, 틱 사이에 눌린 점프를 그냥 읽으면 절반쯤 사라진다. 상호작용(E)도 같은 이유로 래치한다.

**엣지 버튼은 `LastInput` 에 남기지 않는다.** 새 입력이 없으면 서버가 마지막 입력을 최대 `MaxInputRepeatTicks` 만큼 반복하는데, 이동은 반복되어야 맞지만 한 번만 발동해야 하는 버튼은 그러면 안 된다. 요청을 세우는 곳을 **새 입력 갈래 하나로** 두는 것이 실제 방어이고, `InputValidator.WithoutEdgeButtons` 는 그 불변식이 두 곳의 협조에 의존한다는 사실에 대한 보험이다.

**`Jump` 은 예외이고, 그 예외가 수치 관계에 의존한다.** 점프도 엣지지만 반복돼도 재점프가 되지 않는다 — 반복 구간(3틱 = 0.1초)이 체공(0.7초)보다 짧아 반복된 `Jump` 가 전부 공중에서 소비되고 접지 검사에 걸린다. 오히려 공중에서 누른 점프가 3틱 재시도되어 **점프 버퍼로 동작**하므로 지우면 조작감을 잃는다. **위험은 그 관계가 코드에 적혀 있지 않다는 것**이었고, `JumpRepeatTests.반복이_공중에서_끝난다` 가 그것을 단정문으로 고정한다 — 지연 보상을 위해 반복 상한을 올리는 변경이 들어오면 그 테스트가 먼저 실패한다. **두 상수의 대소 관계가 규칙을 성립시키고 있으면 그 관계를 테스트로 적는다.**

**상호작용은 대상을 와이어에 싣지 않는다.** "나는 저 문을 쓴다" 를 클라이언트가 지목하면 사거리 밖의 문도 지목할 수 있고, 그것은 "내가 맞췄다" 와 같은 형태의 주장이다. 비트 하나만 보내고 **서버가 자기 좌표로 대상을 고른다.**

**서버 상태를 폴링으로 적용할 때는 반복 호출이 무해한지 확인한다.** 전문은 같은 값을 2Hz 로 계속 보내므로 적용 함수는 사실상 매 프레임 불린다. 값을 **더하면** 초당 두 배로 늘어나고(그래서 `SetCarriedKeys` 가 있고 `AddKeys` 를 쓰지 않는다), 부수 효과가 있으면 그것이 매 프레임 다시 시작한다 — `PlayerAgent.SetBleeding` 은 `BloodTrail` 을 켜므로 값이 바뀔 때만 불러야 하고, 그러지 않으면 **부상한 Runner 가 흔적을 전혀 남기지 않는다.**

**전이에서만 알림을 올린다.** 그리고 알림에 넣을 수 있는 정보가 무엇인지 매번 다시 본다 — 열쇠 삽입은 서버가 *누가* 넣었는지 말하지 않으므로 알림을 뺐고, 탈출은 *몇 명* 이 0.5초 늦게 오므로 숫자를 뺐고, 피격은 전문이 대상을 말하므로 살렸다. 비대칭 게임에서는 **알림도 정보 규칙**이다.

컴포넌트를 코드로 붙여 오브젝트를 조립할 때는 비활성 상태에서 필드를 채운 뒤 활성화한다. `AddComponent`는 그 자리에서 `Awake`를 돌리므로, 필드를 나중에 채우면 원격 플레이어가 자기를 로컬 플레이어로 알고 메인 카메라를 붙잡는다.

맵 콜리전 JSON의 부동소수점은 왕복 보존 형식(`"R"`)으로 쓴다. 자릿수를 줄이면 서버가 파싱한 값이 클라이언트의 값과 비트가 달라 맵 해시가 이유 없이 불일치한다.

`CollisionWorld`는 브로드페이즈가 없다. Backrooms는 박스 1367개여서 그 전제("수십 개")를 벗어나지만, 실측으로 8인 한 틱이 482us — 33.3ms 예산의 1.4%다. 브로드페이즈를 넣지 않는다. 넣으면 순회 순서가 바뀌어 스윕의 동시 접촉 타이브레이크가 달라지고, 클라이언트와 서버의 결과가 갈릴 수 있다.

접속 UI 가 열려 있는 동안 캐릭터 입력을 끊고 커서를 놓는다. 컨트롤러는 커서가 풀려 있으면 좌클릭으로 다시 잠그는데, 그것을 그대로 두면 버튼을 누르려는 클릭이 매번 커서를 재잠금한다.

씬 시작 시점에 로컬 플레이어를 서버 권위 모드로 바꾸지 않는다. 서버에 붙기 전까지는 캐릭터가 아무 입력에도 반응하지 않고, 원인이 드러나지 않는다. 권위는 **룸이 진행 단계가 될 때** 넘기고, 끊기거나 로비로 돌아가면 오프라인 조작으로 되돌린다. `Welcome` 시점이 아니다 — 대기 단계에서는 서버가 시뮬레이션하지 않아 스냅샷이 오지 않으므로, 그때 권위를 넘기면 캐릭터가 입력에도 반응하지 않고 서버 위치로도 옮겨지지 않는다.

접속을 씬 오브젝트가 소유하지 않는다. 세션은 씬보다 오래 살아야 로비에서 붙은 소켓이 게임 씬으로 넘어간다. 씬 쪽 컴포넌트는 스냅샷을 몸에 적용하는 일만 하고, 세션이 없으면 아무것도 하지 않는다 — 없을 때 만들어 버리면 오프라인으로 씬을 여는 것만으로 아무 곳에도 접속하지 않은 세션이 생긴다.

목표물 배치 씨드를 서버에서 받아 주입한다. 클라이언트의 매치 설정은 씨드가 0 이면 자기 시계로 난수를 만들고, 그러면 플레이어마다 문·열쇠·장치가 다른 곳에 생긴다. 증상은 "남이 없는 문에 열쇠를 꽂는다" 로 나타나 네트워크 문제로 보이지 않는다. 설정 에셋(`ScriptableObject`)에 써서 넘기지 않는다 — 런타임 변경이 에디터에서 그대로 저장되어 다음 오프라인 세션이 지난 매치의 씨드를 재사용한다.

명단 전원의 몸이 도착한 뒤에 매치를 시작한다. 원격 몸은 첫 스냅샷이 와야 만들어지고 역할은 시작 시점의 명단에만 배정되므로, 먼저 시작하면 늦게 도착한 플레이어가 역할 없이 남아 화면에서 관전자처럼 보인다.

룸 상태 전문을 받을 때마다 UI 를 다시 만들지 않는다. 전문은 2Hz 로 계속 오므로 로비에서 초당 두 번 트리를 새로 짓게 된다. 바뀌었는지 비교할 때는 들어온 명단을 **별도 버퍼로 읽어** 이전 것과 대조한다. 바로 덮어쓰면 한 명이 나가고 다른 한 명이 들어온 전문을 "바뀐 것 없음" 으로 판단해 화면에 나간 사람의 이름이 남는다.

접속을 소켓 열림과 `Welcome` 수신 두 단계로 나눈다. 합치면 "접속됐다는데 아무것도 안 보임"(룸 정원 초과) 이 정상 상태처럼 보인다. 두 단계 모두 타임아웃을 둔다 — 실패를 표면에 올리지 않으면 화면에 "접속 중" 만 영원히 남는다.

맵을 서버 전체에 하나만 두지 않는다. **맵 id** 로 고르고(`Game:Maps`), 룸을 만들 때 그 id 를 받는다. 룸 id 로 고르면 초대 코드 룸이 전부 기본 맵으로 조용히 열린다 — 설정 파일이 코드를 미리 알 수 없기 때문이다. 등록되지 않은 맵 id 는 **거절한다**. 기본 맵으로 대신 열면 증상이 맵 해시 불일치로만 나타나고 방을 만든 사람은 자기가 무엇을 잘못 골랐는지 알 수 없다. 빈 콜리전으로도 열지 않는다.

기동 시 로드한 맵을 전부 로그에 남기고, 룸 생성 시 그 룸이 어느 맵을 물었는지 다시 남긴다. 룸별로 맵이 다르면 하나만 찍어서는 클라이언트가 보고한 해시를 어느 쪽과 비교해야 할지 알 수 없다.

없는 룸 id 로 룸을 만들어 주지 않는다. 룸은 `POST /rooms` 로만 생기고 접속은 존재하는 코드로만 된다. 접속 경로에서 룸을 만들어 주면 초대 코드 모델의 전제("코드를 아는 사람만 들어온다")가 그 한 줄로 사라진다.

참가자가 없는 룸을 회수한다. 동시 룸 수에 상한이 없으므로 이것이 유일한 정리 수단이다 — 없으면 만들어진 방이 전부 메모리에 남고 코드 길이도 그 수에 따라 계속 늘어난다. 단계별로 다른 기준을 두지 않는다 — 전원이 나가면 룸이 스스로 대기 단계로 돌아가므로 "비어 있으면서 진행 중인 룸" 은 존재하지 않고, 그 분기는 도달할 수 없는 코드가 된다.

**회수 규칙을 "한 번이라도 사람이 있었는가" 로 가른다.** 있었으면 비는 즉시 회수하고, 아직 없었으면 만든 사람이 붙을 시간을 준다. "참가자 0이면 삭제" 를 문자 그대로 적용하면 안 되는 이유가 방을 만드는 절차에 있다 — `POST /rooms` 로 룸이 생긴 뒤 방장이 WebSocket 으로 붙기까지 참가자가 0이므로, 그 구간에서 즉시 회수하면 **모든 방이 만든 사람이 들어오기 전에 사라진다.** 증상은 "방을 만들었는데 없는 코드라고 한다" 이고, 방을 만드는 코드에는 잘못이 없어 원인이 회수 쪽이라는 것이 드러나지 않는다.

**노출은 기본값이 아니라 선택이다.** 방의 공개 여부는 만들 때 정하고 그 뒤로 바꾸지 못한다 — 비공개인 줄 알고 코드를 나눈 방이 나중에 목록에 뜨는 경로를 두지 않기 위해서다. `POST /rooms` 는 `isPublic` 이 **없으면 비공개**로 해석한다. 반대로 두면 필드를 모르는 옛 클라이언트가 만든 방이 본인도 모르게 목록에 뜬다.

**"전부 돌려주는" 목록 메서드를 두지 않는다.** 거르는 자리를 레지스트리 안(`ListPublicRooms`)에 두고 그 밖에 전체를 내주는 문을 만들지 않는다. 엔드포인트에서 거르면 전체를 주는 메서드가 남고, 다음에 목록이 필요한 곳에서 그쪽을 부르는 순간 비공개 방이 조용히 새어 나간다. 새지 않는 유일한 방법은 새는 메서드를 두지 않는 것이다.

**설정 플래그로 기능을 통째로 막는 것과 항목마다 동의를 받는 것은 다른 문제다.** `Realtime:AllowRoomListing` 은 목록이 모든 방을 내주던 시절, 통째로 막는 것 말고 할 수 있는 일이 없어 둔 플래그였다. 방마다 공개 여부가 생기자 근거가 사라졌고, 남겨 두면 공개를 선택한 방조차 뜨지 않아 그 선택이 무의미해진다. 다만 플래그를 없애면 그 경로가 **상시 열린다** — 개발 설정에서만 열리던 탓에 없던 요청 속도 제한을 같은 커밋에서 붙여야 한다.

**동시 룸 수에 상한을 두지 않는다. 대신 요청 속도를 제한한다.** 상한은 임의의 쿼리스트링으로 룸이 무한히 생기던 시절의 방어선이었고, 룸이 `POST /rooms` 로만 생기는 지금 막아야 하는 것은 룸의 개수가 아니라 요청의 속도다. 개수로 막으면 정상적인 사용자가 남이 만든 방 때문에 방을 못 만드는 반면, 속도로 막으면 각자가 자기 몫만 쓴다.

조회와 접속을 같은 요청 제한 양동이에 둔다. 조회만 막으면 조회를 건너뛰고 접속으로 코드를 찍을 수 있다 — `/ws` 도 없는 코드와 있는 코드에 다르게 답하므로 가려내는 데 충분하다. 룸 수 상한이 사라진 뒤로 코드가 남의 방을 막는 유일한 수단이므로, 시도 횟수를 세는 자리가 한 곳이어야 한다.

요청 제한에 대기열을 두지 않는다. 넘친 요청을 붙잡고 있으면 클라이언트는 느린 서버와 거절을 구분할 수 없고, 화면에는 "접속 중" 만 남는다.

요청 제한 미들웨어를 CORS 뒤에 둔다. 앞에 두면 거절된 응답에 CORS 헤더가 붙지 않아 브라우저가 `429` 를 읽지 못하고 네트워크 오류로 처리한다 — 화면에서 "서버에 닿지 못했다" 와 "너무 자주 요청했다" 가 구분되지 않는다.

초대 코드와 방장 토큰은 `RandomNumberGenerator` 로 만든다. `DeterministicRandom` 은 클라이언트와 같은 값을 내는 것이 목적이라 씨드를 알면 다음 값이 나온다 — 코드를 찍어 남의 방에 들어가거나 토큰을 추측해 방장을 가로채는 것을 막아야 하는 값에는 정반대의 성질이다.

초대 코드 알파벳에서 `i` `l` `o` `0` `1` 을 뺀다. 코드는 사람이 듣고 받아 적는 값이고, 한 글자만 갈리면 "없는 방" 과 구분되지 않는 실패가 된다. 제외된 문자를 비슷한 문자로 고쳐 주지도 않는다 — 사용자가 적은 것과 다른 방에 들어가고, 그때 화면에는 아무 설명이 없다.

무작위 바이트를 알파벳으로 접을 때 거부 표집을 쓴다. 256은 31로 나누어떨어지지 않으므로 나머지를 그대로 쓰면 앞쪽 8개 문자가 더 자주 나오고, 그만큼 코드 공간이 실질적으로 줄어든다. 룸 수 상한이 있던 동안에는 무해했지만, 코드가 유일한 방어선이 된 지금은 공간을 깎는 요소를 남길 이유가 없다.

**코드 길이를 고정하지 않는다.** 열려 있는 룸 수에 맞춰 늘려서 부하율(룸 수 / 코드 공간)을 일정하게 유지한다. 공간이 고정이면 룸이 늘수록 충돌이 잦아지고, 재시도 횟수를 다 쓰면 방 만들기가 실패한다. 길이를 다시 줄이지는 않는다 — 룸이 줄었다고 짧은 코드로 돌아가면 방금 사라진 방의 코드를 다른 방이 물려받을 확률만 올라간다. 클라이언트는 길이를 범위로만 검사한다. 한 값으로 못박으면 서버가 늘린 코드를 클라이언트가 형식 오류로 거부한다.

방장 승계는 퇴장 커맨드 안에서 한다. 접속 스레드에서 하면 퇴장이 적용되기 전이라 이미 나간 세션을 방장으로 만든다. 슬롯 반납이 틱 루프에서 일어나는 것과 같은 이유다.

방장 토큰을 매 요청에 요구하지 않는다. 접속할 때 한 번만 쓰고, 그 뒤 시작 권한은 "그 세션이 방장 세션인가" 로 판정한다. 매번 토큰을 요구하면 방장이 나갔을 때 남은 사람에게 줄 토큰이 없어 승계가 막히고, 방이 영구히 잠긴다.

클라이언트를 두 개 띄울 때 `runInBackground`를 켠다. 꺼져 있으면 포커스를 잃은 창이 스크립트를 멈추고, 상대가 얼어붙어 있다가 창을 클릭하면 순간이동한다. 증상이 보간이나 스냅샷 결함으로 보이지만 서버는 정상이다. 전체 화면 기본값도 창을 나란히 놓을 수 없게 만든다.

멀티플레이 확인은 Backrooms가 아니라 테스트 룸(`test-room`)에서 한다. 180m 미로에서는 두 클라이언트가 서로를 찾는 데 시간을 다 쓰고, 찾으려던 증상(떨림, 고무줄, 미끄러짐)은 상대가 화면에 있어야만 보인다.

## 문제 해결

30분 이상 걸린 문제만 기록한다. 증상 → 원인 → 대응 순으로 한 항목씩.

### 통과하는 쪽만 검사한 테스트는 규칙을 지키지 않는다

**증상.** `Control(EndMatch)` 를 쓰는 테스트가 여섯 개 있었고 전부 통과했다. 그런데 여섯 개가 모두
**방장 세션에서만** 보냈다 — "방장이 끝낼 수 있다" 를 여섯 번 검사하고 "방장이 아니면 끝낼 수 없다"
를 한 번도 검사하지 않았다. `IsAuthorized` 호출을 지우는 변경은 그 여섯 개를 모두 통과한다.

**원인.** 정상 경로는 기능을 만들면서 자연히 테스트가 쌓이지만, **거부 경로는 누가 일부러 찾지
않으면 비어 있다.** 그리고 인증에서 진짜 규칙은 거부 쪽이다 — 이 경로가 지키는 것이 "클라이언트
권위로 게임 결과를 결정하지 않는다" 이고, 서버가 결과 코드를 아직 정하지 않는 동안 그 인증이 그
규칙의 전부였다.

**대응.** 인증·검증·상한이 있는 곳은 **거부되는 호출을 함께 검사한다.** 그리고 같은 검사 함수를 쓰는
명령이 여럿이면 각각 확인한다 — `EndMatch` 와 `ReturnToLobby` 는 같은 `IsAuthorized` 를 쓰지만 별개의
명령이므로 한쪽만 검사하면 다른 쪽이 열린 채 남는다. **일반화: "아닌 쪽" 이 검사되지 않은 자리를
찾는다** — 구성이 없는 쪽(열화 경로), 판정이 겹치는 쪽(경합), 권한이 없는 쪽(거부).

### 개발 루프가 쓰는 맵의 열화 경로는 별도로 고정한다

**증상.** 없었다 — 그것이 문제다. `test-room` 은 의도적으로 격자를 내놓지 않고(플랫폼과 커버 블록이
있어 전부 `FreeFloor` 로 채울 수 없다), `MultiplayerTest` 씬이 그 룸에 붙는다. **두 클라이언트로
확인할 때 실제로 도는 것은 격자 없는 열화 모드**인데 전투 쪽 테스트가 하나도 없었다.

**원인.** 두 사실이 각각 문서에 있었고 곱해 본 사람이 없었다. 그리고 **격자가 있는 맵의 테스트는
순간이동 경로를 바꾸는 변경에 전부 통과한다** — 그래서 그런 변경은 자동 테스트를 통과하고 개발
루프만 조용히 깨뜨린다. 개발 루프가 깨지면 사람이 스모크를 돌리는 것 자체가 막힌다.

**대응.** 격자가 필요한 곳을 세어 경계를 확정하고(피격 순간이동 하나뿐이었다) 그 경계를 테스트로
고정했다(`GridlessMatchTests`). **일반화: 개발·CI 가 쓰는 구성이 프로덕션 구성의 부분집합이면, 그
부분집합에서만 도는 경로를 따로 고정한다.** 전체 구성의 테스트가 그것을 대신해 주지 않는다.

### 맵 파일 검사는 한 곳에만 쓴다 — 서버와 export 가 갈려 있었다

**증상.** export 가 성공했다고 말한 파일로 서버가 기동을 실패한다. 또는 격자가 없는 맵 파일이
정상으로 쓰이고, 매치에 열쇠도 문도 생기지 않는다.

**원인.** 서버 `MapLoader` 는 네 가지를 검사했고(박스 없음, `min > max`, 스폰 없음, 격자 불일치)
export 는 그중 격자 하나만 봤다. 검사가 두 곳에 있으면 한쪽이 늘어날 때 다른 쪽은 그대로 남는다.
게다가 `MapGridBuilder.MarkFreeFloor` 는 표시한 셀 수를 **그 용도로** 돌려주는데 export 가 그 값을
버렸다 — 0 은 격자와 콜리전이 서로 다른 좌표계를 말한다는 뜻이고, 그때도 크기 검증과 맵 해시는
전부 통과한다.

**대응.** `Shared/Collision/MapDataValidator.cs` 하나가 검사를 갖고, `MapLoader` 와 에디터 export 가
같은 것을 부른다. 두 층으로 나뉘며 기준은 비용이다 — `TryValidateSchema` 는 파일이 자기 자신과
맞는지만 보므로 기동 경로에 두고, `InspectSimulation` 은 시뮬레이션을 돌려 검산하므로 export 와
테스트만 부른다.

**남는 규칙.** **export 시점에 잡을 수 있는 것을 서버 기동이나 테스트로 넘기지 않는다.** 판정에
쓰는 코드가 `Shared` 에 있으면 Unity 에서도 그대로 돌고, export 는 커밋 전이며 `dotnet test` 는
커밋 뒤다.

### Unity EditMode 테스트는 예상하지 못한 `LogError` 만으로 실패한다

**증상.** 단정이 전부 통과하는데 테스트가 실패한다. 메시지는
`Unhandled log message: '[Error] …'. Use UnityEngine.TestTools.LogAssert.Expect` 다.

**원인.** Unity 의 테스트 프레임워크는 테스트가 도는 동안 나온 `Debug.LogError` 를 실패로 센다.
검사 대상 코드가 **의도적으로** 에러를 남기는 경우(여기서는 `MapExport.AttachGrid` 가 격자를
버렸다는 것을 사람에게 알린다)에도 그렇다.

**대응.** 그 로그를 기대한다고 미리 말한다:
`LogAssert.Expect(LogType.Error, new Regex("격자가 잘못됐다"))`. 로그를 없애는 쪽으로 고치면 안
된다 — 그 로그가 런타임에서 격자가 사라진 것을 알리는 유일한 신호다.

**곁들여.** 이 프로젝트에는 EditMode 테스트를 CLI 로 돌리는 길이 없지만, MCP 로
`TestRunnerApi.Execute(new ExecutionSettings(new Filter { testMode = TestMode.EditMode }))` 를
띄우고 `[태그]` 를 붙여 `Debug.Log` 로 결과를 남기면 콘솔 로그로 받아볼 수 있다. 콜백은
`ICommandScript` 에 **직접** 구현한다 — 중첩 클래스는 MCP 의 커맨드 래퍼가 네임스페이스 밖으로
복제해 `CS1527` 이 된다.

### 브로드페이즈는 필요 없다 — 재기 전의 추정이 한 자리 이상 틀렸다

**측정값** (Release, `backrooms.json` 736박스 / 2450셀):

| 무엇 | 1회 | 뜻 |
|---|---|---|
| `PlayerMovement.Step` | 0.0129 ms | 8명 한 틱 = **0.103 ms**, 33.3ms 예산의 **0.31%** |
| `MapGridBuilder.MarkFreeFloor` | **1.3 ms** | export 와 접속 시 1회 |
| `CollisionWorld.Raycast` | 1.98 µs | 사격 1회 |

**추정은 이랬다.** 겹침 해소가 최대 4회 반복 × 736박스이므로 `MarkFreeFloor` 는 2450셀 ×
4 × 736 ≈ 720만 회 AABB 검사이고 수백 ms 일 것이다. 상한 자체는 맞지만 **실제로는 1.3 ms 다.**
겹치지 않는 자리에서는 첫 패스가 `resolved` 를 참으로 두고 끝나므로 반복이 1회이고,
`Aabb.Overlaps` 는 비교 여섯 번이다. 이동도 같은 이유로 예산의 0.3% 다.

**대응. 브로드페이즈를 넣지 않는다.** `CollisionWorld.cs` 의 "박스 수십 개 규모" 주석은 지금
736박스에 비해 낡았지만, 그 주석이 가리키는 결론(브로드페이즈 없이 충분하다)은 여전히 맞다.
넣으면 값은 크지 않고 위험은 실질적이다 — `Depenetrate` 는 박스를 **순차적으로** 밀어내므로
순회 순서가 결과를 바꾸고, 한 패스 중에 위치가 움직여 처음에는 겹치지 않던 박스와 겹칠 수 있다.
후보 집합을 미리 정하는 방식으로는 그 경우에 브루트포스와 같은 결과를 보장할 수 없고, 어긋남은
클라이언트 예측과 비트가 갈리는 것이므로 증상이 "특정 위치에서만 캐릭터가 튐" 으로만 나타난다.

**남는 규칙.** **`O(N)` 이 보이면 재고 나서 고친다.** 여기서 추정이 틀린 이유는 상한을 실제
값으로 읽은 것이고, 그 차이가 한 자리 이상이었다. 박스 수를 크게 늘리는 변경(층 추가, 프랍 포함)
을 할 때 이 표를 기준선으로 다시 잰다.

### `FreeFloor` 는 "겹치지 않는다" 이고 "서 있을 수 있다" 가 아니다

**증상.** 없었다 — 격자가 통째로 지형 밖으로 밀려도 모든 검사가 통과한다.

**원인.** `MapGridBuilder.IsFree` 는 플레이어 박스가 지형과 겹치는지만 본다. 격자의 원점이나 셀
크기가 어긋나 셀 중심이 맵 밖으로 나가면, 그곳은 **아무것과도 겹치지 않으므로 전부 통과한다.**
증상이 "`FreeFloor` 가 0 개" 로 나타날 것이라 기대하기 쉬운데 정반대로 **전부 `FreeFloor` 가 된다.**
크기 검증도 맵 해시도 이 상태를 통과한다.

**대응.** 검산(`MapDataValidator.InspectSimulation`)이 `FreeFloor` 셀마다 `CollisionWorld.IsGrounded`
로 발밑에 바닥이 있는지 함께 본다. `MarkFreeFloor` 자체는 건드리지 않았다 — 그쪽을 고치면 플래그가
달라져 모든 맵의 해시가 바뀌고, 그 재-export 로 늘어나는 정보는 없다. 파일이 옳은지 보는 것은
검사의 몫이고 파일에 무엇을 적을지는 export 의 몫이다.

**남는 규칙.** 겹침 판정으로 "여기 있어도 되는가" 를 물을 때, **허공이 통과한다**는 것을 항상 함께
본다.

### 기록해 둔 차단 사유를 확인하지 않고 재사용하면 사실처럼 굳는다

**증상.** 클라이언트 EditMode 테스트 인프라(IG-018)를 세 이터레이션에 걸쳐 미뤘다. 근거는 매번
같았다 — "Unity 의 asmdef 는 `Assembly-CSharp` 를 참조할 수 없으므로 `Assets/Scripts` 전체를
asmdef 로 옮기는 큰 변경이 선행된다". 세 번째에는 그것이 확립된 사실처럼 읽혔다.

**원인.** 그 전제는 **asmdef 로 테스트 어셈블리를 만들 때만** 성립한다. 생성된 프로젝트를 열어
보니 `Assembly-CSharp-Editor.csproj` 가 `nunit.framework`·`UnityEditor.TestRunner`·
`UnityEngine.TestRunner` 를 이미 참조하고, `Assembly-CSharp` 와 `Shared` 를 `ProjectReference` 로
갖고 있었다(에디터 스크립트가 런타임 컴포넌트를 조작하므로 당연하다). **`Assets/Editor/` 아래에
테스트를 두면 아무 설정도 필요 없었다.**

**대응.** 첫 기록에 "확인해야 한다" 고 썼으면 **인용하기 전에 확인한다.** 특히 자기 기록을 다음
이터레이션의 근거로 복사할 때가 위험하다 — 근거의 출처가 조사가 아니라 자기 자신이 된다.
차단 사유는 **어떻게 확인했는지**를 함께 적어야 다음 사람(과 다음 이터레이션의 자신)이 그것을
검증 가능한 주장으로 읽는다.

### 필터로만 돌린 테스트는 스폰 배치의 우연에 기대고 있을 수 있다

**증상.** 피격 테스트 11개가 `--filter` 로는 전부 통과하고 **전체 실행에서만 하나가 실패**했다.
실패한 것은 "쏜 사람은 자기 총알에 맞지 않는다" 인데, 실패 내용은 *Runner* 의 피격 수가 1 이었다.

**원인.** 테스트 픽스처의 두 스폰은 `(0,0,0)` 과 `(-2,0,0)` 으로 **X 만 다르다.** 그리고 누가
Seeker 인지는 매치마다 무작위다. Seeker 가 `(-2,0,0)` 으로 뽑히면 +X 로 쏜 총알의 사격선에
Runner 가 정확히 놓인다 — 반대로 뽑히면 아무도 없다. 실행 순서에 따라 다른 매치 상태에서
시작하므로 필터 실행과 전체 실행의 결과가 갈렸다.

**대응.** 무작위가 섞인 판정을 검사할 때는 **판정 대상의 자리를 고정한다.** 이 테스트들은 이제
사격 전에 Runner 를 사수 앞 2m 로 옮긴다 — 피격 순간이동의 착지점도 무작위이고 픽스처 맵에는
벽이 있어서, 옮겨진 자리를 그대로 조준하면 "벽 뒤로 갔는지" 에 따라 또 흔들린다. 그리고
**고친 뒤에는 전체 실행을 여러 번 돌려 확인한다** — 이 문제는 한 번의 통과로는 구별되지 않는다.

### 소켓 없는 참가자를 넣으면 "참가자에게는 세션이 있다" 는 전제가 여러 곳에서 드러난다

**증상.** 봇을 명단에 넣는 것 자체는 20줄이었다. 그 뒤에 나온 것들이 본체다 — 봇이 방장을 승계하고,
사람이 다 나간 방이 회수되지 않고, 전문이 없는 세션으로 인코딩되고, 리빌 중에 봇만 움직이려 했다.

**원인.** 룸은 참가자마다 소켓이 있다는 전제 위에 쓰여 있었고, 그 전제가 **한 곳에 적혀 있지 않았다.**
`LowestRemainingSessionId`(방장 승계), `Leave` 의 `_players.Count == 0`(빈 방 판정), 네 곳의
`Broadcast*`(수신자 순회), `StepPlayer`(입력 버퍼)가 각각 그것에 기대고 있었다. 어느 하나도 틀린
코드가 아니었다 — 전제가 깨진 것이다.

**대응.** 넣기 전에 그 전제를 쓰는 자리를 세어 표로 만들고 하나씩 막았다(`test-room-bots-plan.md` §4).
증상으로 찾으면 두 개는 보이지 않는다 — 정적 룸은 전원에게 시작 권한이 있어 방장 승계가 잘못되어도
화면에 아무 일도 일어나지 않고, 회수 실패는 며칠 뒤 방 목록에서만 보인다. **일반화: 어떤 타입에
"항상 X 가 있다" 는 전제가 있고 X 없는 개체를 새로 넣는다면, 증상을 기다리지 말고 그 전제를 읽는
자리를 먼저 센다.** 그리고 그중 **증상이 없는 자리**가 가장 위험하다.

곁따라 확정한 규칙 둘. **봇은 `InputFrame` 만 만든다** — 위치를 직접 옮기는 봇으로 확인한 것은 사람에게
성립하지 않으므로, 두뇌에 넘기는 시야에서 산 객체를 빼고 값 복사와 `IReadOnlyList` 만 남겼다.
그리고 **개발 전용 기능은 설정 기본값만으로 막지 않는다** — 개발 환경 밖에서 켜져 있으면 기동을
멈춘다. 조용히 꺼 주면 설정이 거짓말을 하고, 조용히 켜 두면 실제 사용자가 `BOT 2` 와 같은 방에 들어간다.

### 권위와 그 권위에 대한 진술이 어긋나면 증상이 UI 에만 나타난다

**증상.** 정적 룸(`test`)에서 아무도 **게임 시작** 을 누를 수 없었다. 버튼 옆에는 "방장이 시작하기를
기다린다" 가 떠 있었고, 그 방에는 방장이 될 사람이 없었다.

**원인.** `Room.IsAuthorized` 는 정적 룸에서 **처음부터 전원의 요청을 받아들이고 있었다.** 서버 쪽
규칙은 옳았고 테스트도 그것을 고정하고 있었다. 그런데 명단 전문의 방장 자리에는 `NoPlayer`(255)가
실렸다 — 그 룸은 `POST /rooms` 를 지나지 않아 방장 토큰을 받은 세션이 없기 때문이다. 클라이언트는
`RoomState.HostPlayerId == LocalPlayerId` 로 방장을 판단하므로, **서버가 받아 줄 요청을 클라이언트가
보내지 않았다.** 서버 테스트로는 절대 보이지 않는다 — 서버는 요청이 오면 정상적으로 처리한다.

**대응.** 정적 룸에서만 명단 전문을 세션별로 인코딩해 방장 자리에 받는 사람 자신의 id 를 싣는다.
권한을 새로 준 것이 아니라 이미 있던 권한을 전문이 말하게 한 것이다. **일반화: "누가 무엇을 할 수
있는가" 를 서버가 판정하는데 클라이언트가 그 판정을 자기 사본으로 예측해서 UI 를 만든다면, 그 예측의
입력이 실제 판정과 같은 것인지 확인한다.** 두 곳이 어긋나면 서버 테스트는 전부 통과하고 화면만
고장난 것처럼 보인다.

곁따라 하나 알아 둘 것. 방장이 하는 일이 시작 말고도 있으면 그것도 전원이 하게 된다 — 여기서는
매치 결과 보고(`MatchSync.ResolvesOutcome`)가 그랬다. 룸이 진행 중일 때만 종료를 받아들이므로 먼저
온 하나가 이기고 나머지는 무시된다. **한 명이 하기로 되어 있던 일을 전원이 하게 만드는 변경은,
그 일이 여러 번 일어나도 되는지 확인해야 한다.**

### 테스트가 슬롯을 예약하지 않으면 슬롯을 예약하는 참가자와 충돌한다

**증상.** 봇 테스트에서 한 룸에 `PlayerId` 가 0 인 참가자가 둘이 되었다. 사람이 나간 뒤 봇이 그 자리를
채우는 경로에서만 나타났다.

**원인.** 슬롯 예약은 접속 경로(`/ws`)에 있고, 룸 테스트는 `RoomCommand.Join` 에 `PlayerId` 를 손으로
넘긴다 — 그래서 `_slots` 배열이 전부 비어 있다. 사람만 있는 룸에서는 아무 문제가 없다. **봇은 진짜
참가자이므로 `TryReserveSlot` 으로 자리를 받고**, 그때 비어 있는 배열을 보고 사람이 쓰는 번호를 집는다.

**대응.** 픽스처에 예약까지 하는 `JoinHuman` 을 두고 봇을 쓰는 테스트는 그것으로 참가시킨다.
**일반화: 테스트 조립이 프로덕션 경로의 일부를 건너뛰고 있다면, 그 건너뛴 부분에 의존하는 기능이
들어올 때 조립부터 고친다.** 기능을 조립에 맞추면 프로덕션에서만 깨진다.

### 무작위 술래 선정이 남긴 flaky 테스트 둘 — 원인 확정, 서로 다른 원인이었다

**증상.** `EndMatchAuthorityTests.종료_뒤에도_최종_수치가_전문에_남는다` 와
`HitTests.맞으면_다른_곳으로_옮겨진다` 가 전체 실행에서 간헐적으로 실패했다. 8회 실행에서 전자가
3회, 후자가 1회. 같은 계열로 보였지만 **원인이 달랐고, 한쪽을 고치는 대응은 다른 쪽에 닿지
않는다.**

**원인 1 — 역할을 가정했다.** 앞의 테스트는 전문을 세션 2의 사본으로 읽고 열쇠 진행도가 실려
있기를 기대했다. `Room.PickSeeker` 는 `Random.Shared` 로 고르므로 세션 2가 술래인 경우가 절반이고,
그때 코덱이 열쇠 진행도를 0 으로 만든다(그것이 코덱의 일이다). **역할에 따라 내용이 달라지는
전문을 읽을 때는 누가 그 역할인지 물어봐야 한다** — 룸 상태의 `SeekerPlayerId` 에 있다.

**원인 2 — 판정 좌표가 격자 위에 있었다.** 뒤의 테스트는 Runner 를 사수 앞 2m 에 세우고 쏜 뒤
좌표가 바뀌었는지 본다. 픽스처의 셀 중심은 4m 간격의 {-10,-6,-2,2,6,10} 이고 스폰 하나가
(-2,0,0) 이라, 그 2m 앞은 **X 와 Z 가 모두 셀 중심인 (-2,0,2)** 다. 피격 순간이동은 무작위
`FreeFloor` 셀 중심으로 보내므로 그 셀이 뽑히면 사격 전후의 좌표가 같아진다. 순간이동은 정상으로
일어났고 테스트만 그것을 볼 수 없었다.

**대응.** 전자는 명단에서 Runner 를 찾아 그 세션으로 읽는다. 후자는 거리를 2.5m 로 옮겨 판정
좌표를 격자에서 뺐다 — 스폰을 옮기지 않은 이유는 다른 테스트들이 두 스폰의 2m 간격에 기대고 있기
때문이다(`EscapeTests` 의 반경, `HitTests` 의 "한 틱 안에 닿는다"). 고친 뒤 전체 실행 10회에서
실패 0건.

**남는 규칙.** 무작위가 섞인 판정을 좌표 비교로 확인할 때는 **비교하는 좌표가 그 무작위의 값역에
들어 있는지** 본다. 격자에서 뽑는 무작위라면 판정 좌표를 격자 밖으로 옮기는 것이 가장 싸다.

### bool 파라미터의 뜻을 뒤집으면 호출부가 조용히 반대가 된다

**증상.** `Room` 생성자의 플래그를 `requiresHost` 에서 `isStatic` 으로 바꾼 뒤, 컴파일은 통과하고 테스트 두 개만 실패했다. 실패한 것은 "방장이 아니면 시작할 수 없다" 였고, 방장이 아닌 세션이 매치를 시작하고 있었다.

**원인.** 테스트 픽스처가 같은 자리를 위치 인수로 넘기고 있었다. 픽스처 쪽 파라미터 이름은 그대로 `requiresHost` 였으므로 `Create(requiresHost: false)` 라는 호출은 여전히 컴파일되었고, 그 값이 `isStatic` 자리에 들어가 의미만 정확히 반대가 되었다. 이름이 맞아 보이는 호출부가 뜻이 뒤집힌 채로 통과한다.

**대응.** 플래그의 뜻을 뒤집을 때는 타입이 같더라도 호출부를 전부 훑는다. 테스트가 잡아 준 것은 운이었고, 잡히지 않았다면 정적 룸이 아닌 모든 룸에서 아무나 매치를 시작할 수 있었다.
