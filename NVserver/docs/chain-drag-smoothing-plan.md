# 체인 견인 스무딩 계획

## 증상

서버 권위 매치에서 Seeker 가 3발을 소진해 체인에 걸리면 제단까지 자동으로 끌려간다.
이 견인이 부드럽지 않다 — 화면이 계단식으로 뚝뚝 끊기고, 간헐적으로 순간이동하듯 튄다.
오프라인(비서버) 매치의 견인은 매끈하다. 즉 문제는 견인 규칙이 아니라 **서버가 옮긴 위치를
클라이언트가 화면에 옮겨 그리는 경로**에 있다.

## 원인 진단 (코드 근거)

끊김은 한 가지가 아니라 네 가지가 겹친 결과다. 큰 것부터.

### 1. 견인 속도가 로컬 스냅 임계를 넘는다 — 순간이동처럼 튀는 주범

`MatchConstants.ChainDragSpeed` = **45 m/s** → 30Hz 틱당 **1.5 m** 이동.
`NetworkBootstrap.localSnapDistance` = **2 m** — 현재 위치와 최신 스냅샷의 거리가 이걸 넘으면
감쇠 없이 즉시 순간이동시킨다(`NetworkBootstrap.ApplyLocal`, 스폰·리스폰용 분기).

스냅샷 하나만 늦게 도착하거나 프레임이 출렁이면 두 틱 분량(3 m)이 한 번에 도착해
임계를 넘고, 견인 내내 이 분기를 반복해서 때린다. "끌려가다가 순간 튄다"는 증상이 이것이다.

### 2. 로컬 플레이어에는 보간 버퍼가 없다 — 30Hz 계단이 그대로 보인다

원격 몸은 100ms 보간 버퍼로 스냅샷 사이를 펴서 그린다. 로컬 플레이어는 조작 지연을
얹지 않으려고 **최신 스냅샷 하나**를 `SmoothDamp`(0.05s) 로 짧게 쫓는다
(`NetworkBootstrap.ApplyLocal` — `TryLatest`). 평상시에는 옳은 선택이지만, 견인 중에는
33ms 마다 1.5 m 씩 점프하는 목표를 렌더 프레임마다 쫓는 구조가 되어 30Hz 계단이
화면에 그대로 남는다. 원격 시점에서 보는 체인 걸린 Seeker 는 매끈하고 **자기 화면만
끊기는** 이유가 이것이다.

### 3. 서버 견인은 등속 · 선형이다 — 시작과 도착이 급하다

`Room.StepChain` 은 경과 비율 t 를 그대로 경로 거리에 곱한다(등속). 오프라인 경로
(`ChainDrag.Run` 의 비서버 분기)는 `Mathf.SmoothStep` 이징을 쓰므로, 서버 매치의 견인은
출발이 홱 당겨지고 도착이 뚝 멈춰 오프라인과 느낌 자체가 다르다.

### 4. 스냅샷 Velocity 가 0 이다 — 클라이언트가 쓸 힌트가 없다

`StepChain` 은 매 틱 `state.Velocity = Vector3.Zero` 를 쓴다. 클라이언트가 외삽이나
보간 힌트로 쓸 재료가 없다. (부수: 변위 기반이라 애니메이터는 무관하지만, 다리가
45 m/s 변위를 재서 미친 듯이 젓는지도 확인 대상이다.)

## 개선안 — 3단계

### 1단계 (핵심): 체인 중에는 로컬 플레이어도 보간 버퍼를 태운다

체인에 걸린 동안 입력은 위치에 아무 영향이 없다 — 서버가 입력을 소비만 하고 무력화한다
(`Room.cs` 의 `Chained` 분기). 즉 **보간 지연 100ms 를 얹어도 조작감 손실이 0 인 유일한
구간**이고, 로컬에 보간 버퍼를 쓰지 않던 이유가 이 구간에는 성립하지 않는다.

- `NetworkBootstrap.ApplyLocal` 에서 로컬 엔티티의 `EntityFlags.Frozen` (서버가
  `MovementLocked || Chained` 일 때 세우는 비트)을 읽어, 서 있는 동안은 지금처럼
  `TryLatest` + `SmoothDamp`, Frozen 인 동안은 원격과 같은 `TrySample`(100ms 보간)로 전환.
- **진입/이탈 팝 방지**: 모드가 바뀌는 프레임에 목표가 100ms 어치 점프하므로, 전환 직후
  잠깐은 기존 `SmoothDamp`(localSmoothing) 로 크로스페이드해서 잇는다.
- **스냅 임계**: Frozen 동안 `localSnapDistance` 를 견인 기준으로 상향
  (예: `ChainDragSpeed × 0.17s ≈ 7.5 m` — 보간 지연 + 2틱 여유) 하거나, 보간 샘플에는
  스냅 분기를 아예 적용하지 않는다. 경로는 서버가 벽을 뚫지 않게 이미 보장하고
  (`GridRoute`), 로컬 적용은 `ApplyNetworkState` 가 transform 을 직접 쓰므로
  CharacterController 의 밀어내기와도 싸우지 않는다.

이 단계만으로 증상 대부분이 사라져야 한다. 여기서 한 번 검증하고 다음으로 간다.

### 2단계: 서버 견인에 이징을 넣어 오프라인과 느낌을 맞춘다

- `Room.StepChain` 의 t 에 SmoothStep(`t·t·(3−2t)`) 을 적용. 이 코드는 서버 전용이고
  클라이언트가 이 이동을 예측하지 않으므로 `Shared` 의 결정론 제약(DeterministicMath)과
  무관하다 — `Room.cs` 안에서 자유롭게 계산해도 된다.
- **주의**: 이징의 순간 최고 속도는 평균의 1.5배(≈ 67 m/s, 틱당 ≈ 2.2 m). 1단계의
  스냅 임계 정리가 **선행되지 않으면** 이 단계가 오히려 튐을 늘린다. 순서 고정.
- `ChainTests` 에 추가: 이징 후에도 시작 틱 위치·도착 틱 위치가 불변일 것, 진행이
  단조 증가일 것.

### 3단계 (선택): 스냅샷 Velocity 에 실제 견인 속도를 기록

- `StepChain` 이 이번 틱의 실제 진행 벡터를 `state.Velocity` 에 쓰면, 클라이언트
  보간·애니메이션이 쓸 힌트가 생긴다.
- **선행 확인**: Velocity = 0 에 기대는 소비자가 있는지 (클라 애니메이터는 변위로 재므로
  무관할 가능성이 높지만, 착지 판정 등 `Velocity.y` 소비처가 있다). 확인 전에는 넣지 않는다.

**결론: 실행하지 않는다.** 선행 확인에서 전제가 무너졌다 — 와이어(`EntityState`, 13바이트)에
속도 필드가 아예 없다. 서버의 `state.Velocity` 는 서버 시뮬레이션 내부 값이고 클라이언트에
도달할 경로가 없으며, 클라이언트가 쓰는 속도는 `SnapshotBuffer.Lerp` 가 두 스냅샷의 위치
차이에서 합성한다 — 1단계로 로컬 플레이어가 체인 중 그 보간을 타게 되면서 이 힌트는 이미
생겼다. 와이어에 필드를 더하는 것은 프로토콜 버전을 올리고 모든 스냅샷을 키우는 대가라,
보간이 공짜로 만드는 값을 위해 지불할 이유가 없다.

## 검증

- **수치 (자가 검증 가능)**: 견인 중 프레임 간 이동 거리를 로그로 남겨 표준편차·최댓값을
  잰다. 스냅 분기 히트 카운트가 견인 중 **0** 이어야 한다. 애니메이션 부드러움은 화면으로
  자가 검증할 수 없으므로(NVproject/CLAUDE.md) 수치가 1차 판정.
- **시각**: **Tools ▸ NV ▸ Build and Launch 2 Clients** 로 두 클라이언트를 띄워 사용자
  육안 확인 — 체인 걸린 본인 시점과, 그를 보는 원격 시점 둘 다.
- **회귀**: `dotnet test` (특히 `ChainTests`). 원격 시점은 원래 100ms 버퍼라 변화가
  없어야 정상이다.

## 건드리지 않는 것

- `ChainDrag.cs` 의 서버 주도 분기 — 이미 그리기 전용으로 옳게 물러나 있다. 몸의 이동을
  클라이언트가 다시 가져오는 방향은 금지: 다음 스냅샷이 되돌려서 지금보다 나빠진다.
- 오프라인 견인 경로 — 이미 SmoothStep 이라 변경 없음.
- `ChainDragSpeed` 45 등 고정 파라미터 — 밸런스 값이므로 유지. 부드러움은 전달 경로의
  문제지 속도의 문제가 아니다.
