# 테스트 룸을 맵·모드 전체로 넓히는 계획

> **상태: 계획(2026-08-05).** `test-room-bots-plan.md`(구현 완료)의 후속이다. 그 계획이 "봇으로
> 사람 하나가 매치를 끝까지 돌린다"를 만들었다면, 이 계획은 그 장치를 **서버가 여는 모든 룸
> 구성 — 지금은 맵, 앞으로는 게임 모드 — 에 최소 비용으로 붙이는 구조**를 만든다.

배경은 `architecture.md`(금지 목록·신뢰 경계), `structure.md`(파일 배치 8문 표),
`conventions.md`(함정 목록), `test-room-bots-plan.md`(봇 설계의 근거 전부)다. **이 계획도
규칙을 바꾸지 않는다** — 봇은 여전히 `InputFrame` 만 만들고, 테스트 룸의 모든 편의는
정적 룸 경계 안에만 있다.

## 1. 지금 무엇이 있는가

| 구성 요소 | 현재 형태 | 근거 |
|---|---|---|
| 정적(테스트) 룸 | `Game:StaticRooms` — **룸 id → 맵 id 문자열 한 쌍이 전부다.** 기동 시 생성, 회수 없음, 공개, 방장 없음, 전원 시작 권한 | `StaticRooms.cs`, `RoomRegistry.CreateStaticRooms` |
| 봇 설정 | `Realtime:Bots` — **서버 전역 하나.** `Enabled`·`FillTo`·`Behavior`·`Role`·`Seed` 가 모든 정적 룸에 동일하게 걸린다 | `BotOptions.cs`, `RoomRegistry.CreateStaticRooms` 의 `bots: _options.Bots` 한 줄 |
| 봇 능력 | `Idle` / `Wander` / `Objective`. `Objective` 는 경로 탐색이 없어 **열린 방에서만 목표에 도달한다** | `BotBrain.cs` |
| 게임 모드 | **하나다** — 비대칭 술래잡기(Seeker/Runner). 모드라는 축 자체가 코드에 없고, 규칙은 `Match` + `MatchConstants` 에 고정이다 | `Match.cs`, `MatchConstants.cs` |
| 맵 | `Game:MapDirectory` 스캔으로 자동 등록. 지금 3개 — `test-room`, `backrooms`, `backrooms-v2` | `ModuleRegistration.LoadMaps` |
| 방어선 | `Bots:Enabled` 는 개발 환경 밖에서 기동 거부. 봇은 정적 룸에서만 생긴다 | `GuardDevelopmentOnlyOptions`, `Room.JoinBot` |

정리하면 — **테스트 룸이라는 개념은 이미 있고 잘 만들어져 있는데, 인스턴스가 하나뿐이고
복제할 방법이 수동이다.** `test`(→ `test-room`) 하나가 전부이며, 그 룸의 봇 구성은 서버 전역
설정과 한 몸이다.

## 2. 무엇이 부족한가

| # | 구멍 | 증상 |

## 3. 설계

### 3.1 룸 정의를 문자열 한 쌍에서 프로필로 — `TestRoomProfile`

`StaticRooms`(룸 id → 맵 id)를 **룸 id → 프로필**로 넓힌다. 프로필은 맵과 그 룸 전용
봇 구성을 담는 불변 값이다.

```jsonc
"Game": {
  "TestRooms": {
    // 문자열이면 예전 그대로 맵 id 다 — 기존 설정 파일이 그대로 돈다.
    "test": "test-room",

    // 객체면 프로필이다. 생략한 봇 필드는 전역 `Realtime:Bots` 를 따른다.
    "test-br2": {
      "Map": "backrooms-v2",
      "Bots": { "Behavior": "Wander", "FillTo": 3 }
    }
  }
}
```

- **키 이름은 `Game:StaticRooms` 를 유지할지 `Game:TestRooms` 로 바꿀지 — 유지한다.**
  "정적"은 이 룸들의 수명 규칙(회수되지 않는다)을 말하는 이름이고 그 규칙은 그대로다.
  이름을 바꾸면 문서·설정·환경 변수 세 곳이 같이 움직여야 하는데 얻는 것이 없다.
- `StaticRooms` 클래스는 `IReadOnlyDictionary<string, TestRoomProfile>` 을 들게 된다.
  `TestRoomProfile` 은 `Contracts/` 의 새 타입 — `MapId` 와 `BotOptions?` 둘이다.
  구성 바인딩에서 문자열/객체 양쪽을 받는 것은 `LoadStaticRooms` 가 한다(`Game:Maps` 의
  경로/id 이중 해석과 같은 자리, 같은 방식).
- **`Room` 은 이미 `BotOptions` 를 생성자로 받는다.** `CreateStaticRooms` 가 전역 대신
  프로필의 것을 넘기는 것으로 룸 쪽 변경이 끝난다. 룸은 자기 설정이 어디서 왔는지
  모르는 채로 남는다.

**`Enabled` 는 프로필에 두지 않는다.** 봇 기능의 방어선은
`GuardDevelopmentOnlyOptions` 가 보는 전역 `Realtime:Bots:Enabled` 하나이고, 프로필마다
스위치를 두면 그 방어선이 흩어진다 — "전역은 꺼져 있는데 프로필이 켠다"가 표현 가능한
상태가 되면 안 된다. 전역이 마스터 스위치, 프로필은 채움 수·행동·역할·씨드의
**오버라이드**다.

### 3.2 맵마다 자동 테스트 룸 — 내보내면 열린다

`Game:TestRoomsPerMap`(bool, `Development` 기본 `true`)을 더한다. 켜져 있으면 등록된
모든 맵에 대해 `test-{맵 id}` 룸을 자동으로 연다. 명시 프로필이 이미 그 맵을 가리키면
건너뛴다 — `test` 가 `test-room` 을 가리키므로 `test-test-room` 은 생기지 않는다.

이것이 구멍 2를 닫는다. **맵 등록이 "파일을 쓰면 끝"이므로 테스트 룸도 그래야 한다** —
Unity 에서 Export Map Collision 을 실행하면 서버 재시작만으로 그 맵의 테스트 룸이 생기고,
로비 목록(`GET /rooms` — 정적 룸은 공개다)에 떠서 에디터 Play 로 바로 들어갈 수 있다.

- 자동 룸의 봇 구성은 전역 `Realtime:Bots` 를 그대로 쓰되, **`Behavior` 는 맵의 격자
  유무로 한 단계 자동 조정한다** — 격자가 없으면 `Wander`/`Objective` 를 `Idle` 로
  내린다. `BotBrain` 이 이미 격자 없는 맵에서 서 있도록 방어하고 있으므로 동작은 같고,
  조정은 기동 로그를 정직하게 만드는 것이 목적이다("Wander 로 열었는데 서 있다"를 없앤다).
  미로에서 `Objective` 를 `Wander` 로 내리는 자동 판단은 **하지 않는다** — "열린 방"을
  기계적으로 판정할 근거가 지금 맵 데이터에 없고, 헤매는 봇도 이동 검증으로는 유효하다.
- 룸 id `test-{맵 id}` 는 룸 id 형식(`a-z0-9-`, 최대 길이)과 맵 id 형식이 같으므로 항상
  유효하다. 접두사 `test-` 는 초대 코드 알파벳(`ilo01` 제외 31자)과 충돌할 수 있는 길이가
  아니다 — 자동 룸 id 는 항상 6자를 넘고, 넘더라도 코드는 대문자 없는 무작위라 실질
  충돌 확률은 코드 생성기의 `TryAdd` 가 흡수한다(기존 규칙 그대로).
- **정적 룸 수 = 맵 수**이므로 상한이 자연스럽다. `Sweep` 이 회수하지 않는 룸이 늘지만,
  참가자 없는 정적 룸의 틱 비용은 대기 갈래의 조기 반환뿐이다.

### 3.3 초기 상태 프리셋 — 검증 지름길

구멍 4다. 프로필에 매치 오버라이드 절을 둔다.

```jsonc
"test-door": {
  "Map": "test-room",
  "Bots": { "Behavior": "Idle" },
  "Match": { "Seconds": 60, "KeysRequired": 1 }
}
```

**전제가 하나 있고 그것이 이 절의 전부다 — 오버라이드할 수 있는 값은 클라이언트가
표시만 하고 계산하지 않는 값뿐이다.** `MatchConstants` 는 `Shared` 에 있고 클라이언트가
같은 상수를 컴파일한다. 시계는 2Hz `MatchState` 벌레틴이 진실이므로 매치 길이는 안전하고,
필요 열쇠 수도 벌레틴이 나른다. 반면 이동·판정 반경 같은 값은 클라이언트 예측이 같은
수로 계산하므로 **건드리면 보정 지터가 된다** — 오버라이드 가능 목록을 화이트리스트로
못박고, 목록에 없는 키는 기동 거부다(`CreateStaticRooms` 의 기존 규칙 — 조용히
건너뛰지 않는다).

이것은 **고정 파라미터를 바꾸는 일이라 구현 전에 확인이 필요하다**(§7). Phase 를 분리해
뒤에 둔 이유다. 화이트리스트 1차 후보: 매치 길이, 필요 열쇠 수, 리빌 시간. 셋 다
서버 판정 + 벌레틴 표시이고 클라이언트 계산이 없다.

### 3.4 게임 모드 축 — 자리만 확정하고 코드는 만들지 않는다

지금 모드는 하나다. `architecture.md` 는 구현이 하나인 추상화를 금지하므로 `IGameMode`
인터페이스도, 쓰이지 않는 `ModeId` 필드도 **지금은 만들지 않는다.** 이 계획이 하는 일은
두 번째 모드가 올 때 바뀌는 자리를 표로 확정해 두는 것이다 — 확장 비용을 지금 지불하는
것이 아니라, 확장 비용이 얼마인지를 지금 알아 두는 것이다.

두 번째 모드가 추가될 때 바뀌는 곳:

| 자리 | 지금 | 그때 |
|---|---|---|
| `TestRoomProfile` | `Map` + `Bots` (+`Match`) | `Mode` 필드 추가. 모르는 모드 id 는 기동 거부 |
| `POST /rooms` | 맵 id 만 받는다 | 모드 id 를 받고, `RoomSummary` 에 싣는다 |
| `Room` | `Match` 를 직접 만든다 | 모드가 매치 규칙 객체를 고르는 분기 — 이때 처음 구현이 둘이 되므로 이때 추상화한다 |
| `BotBrain.Objective` | Runner/Seeker 스위치 | 모드별 목표 수행 함수로 갈라진다. `BotBehavior` enum 은 그대로 — 모드가 행동의 의미를 정한다 |
| 자동 테스트 룸(§3.2) | 맵당 1개 | **맵 × 모드**로 늘린다 — `test-{맵}-{모드}`. §3.2 의 구조가 이 곱을 그대로 받는다 |

이 표가 프로필 구조(§3.1)를 정당화한다 — 룸 정의가 문자열 한 쌍인 동안에는 모드가
들어갈 자리가 없고, 프로필이면 필드 하나다. **§3.1 이 이 계획의 확장점이고, 모드는 그
확장점의 두 번째 손님이다**(첫 손님은 룸별 봇 구성).

### 3.5 봇 능력 갭 — 미로의 `Objective`

`backrooms`·`backrooms-v2` 테스트 룸에서 `Objective` 봇은 헤맨다. 경로 탐색(격자 A\*)은
`match-authority-plan.md` §6 의 체인 견인과 같은 자리를 공유하는 기존 결정이며 **이
계획의 범위가 아니다.** 이 계획이 하는 일은 그 갭을 룸 단위로 우회할 수 있게 하는 것 —
미로 룸의 프로필에 `Wander` 를 적으면 되고, 그것이 §3.1 이 필요한 세 번째 이유다.

## 4. 밟게 될 함정

| # | 함정 | 처리 |
|---|---|---|
| 1 | **로비 목록이 테스트 룸으로 덮인다.** 정적 룸은 공개이고 자동 생성으로 맵 수만큼 늘어난다 | 개발 환경 한정이므로 허용이 기본. 거슬리면 `RoomSummary` 에 `isStatic` 을 실어(HTTP JSON 필드 추가 — `botCount` 와 같은 하위 호환) 클라이언트가 접어 보이게 한다. 숨기지는 않는다 — 목록이 테스트 룸에 닿는 유일한 길이다 |
| 2 | **프로필 오타가 조용히 기본값이 된다.** 구성 바인딩은 모르는 키를 무시한다 | `LoadStaticRooms` 확장에서 자식 키를 화이트리스트로 검사하고 어긋나면 기동 거부. `CreateStaticRooms` 가 잘못된 맵 id 에 던지는 것과 같은 규칙이다 |
| 3 | **자동 룸과 명시 룸이 같은 id 로 충돌한다.** 사용자가 `test-backrooms` 를 손으로 적어 두면 | 명시 프로필이 이긴다. 자동 생성은 이미 있는 룸 id 를 건너뛰고 그 사실을 로그로 남긴다 |
| 4 | **룸별 씨드가 전역 씨드를 덮어 재현이 깨진다** | 프로필 `Seed` 생략 시 전역 값. 전역도 0이면 기동마다 무작위 — 기존 규칙 그대로. 룸이 다르면 `BotSeedFor` 의 파생이 이미 다르므로 추가 규칙이 필요 없다 |
| 5 | **`RoomState` 의 정적 룸 호스트 바이트 규칙**(수신자 자신의 id 를 싣는다)이 자동 룸에도 적용되어야 한다 | 자동 룸도 `isStatic: true` 로 만들 뿐이므로 자동으로 성립한다. 테스트로 고정한다 |
| 6 | **클라이언트에 씬이 없는 맵의 테스트 룸.** 서버는 맵 파일만으로 룸을 열지만 클라이언트는 그 맵의 씬이 있어야 들어간다 | 서버가 알 수 없고 알 필요도 없다 — 씬 없는 룸에 들어가면 `SessionSceneRouter` 쪽 실패이고, 그것은 로비로 방을 만들어도 똑같이 밟는 기존 문제다. 이 계획이 새로 만드는 실패가 아니다 |

## 5. 단계

### Phase 0 — 프로필 (구멍 1)

`TestRoomProfile` 타입, `StaticRooms` 를 프로필 사전으로, `LoadStaticRooms` 의
문자열/객체 이중 해석 + 키 화이트리스트(함정 2), `CreateStaticRooms` 가 프로필의
봇 구성을 룸에 넘긴다. 기존 설정 파일 무변경으로 통과(하위 호환).

검증 — 정적 룸 둘에 서로 다른 `Behavior` 를 적고 각 룸의 봇이 다르게 움직인다.
기존 `BotTests` 전부 통과(전역 설정만 쓰는 경로가 프로필 생략과 동치임의 증거).

### Phase 1 — 맵당 자동 룸 (구멍 2)

`TestRoomsPerMap`, `test-{맵 id}` 생성, 명시 프로필 우선(함정 3), 격자 없는 맵의
`Behavior` 강등, 기동 로그(맵·룸·봇 구성을 한 줄씩 — 기존 정적 룸 로그 형식 그대로).

검증 — 맵 3개 등록 상태에서 기동하면 테스트 룸 3개가 열리고 `GET /rooms` 에 뜬다.
`backrooms-v2` 를 에디터 Play 로 봇과 함께 확인할 수 있다 — 이 계획의 체감 성과다.

### Phase 2 — 목록 정리 (함정 1)

`RoomSummary`·`RoomInfoResponse` 에 `isStatic`. 클라이언트 로비가 테스트 룸을 구분해
그리는 것은 클라이언트 작업으로 남긴다(`botCount` 와 같은 처리).

### Phase 3 — 매치 오버라이드 (구멍 4, **구현 전 확인 필요**)

§3.3. 화이트리스트(매치 길이·필요 열쇠 수·리빌 시간), 정적 룸 한정, 기동 검증.

## 6. 테스트

1. 문자열 값 설정이 예전과 동일하게 동작한다 (하위 호환)
2. 프로필의 봇 필드가 룸에 적용되고, 생략 필드는 전역을 따른다
3. 모르는 프로필 키·모르는 맵 id·형식 어긋난 룸 id 는 기동 거부
4. `TestRoomsPerMap` 켜면 맵마다 룸이 생기고, 명시 프로필이 있는 맵은 건너뛴다
5. 격자 없는 맵의 자동 룸은 `Idle` 로 강등된다
6. 자동 룸도 정적 룸 규칙 전부를 따른다 — 회수 없음, 전원 시작 권한, 호스트 바이트(함정 5)
7. 프로필 `Seed` 가 룸별 궤적을 고정하고, 다른 룸의 궤적을 바꾸지 않는다
8. 초대 코드 룸은 이 계획의 어떤 경로로도 봇을 얻지 않는다 (기존 방어선의 회귀 테스트)
9. (Phase 3) 오버라이드가 벌레틴에 반영되고, 화이트리스트 밖 키는 기동 거부

`Architecture.Tests` 무변경 통과 — 새 프로젝트도 참조도 없고, 새 타입은 `Contracts/` 의
설정 값 객체 하나다.

## 7. 물어봐야 하는 것

1. **매치 파라미터 오버라이드(§3.3, Phase 3)** — `architecture.md` 는 고정 파라미터 변경
   전에 묻도록 정한다. 정적 룸 한정 + 화이트리스트라는 조건이면 허용되는가, 아니면
   테스트 룸에서도 파라미터는 불변이어야 하는가. 후자라면 Phase 3 은 버리고 나머지는
   그대로 성립한다.
2. **자동 룸의 기본 채움 수** — 전역 `FillTo`(지금 2)를 따르면 미로 맵도 봇 1이다.
   Runner 수가 밸런스 수라는 결정(정원 5)에 비추어, 미로 맵 기본을 3~4 로 올릴지는
   써 보고 정한다. 프로필로 룸마다 적을 수 있으므로 구조 결정은 아니다.
