# AI 활용 내역

이 프로젝트는 **Claude Code**(Anthropic 의 CLI 에이전트)를 주 작업 도구로 개발되었다.
이 문서는 그것이 실제로 어떻게 쓰였는지, 무엇을 사람이 했는지, 그리고 산출물이
어떤 게이트를 통과해야 했는지를 적는다.

> 이 문서의 수치는 저장소에서 실측한 것이다. 측정 방법을 함께 적어 두므로 언제든
> 다시 셀 수 있다.

## 1. 단순 코드 생성을 넘어선 부분

### Unity 에디터를 직접 조작한다

MCP 브리지(`mcp__unity-mcp__*`, Unity 공식 `com.unity.ai.assistant`)로 에이전트가
에디터를 직접 몬다 — 씬 구성, 컴포넌트 부착, 메뉴 실행, 플레이 모드 검증, 콘솔 진단.

실제로 이 세션에서 쓰인 예: 천장 뚫림을 고친 뒤 **맵 충돌을 다시 내보내는** 작업을
에이전트가 수행했다. 에디터가 열고 있던 씬을 확인하고(`MainLobby`, 변경 없음),
`SampleScene` 을 열고, `ComputeCollision()` 으로 박스 수가 736 → 740 으로 바뀐 것을
먼저 **측정**한 뒤, 익스포트 메뉴를 실행하고, 열려 있던 씬으로 되돌려 놓았다.
그리고 격자(`Standable` 583, `FreeFloor` 574)가 전후로 같은지 대조했다 — 그 값이
바뀌었다면 열쇠와 탈출 문이 지붕 위에 놓였을 것이기 때문이다.

**브리지는 코드 버그처럼 보이는 실패 방식을 여럿 갖고 있다.** 그 목록이
`NVproject/.claude/skills/unity-mcp-ops` 이며, 아래 "지식이 축적되는 구조" 의
대표 사례다.

### 지식이 축적되는 구조

에이전트는 매 세션 백지에서 시작한다. 그래서 이 저장소는 **다음 세션의 에이전트가
같은 실수를 반복하지 않도록** 지식을 파일로 남긴다.

| 무엇 | 어디 |
|---|---|
| 프로젝트 전반의 규칙과 함정 | `CLAUDE.md`, `NVproject/CLAUDE.md` |
| 밟은 함정의 증상 → 원인 → 수정 | `NVserver/docs/conventions.md` |
| 게임 규칙 (진실의 출처) | `NVproject/.claude/skills/game-rules/references/ruleset.md` |
| 설계 결정 기록 | `docs/adr/` |
| 스킬 11종 | `NVproject/.claude/skills/` |

스킬은 "무엇을 만드는가"(`fps-weapon-system`, `lobby-builder`, `game-rules` …)와
"어떻게 조작하는가"(`unity-mcp-ops`)로 나뉜다. 전자는 설계를, 후자는 도구의 실패
방식을 담는다.

**이 기록이 실제로 값을 한 사례** — 결과 화면이 뜨기 전에 씬이 전환되는 버그를
네 번 고쳤는데, 원인이 매번 달랐다(1.6초 지연 → 실행 순서 60 대 0 → 방 단계 의존
→ 비멱등 `Raise`). 세 번째까지의 원인이 `NVproject/CLAUDE.md` 에 남아 있었기에
네 번째에서 "HUD 안에서 옮기는 것으로는 절대 해결되지 않는다" 를 다시 발견할
필요가 없었다.

### 자율 반복 루프

인게임 규칙을 **클라이언트 판정에서 서버 판정으로 옮기는** 작업을 에이전트 자율
루프로 수행했다. 기록은 `docs/LOOP_PROGRESS.md`, 결과는 `docs/INGAME_GAP_MATRIX.md`.

- **40회 이터레이션**
- 서버 판정 완료 항목 **3 → 28**
- 각 항목이 자동 테스트로 고정됨
- 사람의 결정이 필요한 항목 **8개**(`OQ-1` ~ `OQ-8`)는 **임의로 판단하지 않고**
  선택지와 함께 남기고 종료

마지막 항목이 이 루프에서 가장 중요하다. 예를 들어 `OQ-8` 은 "같은 틱에 탈출
완료와 총알 도착이 겹치면 무엇이 이기는가" 이고, 지금 구현은 판정 순서 때문에
탈출이 이긴다 — 그런데 유지 시간의 문서화된 목적은 "술래가 끊을 수 있는 순간을
만드는 것" 이다. 창은 한 틱(33ms)이지만 결과는 이진이다. 이런 것은 밸런스 결정이지
구현 결정이 아니므로 에이전트가 정하지 않았다.

## 2. 검증 — AI 산출물이 통과해야 하는 것

**기계적 게이트는 예외가 없다.**

- 서버 빌드 **경고 0** (`TreatWarningsAsErrors`)
- 서버 테스트 **678개 전부 통과**
- **아키텍처 테스트** — 모듈 간 참조 금지와 `Contracts/` 밖 `internal` 규칙을
  `ProjectReference` 선언을 직접 읽어 검사한다(리플렉션은 과소 보고하므로 공허하게
  통과한다)
- 클라이언트 양쪽 어셈블리 타입 검사

**규칙을 고칠 때는 되돌려서 확인한다.** 수정을 넣고 테스트가 통과하는 것은 절반이고,
수정을 빼서 그 테스트가 **실패하는지**까지 봐야 그 테스트가 무언가를 지킨다는 것을
안다. 이 저장소에서 실제로 그렇게 확인한 것들: 한 클릭이 두 발이 되던 버그, 계단
경로, 시간 초과의 승패 판정, 준비 게이트, 결과 화면의 래치.

**작성과 리뷰를 분리했다.** 같은 맥락 안에서 자기 작업을 승인하지 않는다.

**사람이 해야 하는 것은 사람이 했다.**

- 애니메이션의 자연스러움 같은 시각 판단 — 에이전트는 수치로만 검증할 수 있다
  (발 미끄러짐 0.000000 m/s 는 계산이지 "자연스러움" 이 아니다)
- 실기기·2클라이언트 스모크 검증
- 밸런스 숫자의 최종 판단 (어둠의 정도, 술래의 달리기 4초가 붙기에 충분한가)

**문서와 코드가 어긋나면 코드가 옳다.** `INGAME_GAP_MATRIX.md` 는 스스로 이 원칙을
적어 두었고, 실제로 종료 정리에서 자기 문장 세 줄이 거짓이 된 것을 취소선으로
표시했다. 이 문서를 쓰면서도 같은 일이 있었다 — 초안의 "이터레이션 39"·"결정 대기
10개" 를 실측(40, 8)으로 고쳤다.

## 3. 이 방식이 남긴 흔적

코드베이스에서 AI 개발의 특징이 드러나는 곳:

**주석이 "무엇을" 이 아니라 "왜, 그리고 왜 다른 방법이 아닌가" 를 적는다.** 다음
세션의 에이전트가 같은 자리에서 같은 판단을 다시 하지 않도록. 예를 들어 파편
연출이 Rigidbody 를 쓰지 않는 이유는 "콜라이더가 로컬 `CharacterController` 를 밀어
서버가 아는 위치와 어긋나게 만들기 때문" 이라고 코드에 적혀 있다.

**함정이 발견된 자리에 테스트가 남는다.** `한_번의_클릭은_한_발이다`,
`쓰러진_몸은_입력을_받아도_움직이지_않는다`, `정적_룸도_준비를_요구한다` 처럼
테스트 이름이 곧 규칙 문장이다.

**규칙의 집이 하나로 고정되어 있다.** 클라이언트와 서버가 같은 계산을 해야 하면
`SimConstants`, 서버 혼자 정하면 모듈 상수. 값을 두 곳에 적으면 갈리고, 갈린
것은 조용히 갈린다 — 이 제약이 문서가 아니라 구조로 존재한다.

## 부록 — 프롬프트 사례

작업 지시는 대부분 한국어 한두 문장이었고, 에이전트가 조사 → 진단 → 수정 →
검증 → 문서화를 이어서 수행했다.

| 지시 | 에이전트가 한 일 |
|---|---|
| "지금 계단쪽을 스무스하게 올라가지 못하는 버그가있고 그거 때문에 제단에서 걸어갈 길이 없어서 체인을 못걸어" | 두 개의 별개 원인을 분리 — `MoveBox` 에 스텝업이 없던 것, 그리고 두 층이 격자에서 연결되지 않아 경로 탐색이 실패하던 것. 각각 수정하고 되돌려 실패를 확인 |
| "지금 인게임에 있는 요소 중에 멀티가 안되어 있는게 있는지 확인해봐" | 코드를 훑어 동기화 누락 항목을 심각도 순으로 보고. 사람이 고칠 범위를 고르면 그것만 수정 |
| "술래는 계속 못뛰고 게이지를 둬서… 풀 기준으로 4초 속도는 플레이어 뛰는거에 1.6배, 충전은 10초" | 규칙을 `ruleset.md` 에 먼저 적고, 속도·자격·게이지를 세 곳으로 분리해 구현, 와이어 한 바이트 증설과 프로토콜 버전 인상까지 판단해 보고 |
| "지금 모든 플레이어가 레디를 안해도 시작이 되는데 그거 고쳐" | 먼저 테스트 세 개를 써서 서버 게이트가 **정상임을 확인**한 뒤, 진짜 원인(공개된 정적 개발룸이 게이트를 통째로 건너뛰던 예외)을 찾아 서버와 클라이언트 양쪽에서 제거 |

마지막 사례가 이 프로젝트에서 AI 를 쓰는 방식을 가장 잘 보여준다 — **고치기 전에
재현부터 한다.** 증상만 보고 손대면 멀쩡한 코드를 고치게 된다.
