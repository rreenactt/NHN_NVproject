# 대기방의 서버 계약 (프로토콜 4)

이 문서는 **지금 동작하는 것**을 적는다. 왜 그렇게 정했는지는
`NVserver/docs/game-lobby-plan.md`, 밟은 함정은 `NVserver/docs/conventions.md` 에 있다.

이 파일은 `netcode-integration.md` 를 대체한다. 그 문서는 네트워킹이 **없다**는 전제로
쓰인 인계 문서였고, `LobbyManager`·`ILobbyTransport`·`OfflineLobbyTransport`·17개의
`// NETCODE:` 표식을 가리켰다. 그 넷은 아직 파일로 존재하지만 **오프라인 프로토타입 씬
(`Lobby.unity`) 안에서만** 살아 있다 — 서버 연동 대기방(`GameLobby.unity`)은 그중 아무것도
참조하지 않으며, 연동 확인이 끝나면 프로토타입과 함께 사라진다.

**화면 쪽 구조.** 대기방은 3D 씬이다. 명단은 두 곳에 동시에 그려진다 — 스탠드 줄의 마네킹과
HUD 의 목록 — 그리고 **둘 다 같은 전문에서 나온다.** 스탠드 번호는 `PlayerId` 이고 그것이
서버의 스폰 선택과 같은 값이다.

---

## 1. 무엇이 어디서 결정되는가

| 상태 | 소유 | 클라이언트가 하는 일 |
|---|---|---|
| 방 단계(`RoomPhase`) | 서버 | 받아서 화면을 고른다 |
| 방장 | 서버 | 자기 `PlayerId` 와 비교해 자기가 방장인지 안다 |
| 명단(누가 있는가) | 서버 | 그린다 |
| 준비 | 서버 | 요청하고, 결과를 명단에서 읽는다 |
| 캐릭터 | 서버 | 요청하고, 결과를 명단에서 읽는다 |
| 정원·최소 인원 | 서버 (`GET /rooms/{code}`) | 참가 전 조회로 받는다. **상수로 복제하지 않는다** |
| 캐릭터 개수 | `Shared` (`ProtocolInfo.LobbyCharacterCount`) | 표의 길이가 이 값과 같아야 한다 |
| 캐릭터의 이름·색·머리 장식 | **클라이언트** | 서버는 번호만 안다 |

**클라이언트가 결정하는 것은 표현뿐이다.** 규칙을 클라이언트가 하나라도 가지면 그것은
서버와 어긋날 수 있는 상태가 되고, 대기방에서 그 증상은 "어떤 사람 화면에서만 시작
버튼이 켜진다" 로 나타난다.

---

## 2. 클라이언트 → 서버 (`Control`, 0x02, 3B)

`opcode(1) + kind(1) + value(1)`. 전부 **요청**이며 서버가 틱 경계에서 다시 판정한다.

| kind | value | 서버가 다시 보는 것 |
|---|---|---|
| `StartMatch` (1) | 0 | 방장인가 · 대기 단계인가 · 최소 인원인가 · **요청자를 뺀 모든 사람이 준비했는가** |
| `EndMatch` (3) | 결과 코드 | 방장인가 · 진행 중인가 |
| `ReturnToLobby` (4) | 0 | 방장인가 · 대기 단계가 아닌가 |
| `SetReady` (5) | 0/1 | 참가자인가 · 대기 단계인가 |
| `SetCharacter` (6) | 캐릭터 번호 | 범위인가 · **방 안의 다른 사람이 입고 있지 않은가** · 대기 단계인가 |
| `KickPlayer` (7) | 대상 `PlayerId` | **방장 세션인가**(`IsAuthorized` 아님) · 대상이 있는가 · 자기가 아닌가 |
| `TransferHost` (8) | 대상 `PlayerId` | **방장 세션인가** · 대상이 사람인가 |

`2` 는 비어 있다. 자발적 퇴장을 두었다 뺐다 — WebSocket 정상 종료 프레임이 이미 그것을
말하고, 둘을 다 보내면 같은 소켓에 두 송신이 겹친다.

**거부를 알리지 않는다.** 다음 전문이 진실을 말하므로 클라이언트는 자기 요청이 반영되지
않은 것을 본다. 거부 알림은 놓칠 수 있는 한 번짜리 메시지가 된다(ADR 0003).

## 3. 서버 → 클라이언트 (`Event` 0x82, `EventKind.RoomState`, 2Hz)

고정부 11B: `phase · host · seeker · outcome · startTick(4) · playerCount`.
**배치 씨드는 없다** — 그것을 받은 Seeker 는 문의 좌표를 계산할 수 있었다.

명단 항목 4B + 이름:

| 필드 | 뜻 |
|---|---|
| `playerId` | 슬롯 번호. 룸 안에서 유일하며 스냅샷의 엔티티 id 와 같다 |
| `flags` bit0 `Ready` | 준비했는가. **방장은 누르지 않는다** |
| `flags` bit1 `Bot` | 서버가 채운 참가자인가 |
| `flags` bit2~7 | **비어 있다. 팀·관전자가 여기 들어간다** |
| `characterId` | 카탈로그 인덱스. `0xFF` 미배정 |
| `nameLength` + name | ASCII, 최대 `ProtocolInfo.MaxDisplayNameBytes`(12) |

전문이며 알림이 아니다. 매 2Hz 전체가 다시 오고 멱등하다.

### 항목에 필드를 더할 때

1. `RoomPlayerEntry` 의 `FixedWireSize` 를 올린다
2. `MessageCodec.WriteRoomState` / `ReadRoomState` 양쪽
3. `Room.BroadcastRoomState` 가 싣는다
4. **`NetworkClient.Differs` 에 비교를 더한다** — 이 비교가 화면 갱신 신호를 만드는
   유일한 지점이다. 빠뜨리면 서버는 보내는데 화면이 바뀌지 않는다
5. `ProtocolInfo.Version` 을 올린다. 구버전 클라이언트는 426 으로 전부 거부되고 WebGL
   빌드는 수 분이 걸리므로, **한 번의 인상 안에서 필요한 자리를 모두 잡는다**
6. `WireSizeTests` 의 상한 값을 고친다

## 4. 강제 퇴장의 닫힘 코드

**4003.** 서버의 `RealtimeConstants.Kick.CloseCode` 와 클라이언트의
`NetSession.KickedCloseCode` 가 같은 값이어야 한다. `Shared` 에 두지 않은 이유는 그것이
와이어 포맷이 아니라 전송 계층의 값이라는 것이다 — `Shared/Transport` 가 게임의 강제
퇴장을 알게 만들지 않는다.

이 코드가 없으면 클라이언트는 강제 퇴장을 회선 절단으로 읽고, 자동 재시도(0.5·1·2·4초)가
방금 내보내진 사람을 그 방에 다시 데려간다.

**계정이 없으므로 강제 퇴장은 소켓을 끊는 것까지다.** 초대 코드를 아는 사람은 다시
들어올 수 있다.

## 5. 지금 없는 것

| 없는 것 | 대신 |
|---|---|
| 카운트다운 | 준비가 조건이고 방장이 시작을 누른다. 넣을 때는 **시작 틱 + 길이**를 복제한다 — 프레임마다 float 을 보내면 흔들리고, 클라이언트가 자기 시계로 세면 사람마다 다른 시각에 매치가 시작된다 |
| 자리(슬롯) 이동·교환 | 스탠드 번호가 곧 `PlayerId` 이고 그것이 서버의 스폰을 고른다. 표시용 슬롯을 떼어내는 것이 선행 조건이다 |
| 팀·관전자 | `flags` 의 남은 비트. 관전자는 **참가자에 플래그가 붙은 것**이다 — 명단을 둘로 나누면 정원·승계·준비 판정이 전부 두 벌이 된다 |
| 대기방에서 맵 변경 | 맵은 방 생성 시 고정이고 맵 해시는 접속 시 검사된다. 싼 길은 방을 다시 만드는 것이다 |
