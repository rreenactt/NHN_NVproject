# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity **6000.3.20f1** (Unity 6.3), **URP 17.3**, **new Input System** (`activeInputHandler: 1` — legacy `Input.GetAxis`/`Input.GetKey` will throw).

The game is an **asymmetric hide-and-seek escape FPS in a two-floor Backrooms maze**: one armed Seeker hunts several unarmed Runners, who collect keys and insert them into a door only they can see. Two Runners out = Runner win; the clock running out = Seeker win. The authoritative ruleset is `.claude/skills/game-rules/references/ruleset.md` — **change it before changing any number in the code.**

Five scenes: `MainLobby.unity` is the product entry menu, `GameLobby.unity` is the waiting room you stand in, `SampleScene.unity` is the game (offline, everything built at runtime), `MapRuntime.unity` is the shared scene that hosts any baked map, and `MultiplayerTest.unity` is the networking harness. `Lobby.unity` is a sixth, kept only as the offline lobby prototype until the wired waiting room is confirmed.

The player is a **Minecraft-style figure built from white cubes in code, animated entirely procedurally**. There is no character model, no skinned mesh, no Animator, no AnimationClip and no blend tree anywhere in the project — all of that was removed. **The Seeker is the exception to the figure, not to the method**: at the role reveal the body is rebuilt as a hunched block monster from a `BodyPlan` (`SeekerModelCatalog`, one entry today), same joints, same procedural animator, different flesh — see "the Seeker is the monster" below. `Assets/Shady_3d` and `Assets/Animations` are leftover assets that nothing references; the humanoid scripts that drove them (`AimPitch`, `RootMotionRelay`, `ViewmodelRig`, `FirstPersonSetup`) are deleted. **Do not reintroduce Mecanim to solve an animation problem here** — pose the joints in code instead.

## Working in this project (no CLI build)

There is no build script. **There is now an EditMode test suite** — `Assets/Editor/Tests/` — and it needed no assembly definition: `Assembly-CSharp-Editor` already references `nunit.framework`, both TestRunner assemblies, and `Assembly-CSharp` itself, so a test dropped in that folder sees the client code. Compile-check it with `dotnet build Assembly-CSharp-Editor.csproj`; **running** it needs the Editor's Test Runner. The cost of that boundary is that a separate assembly cannot see `internal` members or `[SerializeField] private` fields, which is what currently limits how much of `MatchManager`'s apply path can be reached.

Everything else happens through the **Unity Editor via MCP** (`mcp__unity-mcp__*`, Unity's official `com.unity.ai.assistant` package).

- **Scripts can be compile-checked without the Editor**, which is worth doing before handing work over — a script error otherwise surfaces as an MCP call failing for no visible reason. Unity leaves `Assembly-CSharp.csproj` / `Assembly-CSharp-Editor.csproj` in the project root (gitignored, regenerated), and `dotnet build Assembly-CSharp.csproj` builds them against the real Unity DLLs. **A newly added `.cs` is not in that project's `Compile` list**, so it fails first with `CS0234` on its own namespace; add the `<Compile Include="…" />` line and rerun. This does not build a player and does not run anything — it only type-checks.
- **Read the `unity-mcp-ops` skill before any Unity MCP task** — the `fps-*` skills say what to build, `unity-mcp-ops` says how to drive the server.
- Keep `com.unity.ai.assistant` pinned at **2.6.0-pre.1**. 2.7.x requires a paid Unity AI seat and every MCP call fails with "Connection revoked" / "Capacity Limit". Enable via Project Settings ▸ AI ▸ Assistant MCP Extensions ▸ "Enable MCP Tools".
- Editing any `Assets/**/*.cs` triggers a domain reload that briefly drops the bridge ("Unity not detected") — retry the next call. **Always re-enter play mode after a script edit before trusting runtime reads**; a stale play session silently runs the old code. A domain reload does *not* reliably exit play mode, so guard any edit-mode-only command with `if (Application.isPlaying) return;` — writes made in play mode are silently discarded.
- **After editing a script from outside Unity, the *first* Play still runs the old assembly.** The editor only notices the file when it regains focus, so entering play mode is what kicks off the import; the recompile and domain reload then land *after* `Awake` has already run, and nothing re-runs it. A brand new component simply is not there, and a fixed one is still broken. Stop, Play again, and only then measure — this costs a cycle every single time and is the single most common way to "verify" a fix that never ran.
- **`Undo.AddComponent` / `Undo.RegisterCreatedObjectUndo` inside a command get rolled back if that command later errors**, even after an `ExecuteMenuItem` has already succeeded — you get a half-applied scene (objects deleted, components missing) with nothing in the console. Use plain `AddComponent` from commands and keep `Undo.*` for genuine editor menu items.
- Newly added components serialize the field defaults **as of that moment**. Changing a default in the `.cs` afterwards does not update the scene — set both, or the scene silently keeps the old value.
- **`Unity_RunCommand` reports `UNEXPECTED_ERROR` if the command logs a single warning**, even when it did exactly what you asked. A player build emits hundreds of shader warnings from the `com.unity.ai.inference` (Sentis) package, so **building through MCP always looks like it failed**. A deliberate `LogError` on a valid path (a build the tool means to refuse) reads the same way. Judge by the `[Log]` line at the very end of the response — print your conclusion once with `result.Log` and treat that as the only trustworthy signal, then confirm side effects from the filesystem.
- `result.Log` only substitutes `{0}`-style object references; format specifiers like `{0:F3}` are printed literally. Pre-format with `ToString("F3")` and concatenate.
- `Mesh` and `Image` collide with namespaces inside the generated command wrapper — write `UnityEngine.Mesh` / `UnityEngine.UI.Image`.
- **Never hold runtime-built references in a `Dictionary` on a MonoBehaviour.** A script edit triggers a domain reload that does not exit play mode; `UnityEngine.Object` fields survive it, a `Dictionary` does not. The half-restored component then throws every frame. Use plain fields, and guard `Update` with a rebuild when a built reference has gone null.
- **Never rewrite this file with PowerShell `Get-Content`/`Set-Content`** — the round trip mangles every em-dash and `▸` into `??`. Use the Edit/Write tools.
- In `Unity_RunCommand`: `AssetDatabase.DeleteAsset` fails ("User interactions are not supported for MCP tool calls") and can abort mid-command — delete the asset + its `.meta` from the filesystem, then `AssetDatabase.Refresh()`. Write to fresh asset paths rather than overwriting.
- **The command wrapper's assembly does not reference the `com.nv.shared` package**, so a command cannot name any `NV.Shared.*` type — not even through `var`, since the return type still has to be resolvable (`CS0012`). Go through an editor-side type that already wraps it: `MapExportPipeline.PlanFor(source)` returns `MapExportPlan`, whose `Describe()` and `Hash` answer most map questions without naming a Shared type.
- **A nested class inside `CommandScript` gets hoisted *and* duplicated by the wrapper**, which then fails with `CS1527` (private member in a namespace). Declare helper classes as separate top-level `internal class`es beside `CommandScript`.
- **EditMode tests cannot be run from a command.** `TestRunnerApi` needs its instance and callbacks to outlive the call, and the command's locals are collected as soon as it returns — the run silently never happens (no `[NVTEST]` lines in `Editor.log`). Compile-check with `dotnet build Assembly-CSharp-Editor.csproj` and ask for the Test Runner.
- `Unity_GetConsoleLogs` can hang indefinitely when the editor is busy. `%LOCALAPPDATA%\Unity\Editor\Editor.log` has the same content and reading it never blocks.
- **A newly written `.cs` has no `.meta` until the editor imports it**, and if the bridge is stuck you cannot force it. Writing the `.meta` by hand is safe — two lines, `fileFormatVersion: 2` and a fresh `guid` (`[guid]::NewGuid().ToString('N')`).
- **`EditorSceneManager.NewScene` unloads asset references loaded earlier in the same command** — they turn Unity-fake-null (`obj == null` true, managed object still alive with a working `GetType()`). A method receiving one then fails its `== null` guard while the error message prints the *correct type name*, which reads as an impossible cast failure. Open/create the scene **first**, then `AssetDatabase.LoadAssetAtPath`. For private serialized fields use `SerializedObject`, not reflection.
- **The first command after an `AssetDatabase.Refresh` that recompiled scripts can execute in the pre-reload domain** — sometimes several commands in a row. Symptom: an `as` cast between your own types fails though every diagnostic says they match. Verify with `typeof(X).Assembly.ManifestModule.ModuleVersionId` from the command before hunting deeper; when the MVIDs match and it still fails, suspect the fake-null trap above instead.
- `System.Reflection` inside `Unity_RunCommand` fails with a bare `UNEXPECTED_ERROR: Object reference not set…` (even just `GetField`). Add a public API to the script instead — `FirstPersonController.SetPitch` exists partly for this. Injected input (`InputSystem.QueueDeltaStateEvent`) also does not reach the player loop from a command, and `Time.deltaTime` does not advance within one command, so **per-frame motion cannot be stepped from a command at all**. Verify the *formula* against the live serialized parameters instead, then ask the user to play it.
- `Unity_Camera_Capture` with a specific camera fails under URP; only the no-arg scene-view capture works. **Animation smoothness cannot be self-verified visually** — verify numerically and ask the user for visual judgement. For "where is it on screen" questions, rasterize: project every triangle of the baked/mesh geometry to viewport space onto a coarse occupancy grid and print an ASCII map. Bounding boxes are useless here — geometry that straddles the near plane produces garbage extents, so skip triangles with any vertex at `z <= nearClipPlane`.
- Editor entry points, all under **Tools** (`Assets/Editor/`):
  - **Block Player ▸ Build Block Player** — strips whatever character is under `Player` and rewires the block player from scratch.
  - **Backrooms ▸ Set Up Match / Create Game Config Asset** — puts the `Match` object in the scene and creates `Assets/Settings/GameConfig.asset`.
  - **NV Network ▸ Setup Networking / Export Map Collision / Create Multiplayer Test Scene / Build and Launch 2 Clients**.

## Architecture

Runtime scripts live in `Assets/Scripts/`. The scene holds almost nothing — `BlockRig` builds every block in `Awake`, so the body exists only at runtime and there is no prefab to keep in sync:

```
Player          CharacterController + FirstPersonController + BlockRig
                + BlockCharacterAnimator + ProceduralReload + WeaponController + WeaponSwitcher
 └─ FP Camera   local (0, 1.62, 0); nearClip 0.02; cullingMask excludes PlayerBody
     └─ Viewmodel Arms   ← built at runtime, framing = BlockRig.viewmodelOffset
Backrooms       BackroomsMapGenerator — the whole two-floor level, built at runtime from a seed
Match           MatchBootstrap — the rules layer; builds everything below at runtime
 ├─ Match Manager / Device System / Match HUD
 ├─ __Objectives   Chain Altar, Escape Door, Key ×10, Device ×9
 └─ __PracticeRunners  wandering Runner dummies (only when practiceRunners > 0)
Mirror / Mirror Frame        repositioned into the spawn room by the generator
Global Volume, Directional Light (disabled)

added to Player at runtime by MatchBootstrap:
 PlayerAgent + PlayerInteractor + ChainDrag + PlayerRoleLoadout + FootstepAudio + WeaponAudio

built at runtime under Player:
 Hips ─ Torso ─┬─ Neck ─ Head        Arm R ─ Hand R ─ Pistol ─ Muzzle
               ├─ Arm R / Arm L      Leg R / Leg L (children of Hips)

built at runtime under Backrooms/__BackroomsMap:
 Carpet ×583, Ceiling Tile ×583 (one per standable cell) ─ Wall X|Z ×136 (merged runs)
 ─ Step ×16 (the stairwell flight) ─ light panels + point lights ─ Ceiling Lid ─ Ambient Hum
```

**Proportions are Minecraft's, on a 16-per-block pixel grid** (`head 8³`, `torso 8×12×4`, `limbs 4×12×4`; legs 12 + torso 12 + head 8 = 32 px). At `totalHeight` 1.8 m the eyes land at 1.62 m, which is where the camera already sat. Every limb's pivot is at its **joint**, with the cube offset half its length below it — get that wrong and limbs orbit their own centre, which is the usual reason a blocky walk looks broken.

**Movement is controller-driven again, and the animation follows it.** `FirstPersonController` moves the `CharacterController` directly and publishes `PlanarSpeed`, `MoveInput`, `VerticalVelocity`, `IsGrounded`. `PlanarSpeed` is **measured from actual displacement**, not from input, so walking into a wall stops the legs instead of leaving them running on the spot.

**The one load-bearing equation.** A rotating leg of length `L` swinging by `A` radians at rate `w` moves its foot through mid-stance at `L*A*w`. Setting that equal to real speed `v` gives

```
A = v / (L * w)
```

so the stride is *derived from measured speed* and the planted foot tracks the ground. Cadence is chosen first (a natural 0.95–1.55 strides/sec), the swing angle follows, and if that angle would exceed `maxLegSwing` (52°) the **cadence rises instead of the stride widening**. Verified: planted-foot speed matches body speed to 0.000000 m/s at 1–7 m/s. This is what replaced baked root motion — do not "fix" foot sliding by reintroducing clips.

**Everything else in `BlockCharacterAnimator` is the naturalness budget**, composed fresh into each joint's `localRotation` every `LateUpdate`:
- **Swing axis is derived from the move direction** (`Cross(up, localMoveDir)`), so strafing abducts the legs sideways and walking backwards reverses the cycle — no extra states, no separate clips.
- Arms counter-swing and **lag the legs** by `armPhaseLag` radians; zero lag reads as clockwork.
- Hips drop as the legs split. The true geometric drop is `L*(1-cos A)` ≈ 0.23 m, which pogo-sticks without knees — `bobAmount` applies a quarter of it. The camera takes `cameraBobRatio` of that plus a small lateral figure-of-eight.
- Torso leans into speed, banks into strafes; **the head counter-rotates `headStabilise` of the body's own pitch and roll** so the gaze stays level. Idle breathes, and only shows through when the body is still.
- Jump tucks the legs, falling spreads them, landing squashes with a `Sin(t*PI)` envelope scaled by impact speed.

**`ProceduralReload` no longer touches any transform** — it only produces a 0..1 `Weight`, and the animator blends the arms toward `loweredDirection` by that amount. One place composes the pose, so a reload cannot fight the walk cycle or the aim. It runs in `Update` (the animator is `[DefaultExecutionOrder(100)]`) so the weight is current when read.

**Arms-only first person, unchanged in principle.** Layers `FirstPersonArms` (8) and `PlayerBody` (9) split what you see from what everyone else sees: the FP camera's `cullingMask` excludes `PlayerBody`, so your own body — head included — is invisible to you but present for the mirror and for shadows. The camera sits *inside* the head block, which is fine precisely because of that mask. The viewmodel arms are a second pair of blocks parented to the camera with `shadowCastingMode = Off`.

**Viewmodel framing.** Anatomically the shoulders sit 0.27 m below and behind the lens, so a faithful copy hangs entirely out of frame; `BlockRig.viewmodelOffset` lifts the pair into shot. Currently **(−0.1692, −0.0028, 0.1027)** with `armedDirectionR` (−0.12, −0.155, 1.0) — arm 8.7° below level — putting the pistol at viewport ≈(0.55, 0.10) and the hand at (0.56, 0.075), covering ~12% of the screen. `armedDirectionL` must point **hard inward** (0.80, −0.170, 1.0): the left shoulder is a third of a metre off-centre, and anything gentler strands that arm against the left edge of the screen (it measured x=0.073 before that fix, 0.423 after).

**The two framing knobs are not independent.** `viewmodelOffset` slides the arms; `armedDirection*.y` changes their *angle*, and raising the angle also pushes the hand **further from the lens**, which shrinks the arms as well as lifting them. Going from 16.6° to 8.7° below level halved screen coverage (26% → 12%) on its own. Always re-measure with the rasteriser and re-solve the offset after touching the angle — a 0.045 m offset shift alone moves coverage by ~16 points.

**A held weapon must not inherit the arm's rotation.** Two traps here, both already paid for:
- `AimLimb` points a limb's local −Y along a direction with `FromToRotation`, which pins the length axis and leaves the **roll arbitrary**. That is fine for limbs — every block has a *square* cross-section, so rolling one is invisible — but the pistol is a child of the hand and inherited that arbitrary roll, which left its barrel 74° off, very nearly straight **up**, and every shot leaving the muzzle sideways.
- Pinning the roll with `LookRotation(forward, -direction)` is **worse**: `LookRotation` prioritises its forward argument and orthogonalises the up axis, so the length axis gets thrown away and the arm hangs straight down (the hand measured viewport y = −5.7).
- The fix is neither: `BlockCharacterAnimator.PointBarrelAt` sets the gun's **world** rotation directly with `LookRotation`, ignoring the arm. There is also a physical reason it can never inherit the hand — the barrel is perpendicular to a rigid arm block, so an arm reaching forward *forces* the barrel to point up or sideways.
- **That `LookRotation`'s up argument must be the camera's up, never `Vector3.up`.** Look far enough up and the barrel approaches world up itself; the two arguments become parallel, the roll is undefined, and the pistol visibly spins. Measured with world up: roll was −0.96° at 20° of pitch but **−131.7° at 82°**. With `cameraTransform.up` it is 0.000° across the entire ±85° range, because the barrel is clamped to within `barrelAlignClamp` of the look direction and so can never align with the camera's own up.

**The shot leaves the muzzle in a straight line.** `WeaponController.UpdateAim` publishes `AimPoint`/`AimDistance` from the crosshair every frame; the animator turns both pistols onto it (clamped to `barrelAlignClamp` 28° from the look direction, and the aim *distance* is what gets smoothed — glancing from a near wall to the sky moves the point 100 m but should only swing the gun a few degrees). The tracer is then drawn along `muzzle.forward`, so it is collinear with the barrel by construction. Measured: barrel off-axis from the shot line **0.9°**, tracer endpoint at viewport (0.496, 0.531) against a crosshair at (0.5, 0.5). Hit detection still comes off the screen centre, so what you hit matches the reticle rather than the barrel's offset — the ~6.5° the gun turns at 3.5 m is pure parallax and correct.

**Recoil** is a `SmoothStep` rise-then-settle envelope in the animator (`recoilRise` 0.035 s to a `recoilKick` of 3.2°, `recoilFall` 0.17 s back), driven by `WeaponController.Fire` calling `BlockCharacterAnimator.AddRecoil()`. It raises both arm pairs (body at `recoilBodyShare` 0.7), kicks the barrel up, and pushes `ViewRoot` back by `recoilPush` 14 mm. `AddRecoil` **restarts** the envelope rather than accumulating, so holding the trigger chatters evenly instead of the hands climbing away. The kick is applied in `LateUpdate`, i.e. *after* `Fire` has already traced the shot from the previous frame's muzzle orientation — so recoil can never pull a bullet off target. Traced live: 0 → 3.18° over 0.036 s, eased decay, hand viewport y 0.075 → 0.112 and back.

**The body arms move too**, since that is what the mirror and other players read. `armedBodySway` (0.55) keeps over half the walk's arm swing alive inside the held-weapon pose — welding the arms to the gun makes the body read as a mannequin being slid around. `armAimFollow` (0.5) adds a share of the look pitch on top of the torso's own, so an 80° look sweep swings the arms through 56° of elevation.

**Feet-on-floor shim.** A `CharacterController` rests its own `skinWidth` (0.08 by default) above the ground, so a body hung straight off the transform floats by exactly that much — plainly visible. `BlockRig.GroundOffset` reads `skinWidth` and the animator subtracts it from the hip height. Residual gap is 0.0067 m, which is just the `seam` shrink.

**The level is a two-floor Backrooms maze, generated in code.** `BackroomsMapGenerator` (on the `Backrooms` root) builds it in `Awake` from a seed: **35×35 cells at 3 m across two storeys** 3.2 m apart, so 105 m square with a 3 m ceiling. It replaced the single-floor `BackroomsMap`, which is still in the folder and referenced by nothing — do not follow it by mistake. The scene holds no level geometry; the `Directional Light` is **disabled, not deleted** (no sun indoors, but easy to put back), and `GameObject.Find` will not return it while it is inactive.

**Determinism is load-bearing, not tidiness.** The collision boxes are hashed and compared against the game server's copy of the map (`INetworkMapSource`), so one stray `UnityEngine.Random` would make client and server disagree about where the walls are. Every procedural choice draws from one seeded `System.Random`, `randomizeSeed` is **off** by default, and `ComputeCollision()` replays the draws in exactly the order `Generate()` does so the editor exporter gets the same level without building it.

Layout is solved entirely in memory before a single GameObject exists, in four passes:
- **Anchors first.** Spawn (ground floor), exit (top floor) and the stairwell are hand-authored `RectInt`s, stamped and marked protected so no procedural pass can eat them. The stairwell occupies the *same cells on both floors* — that is what makes the flights line up.
- **Rectangular rooms**, random per floor, rejected if they overlap another with a cell of padding.
- **Corridors** joining consecutive rooms, plus extra links at `loopChance`. A perfect maze has exactly one path between any two points, which reads as a puzzle rather than as being lost.
- **`EnforceConnectivity`** flood-fills and carves any stranded cell to the nearest reachable one on its own floor. The stairwell is the only vertical edge, so it is the only thing joining the storeys.

Current shape, measured: **583 standable cells of 2450 (24%)**, 136 wall pieces, 52 lights, 736 collision boxes, `MapName` `backrooms2f`.

**Cost control.** Each straight run of wall is merged into **one box with one collider** — 136 pieces instead of one per cell boundary. All walls share the built-in cube mesh and one instanced material. Floor and ceiling are one box per standable cell (583 each). Ceiling light panels are emissive boxes with **no collider** (they must not block shots); real point lights are sparser and have **shadows off** — flat diffuse light is what the reference looks like anyway. Levers if it runs badly: `lightSpacing`, then `gridSize`.

A NavMesh is baked over both floors and the stairs at the end of `Generate()` (`bakeNavMesh`), and the match layer leans on it — see the chain-drag. **Baked-prefab levels (`MapRuntime`) get theirs from `BakedMapSource.Start`** — the prefab carries no NavMesh, and without one `ChainDrag.BuildRoute` silently falls back to a straight seeker→altar chord that `NetworkBootstrap` then projects the server's drag onto, hauling the body through walls. `HasRoute` now refuses that fallback, and `WeaponController.AcceptAmmo` fires `onMagazineEmpty` on the 1+→0 falling edge because the server spends rounds on *held* fire while the local counter only spends on the click edge — without that the server chains a Seeker whose local `ChainDrag` never triggered, so no chain, no HELD banner.

**Ceiling tiles carry no collider — except on the top floor, which gets a `Ceiling Lid`.** Every other storey is sealed from below by the carpet slab of the storey above, which *is* solid. The top floor has nothing above it, so a player who climbed onto a 1 m device console and jumped 1.2 m put their eyes at 7.0 m against a 6.2 m ceiling and saw straight out of the level. One invisible 105×105 box at the ceiling plane fixes it for one collider instead of ~600 tile colliders; the highest reachable feet are now 4.40 m, eyes 6.02 m, under the ceiling by 0.18 m. It is in `CollisionBoxes`, so **the exported map hash changes and the server's copy needs re-exporting**. Unrelated but worth knowing: the navmesh has ~333 vertices at 6.30 on the *tops of the top-floor walls*, and has since long before the lid.

Atmosphere is set at runtime in `ApplyAtmosphere`: exponential-squared fog (density 0.028, sickly yellow), flat ambient, skybox nulled. The fog does most of the dread — not being able to see how far the room goes.

**Mirror:** `PlanarMirror` (on the `Mirror` quad, material `Assets/Shaders/MirrorSurface.mat`) reflects the viewer camera through the surface and renders into a RenderTexture that the `NV/Mirror Surface` shader samples **by screen position** — mesh UVs would not line up with the reflection camera's frustum. It moves a real camera rather than applying a mirror matrix, so face culling stays correct and URP renders it in the normal loop; URP does not support calling `camera.Render()` manually. Unity's Quad has normals along −Z, hence `flipNormal = true`. It **assigns** `reflectLayers` straight to the reflection camera's `cullingMask` (it does not AND with the viewer's), so `reflectLayers` must include `PlayerBody` and exclude `FirstPersonArms`.

**Crosshair:** `Crosshair` builds a `ScreenSpaceOverlay` Canvas of four bars plus a centre dot at Awake — no prefab, no sprite asset, no scene-authored UI. Each bar is drawn twice, a black rect 2 px proud behind a white one, because a plain white reticle vanishes against the Backrooms' pale yellow walls. A `CanvasScaler` against 1920×1080 keeps it the same apparent size at any resolution.

**Hit marker:** four diagonal ticks that flash and drift outward as they fade, raised by `Bullet`'s `onImpact` callback → `WeaponController.OnBulletImpact` → `Crosshair.ShowHitMarker`. It fires when the round *lands*, not when the trigger is pulled — with projectiles those are different moments, which is the whole reason it earns its place. Falloff is squared so it is sharp on impact rather than a slow smear. Offline it marks **any** impact, walls included. Networked it is not raised here at all: the local round is a prediction and remote bodies carry nothing to stop it — the `CharacterController` is disabled so it cannot shove the local player, and the blocks never had colliders — so a shot that hits somebody actually lands on the wall behind them and the marker fired either way. A marker that fires on every shot is not feedback. `MatchManager.AcceptCombatState` raises it instead, off the server's hit count, which costs the bulletin's half second and is worth it: with three rounds and a chain at the end of them, *whether* you hit matters more than knowing 300 ms sooner. It resolves itself once the server's own bullets are drawn.

The gap is **dynamic**: `restGap` + `moveSpread` × (speed / sprintSpeed) + `shotSpread` × `BlockCharacterAnimator.RecoilWeight`. With projectile rounds that take ~40 ms to land, a reticle that visibly kicks is the only immediate feedback a shot happened. **The open/close smoothing must be asymmetric** — a single 0.09 s SmoothDamp only reached ~50% of the intended spread before the 0.2 s recoil envelope had already decayed, so the kick never registered. `openSmoothing` 0.02 s against `closeSmoothing` 0.13 s reaches 96% and reads as a snap-and-settle.

**Weapon switching:** `WeaponSwitcher` (keys 1 = empty hands, 2 = pistol) reuses `ProceduralReload` as the swap animation and does the show/hide via its `onBottom` callback — at the bottom of the motion, where the hands are out of frame. Armed state drives three things together: both pistol copies' active state, `BlockCharacterAnimator.Armed` (the held-weapon arm pose), and `WeaponController.Armed`.

**Weapon:** the component defaults to an 8-round mag reloaded with R or an empty click, but **in a match the loadout resizes it to `GameConfig.seekerMagazine` (3) and hooks `onMagazineEmpty`, which disables both** — the chain owns the empty magazine. Damage goes out via `SendMessageUpwards("OnHit", damage)`. The pistol is built from blocks too. **No block on the character carries a collider** — the `CharacterController` handles collision, and `hitMask` also excludes layers 8/9, so a shot can never hit the shooter (verified). `muzzle` is re-pointed in `Start` to the **viewmodel** pistol's muzzle, so rounds leave the barrel the player can actually see — it must be `Start`, since the rig builds during `Awake`.

**Shots are real projectiles, not hitscan.** `WeaponController.Fire` launches a `Bullet` and resolves nothing itself; the round works out its own impact as it flies (120 m/s default, ~40 ms over 5 m). Trajectory is integrated by hand, not by a Rigidbody — the same rule this project applies to thrown objects.

- **The swept test is the whole thing.** Each step raycasts along the segment the bullet *travelled*, never testing just the new position. At 120 m/s a round covers ~0.7 m per frame against 0.25 m walls, so a position test would tunnel instantly. Verified by firing at **100,000 m/s** — 602 m in one step at a wall 20 m away — and it still stops at the wall.
- **Fire along `AimPoint - origin`, never along `muzzle.forward`.** The muzzle is a viewmodel bone: it bobs with the walk, sways, takes the recoil push, and is re-aimed in `LateUpdate` — so reading its rotation from `Fire` in `Update` uses *last frame's* orientation with the bob added on top. Rounds fired while moving or turning then left at visibly wrong angles (this is what read as bullets "curving"; the trajectory itself is straight to 0.00000 m of lateral drift, verified while shoving the player sideways mid-flight). `AimPoint` is refreshed at the top of the same `Update`, so it is both current and on the reticle: impacts now land at viewport (0.5000, 0.5000) exactly, against 1.31% of screen off with `muzzle.forward` even at rest.
- **Networked, the wire carries the shot, not the mouse button.** `WeaponController.Fire` raises `FirstPersonController.LatchFire()` and `NetworkBootstrap.Sample` consumes it — the same latch shape as the jump and the interact key. It used to send the raw held state, and the server read that out of the last input frame it had; that frame is repeated for up to three ticks when a new one does not arrive, so an ordinary 100 ms click (3 ticks) plus the repeat (3 ticks) outlasted the server's 5-tick fire interval and **one click became two rounds**. This client draws one bullet per click, so the tally that mattered — the three-round magazine — disagreed: two visible shots, chained on the third. The server still re-checks ammo, role and cadence (`Room.FireWeapons`); the bit is a request. `FireEventTests.한_번의_클릭은_한_발이다` holds the line server-side.
- The bullet has **no collider**; it only queries the world. Nothing can hit it and it cannot shove the shooter.
- `Fire` linecasts eye→muzzle and falls back to the eye position if blocked, or standing flush against a wall would let you shoot through it.
- **One raycast survives, in `UpdateAim`, and it is not hit detection** — it is what converges the barrel on the crosshair. Delete it and the gun fires parallel to the camera, so every close shot lands beside the reticle by the muzzle offset.
- `bulletGravity` defaults to **0** so the round stays on the crosshair at any range; turning it on makes the reticle lie at distance.
- Watch out when debugging: `RaycastHit.distance` here is only the portion of *one frame's step* before impact (0.0–0.7 m), not the flight distance. `Bullet` tracks `_travelled` for that reason.

**Footsteps are synthesised, and the falloff is the point.** `FootstepAudio` builds five step clips and a landing slap in code and plays them through one 3D `AudioSource`. They are **heavy leather-soled shoes**: a *click* (white noise differentiated — the cheapest high-pass there is), a *tock* from a damped sine at 560–750 Hz with an **inharmonic** partial at 1.63× so it knocks rather than rings a note, a 112–140 Hz sine under it for weight, and — the detail that sells it as a shoe — a softer **toe tap ~50 ms after the heel**, because a single transient reads as a stick hitting a box. The weight's decay is the heaviness knob: it has to still be sounding when the toe lands, or the step reads as a tap with a thud stapled to the front. Measured 343–568 zero-crossings/s at a high/low energy ratio of 0.15–0.18. That figure is the tone dial and it was found by overshooting in both directions: a light shoe measured 1036–1327 / 0.63–0.91 and read as tap-dancing, a heavy one measured 147–286 / 0.022–0.038 and read as a subwoofer thud with no shoe in it. **The tock carries the sound** — it has to stay in the range a laptop speaker can reproduce, since the weight below it is felt more than heard. The clips are **normalised to 0.92**; the click, tock and weight all peak within a millisecond of each other and summed to 1.24 before that, which `SetData` clips into distortion, and the overshoot differed per variant so the walk sounded uneven. In a hide-and-seek game a footstep is the Seeker's main sensor and the Runner's main leak, so the rolloff is a **custom curve, not Unity's logarithmic default**: the default never reaches zero, and a Runner who is faintly audible from anywhere carries no information. Measured: 100% inside 1.6 m, 78% at 3 m, 42% at 5 m, 18% at 8 m, 6% at 11 m, **0% at 18 m**. `hearingRange` is the balance knob.

- Steps fire on the **animator's stride phase** (`Sin(StridePhase)` changes sign exactly at each footfall, twice per cycle) so the sound lands on the frame the foot does. Anything without an animator — a practice Runner on a NavMeshAgent — falls back to one step per `strideLength` metres; verified at 2.97 steps/s for a 3.2 m/s bot, i.e. 1.08 m per step.
- **Ctrl sneaks**: `FirstPersonController.sneakSpeed` 1.1 m/s against a walk of 2.5, and `FootstepAudio` multiplies the step by `sneakLoudness` (0 — genuinely silent, no voice allocated). Sneak beats sprint when both are held, because you cannot run quietly. Note the scene's walk speed is **2.5, not the 4 this file defaults to**; a new field also bakes its default into the scene the moment it serialises, so `sneakSpeed` had to be set in both places.
- **Your own steps are 2D and quiet** (`isLocalListener` → `spatialBlend` 0, `selfVolume` 0.3). Positioning a source the listener is standing inside is meaningless, and at full volume it drowns out the thing you are listening for.
- `AddComponent` runs `Awake` immediately, so a spawner that sets `isLocalListener` afterwards gets a source already configured for the wrong side. Settings are therefore applied in `Start` and re-checked with one float compare per step.
- Remote networked players will need this component too — nothing adds it to `RemotePlayerPuppet` yet.

**The gunshot is heard three times as far as a footstep, and that is the design.** `WeaponAudio` synthesises the bang the same way — a *crack* (differentiated noise, gone in 3 ms), a *blast* (broadband, ~40 ms), a low *body*, and a heavily low-passed *tail* over half a second, because without the room answering back a shot indoors sounds like it was fired in a field. Three clips, normalised to 0.95. `WeaponController.Fire` plays it **before** resolving the round: the bang is the event, not feedback about a hit. Falloff is deliberately shallower than the footsteps' — still 36% at 20 m and 20% at 30 m, zero at 60 — so a shot tells every Runner in the building roughly where the Seeker is and that they have one round fewer. Firing already costs the chain; this is what it costs in *information*. `WeaponController` adds the component itself if it is missing, so any scene with a weapon makes a noise.

## The lobby (`Assets/Scripts/Lobby/`) — two screens, three scenes

**The main lobby is a menu; the game lobby is a room you stand in.** That is why they are separate scenes rather than two pages of one UI tree.

| Scene | What it is |
|---|---|
| `MainLobby.unity` | The menu — profile, connection state, room list (`GET /rooms`), create room, join by code, quick join, quit. Pure UI Toolkit; nothing 3D. `MainLobbyController` + `LobbyController` + `LobbyUIController` |
| `GameLobby.unity` | The waiting room — the 3D staging space, a row of stands with a figure on each, and the HUD over it. Server-driven. `GameLobbyBootstrap` + `GameLobbyHud` + `GameLobbyPicker` |
| `Lobby.unity` | **The offline prototype, still here on purpose.** `LobbyManager` + `OfflineLobbyTransport` with fake players, a countdown and slot swapping. It is the reference the server-driven room was built from and gets deleted once the wired version is confirmed end to end. Menu: **Tools ▸ Backrooms ▸ Create Lobby Scene** |

Both product scenes are **generated, not authored** — **Tools ▸ NV ▸ Scene ▸ Create Main Lobby Scene** and **Create Game Lobby Scene**. Each puts itself into Build Settings, because `SessionSceneRouter` finds scenes by *name* and an unregistered scene fails to load with no log line at all.

`SessionSceneRouter` (on the session object, so it outlives every scene) owns every transition: `InLobby`/`Ended` → `GameLobby`, `Playing` → the scene matching the room's map, `Idle`/`Failed` → `MainLobby`. **No button loads a scene.** There are four ways into a room — create, code, list, quick join — and a transition each of them has to remember is one that one of them forgets.

**Every lobby-flow scene must attach the router itself** — `SessionSceneRouter.EnsureOn(session)`, called from `MainLobbyController.OnEnable` *and* `GameLobbyBootstrap.Awake`. It is deliberately absent from the dev scenes (`MultiplayerTest`, `SampleScene`), which have no lobby to return to and would bounce to one the moment they saw a waiting state. While only the main lobby attached it, pressing **Play on `GameLobby.unity` directly** — the obvious thing to do while working on the room — gave a waiting room with no session: `NetSession.Current` makes a fresh `Idle` session rather than returning null, so the row fell back to empty stands and **LEAVE only set an already-`Idle` session to `Idle` again**. A room with nobody in it and no way out, with nothing in the console. Since the fix that same Play lands in `MainLobby`, because `Idle` now has a router to act on it.

**`GameLobbyBootstrap` must not re-fetch the session in `Update`.** It did, as a null guard, and that branch would have filled the field *after* `OnEnable` had already run — so `StateChanged` never gets subscribed and the row stays empty however many roster bulletins arrive. `NetSession.Current` never returns null, so the guard only ever cost the subscription.

### The 3D room is the prototype's, unchanged

`LobbyRoom`, `LobbySlot` and `LobbyMannequin` build the space, the stands and the figures exactly as they did offline: mono-yellow walls from the level's palette, half the fluorescents failing, a camera square-on to the row so every figure is the same size, a floor plate per stand whose colour *is* the readout (empty / taken / ready), and a pulsing bar marking which one is you. **Those three are presentation, so a server changed nothing about them** — what changed is who decides who stands where, and that is now the server.

`GameLobbyBootstrap` builds the row from the server's **capacity**, not from a config field. The prototype used `LobbyConfig.maxPlayers` (6), which was a stale copy of the server's 8.

**The stand number is the `PlayerId`.** The server reserves slots by that number and picks the spawn from it, so the figure you see in the row and the body in the match carry the same id — which is what lets you match a roster line to a person on sight. It is also why **slot swapping is gone**: moving a figure would mean moving a spawn.

### The HUD

`GameLobbyHUD.uxml` sits on `game-hud.uss` + `lobby.uss` (the prototype's own sheets, untouched) plus `game-lobby.uss` for what is new. Same room, same interface — the player never leaves the building. Three differences from the prototype's HUD: no countdown, no swap prompt, and an invite-code panel plus host controls.

- **Requests out, bulletins in.** `NetSession.SetReady` / `SetCharacter` / `KickPlayer` / `TransferHost` / `RequestStart` send `Control` (0x02); everything comes back in the `RoomState` bulletin (0x82) at 2Hz, in full, forever. Nothing here is a one-shot message — the session channel is `Bounded(32, DropOldest)`, so a one-shot rejection is a frame that can vanish.
- **There is no client-side authority.** `GameLobbyHud` holds no state; it reads `NetSession`/`NetworkClient` at draw time and exposes `Action`s the bootstrap fills. `RoomMember` is the projection of one roster line (entry + host byte + own id) and is built fresh every refresh — a stored copy is a second roster that can disagree invisibly.
- **The start rule.** Ready is the condition; the host presses start. The host does not ready — pressing start *is* their ready. Bots are not counted (nothing for them to press) and the static dev room skips the condition, the same boundary `IsAuthorized` already uses.
- **Characters are unique per room and the server enforces it.** `LobbyCharacterCatalog` owns names, colours, headgear and idle style; the server knows only the count (`ProtocolInfo.LobbyCharacterCount`) and the index. **The list order is the wire value** — reordering it desyncs anyone already connected. Taken entries are dimmed, not hidden: hiding them makes the catalog look shorter than it is.
- **The preview is the figure on your own stand.** There is no render-texture portrait — you are standing in the row, so picking a character dresses the mannequin everyone else is looking at.
- **Clicking the room is a host gesture.** Offline a click meant "move here" or "trade with me"; now it means "this person", and it raises the kick confirmation. Non-hosts get no reaction at all, which beats sending a request the server will refuse.
- **Kick closes the socket with code 4003**, and that code is the only signal separating it from a dropped connection. Without it the auto-retry (0.5·1·2·4 s) brings the ejected player straight back. There are no accounts, so kicking ends a socket and nothing more — the invite code is the real gate.
- The palette is the level's and the stylesheet is `main-lobby.uss` (which follows `game-hud.uss`), because the lobby is a room in the same building, not a menu.
- The room hands off at `RoomPhase.Playing`: `SessionSceneRouter` opens the scene matching the room's map. Role assignment and every other rule belong to `MatchManager`.

The living wire contract is `.claude/skills/lobby-builder/references/server-contract.md`; the design record is `NVserver/docs/game-lobby-plan.md`.

**The character you pick in the lobby is the body you play — unless you are the Seeker, whose body is the monster for the duration.** `CharacterAppearance` paints a `BlockRig` from the same `LobbyCharacterCatalog` the waiting room uses — torso and arms take the overalls, legs the trim, head the skin, and the head gear (cap / hard hat / band / hood / visor) is rebuilt from blocks sized off `BlockRig.HeadSize`. Your own viewmodel sleeves are painted too, so first person matches what everyone else sees. `AppearanceSync` (created by `NetworkBootstrap`, so it exists in every networked scene including ones with no match layer) polls the roster and applies it — **polls rather than listens, because a remote body only exists once its first snapshot arrives**, and a change-event fired before that would leave that player white for the rest of the match. Materials are cached one per colour per character, and head gear carries no collider for the same reason the body blocks do not.

## The network layer (`Assets/Scripts/Net/`) — present, and deliberately optional

There is a real authoritative server in the sibling repo (`../NVserver`, .NET), and its `Shared` project is wired in as the local package `com.nv.shared`. Only **movement** is server-authoritative so far; the match rules are not on it at all.

- **`NetworkBootstrap` is the single seam, and every scene a room can open must have one.** It is inert without a session (`Bind` checks `NetSession.Exists`, `Update` returns early with no client), so adding it costs a scene nothing — an offline Play behaves exactly as before. `SampleScene` went without one for a while *and that broke multiplayer outright*: `MapSceneTable` pairs the `backrooms` map to `SampleScene`, so every room on the game's main map opened a scene with no puppets, no server-authoritative movement and no `AppearanceSync` — each player alone in their own copy of the maze. The symptom is "players can't see each other" with a clean console. `MultiplayerTest` and `MapRuntime` always had one. **Adding a map/scene pair to `MapSceneTable` means checking the scene has a `Network` object.**

- **A scene loaded *by* a state change has already missed that change's event.** Both `MatchSync` and `NetworkBootstrap` are created in the game scene, and the game scene is loaded *because* the room went to `Playing` — so anything they subscribe to has already fired. This cost the whole networked match twice over:
  - `MatchSync` set `_pendingStart` only from `NetworkClient.RoomStateChanged`. That event fires only when the bulletin's **contents change**, and the phase does not change again after the scene loads, so `TryBeginMatch` never ran: server in `Playing`, client stuck in `MatchPhase.Lobby`, roles `Unassigned`, all three server-authority flags off, no objectives. It now reads `_client.RoomState` every frame — `RoomState` is a **bulletin** (ADR 0003), idempotent and always current, and `_startedTick` already prevents restarting the same match.
  - `NetworkBootstrap` checked the map hash only from `WelcomeReceived`. Welcome arrives in the *lobby*, so the check was skipped for the entire match and `MapHashStatus` sat at `미확인` — silently disabling the only guard on the client/server terrain coupling. `Bind` now calls `OnWelcome()` directly when `HasWelcome` is already true (it is idempotent via `_mapHashChecked`).

  The rule: **in the game scene, read the bulletin; do not wait to be told it changed.**
- `FirstPersonController.ControlMode` decides who owns a body: `Local` (offline, this script moves it), `NetworkAuthority` (own character on a server — input is sampled and sent, position comes back), `Remote` (everything off the wire, and `MeasureSpeed` recovers the move direction from displacement so the animator still works without putting it on the wire).
- Remote players interpolate on a 100 ms buffer; the local player only smooths briefly toward the server position, because adding an interpolation delay to your own character stacks 100 ms on top of the round trip.
- **`MapExport` is why the map generator is deterministic.** The editor exports the collision boxes to JSON for the server, and the runtime hashes the same boxes through the same function to compare against what the server loaded. Both paths must go through one function or the check verifies nothing. **Changing the level's collision — the ceiling lid did — changes the hash and requires re-exporting.**
- **A remote player's shot is heard, not just seen.** `RemotePlayerPuppet` carries `FootstepAudio` and `WeaponAudio`, and `NetworkBootstrap.OnFireObserved` plays the bang and kicks that body's arms off the `FireEvent` — for a while it drew only the tracer, and a tracer needs you to already be looking. The gunshot is the one channel that reaches the far side of the building (60 m against the footsteps' 20), so a silent one deletes what firing costs the Seeker in information. It plays *on the body*, not at the event's coordinates: remote bodies are drawn 100 ms in the past, and a sound pulled to the present separates from the muzzle it came out of.

## The match layer (`Assets/Scripts/Game/`)

The game itself — one Seeker against Runners who insert keys into a hidden door and escape. The ruleset is `.claude/skills/game-rules/references/ruleset.md` and it is **the source of truth**: change it first, then `GameConfig`, then the systems. Tunables live in `Assets/Settings/GameConfig.asset` (menu **Tools ▸ Backrooms ▸ Create Game Config Asset**); the scene object comes from **Tools ▸ Backrooms ▸ Set Up Match**.

**Every rule is decided in `MatchManager` and nowhere else.** Keys, door, devices and agents hold state and raise intentions; the manager resolves them. That is not tidiness — the game is asymmetric, so every rule is also an *information* rule, and a client that decides its own hits decides it was never hit. The event list on it (`PhaseChanged`, `KeysChanged`, `EscapesChanged`, `AgentHit`, `MatchEnded`, `RolesAssigned`, `Notified`) is exactly what a replication layer has to carry. Nothing in it assumes the single local player it currently has.

**Networked, the server owns the rules.** That was not true when this file was first written and the change is the point: `MatchSync` (in `Scripts/Net/Session/`) no longer hands down a seed and a start tick for this client to run a match with — it applies what the server decided. `MatchBootstrap.autoStart` and `debugKeys` still switch themselves off when a session exists, because a local start would run a second match alongside the real one.

Two flags gate it, and they are separate on purpose:

- **`ServerOwnsObjectives`** — placement, key pickup, key insertion, the door opening, escapes. With it on, `KeyPickup` stops polling and `MatchManager.TryPickUpKey`/`TryInsertKey`/`TickEscapes` refuse.
- **`ServerOwnsCombat`** — where a round goes, who it hits, and what that costs. With it on, `MatchManager.ReportHit` refuses.

They are always set together today, but they crossed over in different tasks and for several iterations the server judged one and not the other. One flag covering both would have had to lie during that gap.

**`Bullet` was not deleted, it was disarmed.** It still flies on the shooter's machine and still calls `SendMessageUpwards("OnHit")`; `ReportHit` throws that away under server authority. The offline path runs the identical code and judges normally. The one visible seam left: the hit marker fires off the *local* round's impact, so a shooter can see a marker for a shot the server scored as a miss — presentation, not a rule.

What arrives from the server, and by which route:

| What | Route | Applied by |
|---|---|---|
| Match phase, clock | `MatchState` bulletin, 2 Hz | `AcceptMatchState` |
| Keys inserted, door open | `MatchState` + `ObjectiveState` | `AcceptObjectiveProgress` |
| Carried keys (per player) | `MatchState` participants | `AcceptCarriedKeys` |
| Escape count | `MatchState` | `AcceptEscapes` |
| Hits (per player) | `MatchState` participants | `AcceptCombatState` |
| Bleeding, downed, escaped **on a body** | `EntityFlags` in every snapshot | `AcceptCombatState` / `AcceptEscaped` |
| Held by the chain **on a body** | `EntityFlags.Frozen` in every snapshot | `AcceptChained` |
| Objective positions | `ObjectiveState`, role-filtered | `AcceptObjectiveState` |
| Escape hold progress **on a body** | the snapshot's per-entity byte | `AcceptEscapeProgress` |
| Device spent / cooldown / freeze running | `ObjectiveState` device bytes | `DeviceSystem.AcceptServerStates` |

**Counts come from the bulletin, per-body state from the snapshot.** The bulletin says *how many* escaped; only the flags say *who*, and a body has to disappear the frame it happens rather than up to half a second later. Anything applied by polling must also be idempotent — `SetBleeding` starts a `BloodTrail`, so calling it every frame restarts the trail every frame and the wounded Runner leaves no trail at all.

- **`ServerPlacesAgents`** suppresses `PlaceAgentsAtStart`: movement is server-authoritative, so a teleport here is undone by the next snapshot and the local player visibly snaps twice on the way.
- **`ResolvesOutcome`** is true only on the room's host, and escapes and wipes are still resolved there — reported through `Control(EndMatch)` and taken by everyone else via `AcceptOutcome`. **The clock is no longer among them**: `Room.EndMatchByServer` judges its own timeout, because the host's report could never arrive for that ending (`Room.EndMatch` gates on `Playing`, and the phase had already moved). The questions that blocked the rest have answers — a wipe is a Seeker win, and the escape target is `MatchConstants.EscapesToWinWith` — so what remains is the move, not the decision.
- **`PlacementSeedOverride` no longer comes from the server** — the seed was removed from the wire so that a Seeker holding the placement function has no input to compute the door with. **Nothing writes it now**; it survives as a manual hook for reproducing a layout while testing (set the property rather than the config asset — mutating a ScriptableObject at runtime persists it in the editor and the next session silently reuses the seed). Offline seeding falls to `GameConfig.placementSeed`, and 0 there means this machine's clock. All three are resolved in one place, `ResolvePlacementSeed`, and **called once per match** — the clock fallback returns a different number on every call, so two calls in one `BeginMatch` used to seed the objective layout and the local Random from different numbers.

**The Seeker is the monster, and the monster is the silhouette.** A role on a body used to mean only the pistol; now `PlayerRoleLoadout.ApplyRole(body, role)` is the one shared answer — it rebuilds the rig (`BlockRig.Rebuild`) as the `SeekerModelCatalog` plan for a Seeker and back to the humanoid for anyone else, then shows or hides the weapon (`ShowWeapon` survives as its tail). `PlayerRoleLoadout` itself is still the local player's — camera mask, switcher, chain — so only `ApplyRole` is static and shared, and `RemotePlayerPuppet` calls it when its agent's role changes. It polls rather than listening: a puppet only exists once its first snapshot arrives, so a body born after `RolesAssigned` would miss the one event forever. The check needs a separate "applied" flag because `Role.Unassigned` is both the initial value and a legitimate answer — comparing values alone skips the first application, which is exactly what left every remote body on the rig's armed default with Runners walking around holding pistols.

Three things a rebuild costs, all paid inside `ApplyRole` and only when `Rebuild` reports a real swap:
- **`WeaponController.RebindMuzzle`** — the muzzle cached in `Start` died with the old body. A destroyed transform fails `!= null` *silently*, so every round would leave from the eye instead of the barrel with nothing in the console. The bone barrel keeps the pistol's whole contract (root rotated by `PointBarrelAt`, +Z barrel, direct child named `Muzzle`).
- **`CharacterAppearance.OnRigRebuilt`** — forgets the applied character id, so the roster poll re-dresses the humanoid on the way back (F1 swap, rematch). While the body is a monster, `Apply` returns immediately: the plan owns its colours, and `AppearanceSync` would otherwise repaint the monster in overalls every frame.
- **Hitbox honesty** — the server still judges every shot and move against its fixed 1.8 m × 0.8 m box (`SimConstants`); nothing about the swap is on the wire and the server does not know monsters exist. The plan's rule is to keep the visible mass inside that box, or shots start reading as wrong.

The animator retunes itself from the plan the same polled way (`ApplyPlanProfile` — cadence, hanging arms, unstabilised head, the limp, the stop-and-snap idle twitch), captures the scene's serialized values once and restores *those* on the way back, not the `.cs` defaults. The gait maths is untouched — the no-slide relation solves the swing from measured speed at whatever cadence the plan sets, so monster feet plant like human ones (the limp's short leg skates on purpose; a dragged foot is exactly a foot that does not keep up with the ground). `FootstepAudio.monsterSteps` swaps the step *timbre* only — the rolloff curve and every range are balance values and identical for both bodies.

Remote players get a `PlayerAgent`, `FootstepAudio` and `WeaponAudio` from `RemotePlayerPuppet.Create` — but only when a `MatchManager` exists in the scene, since `MultiplayerTest` wants bodies without rules. `PlayerAgent` registers itself in `OnEnable`, which is the `SetActive(true)` at the end of that builder, so its name and role have to be set before then. The match waits until every roster member has a body before starting; bodies only appear on the first snapshot, and roles are assigned to whoever is present at `BeginMatch`.

**Ctrl is sneak, not crouch, and the wire says nothing about it on purpose.** The server's `ButtonFlags.Crouch` slows a player *and* shortens their box (1.8 → 1.2), so sending it would change the hitbox height — and this game's Ctrl is walking slowly and quietly with the stance unchanged. The cost of that decision is real and unpaid: the server moves at full speed without the bit, so in a networked match sneaking is silent but not slow, and "silence has to cost enough" is free online. Closing it needs a signal meaning *slow* without also meaning *shorter*; `PlayerCrouchHeight` and `ResolveCrouch` stay on the server, correct and unreachable, until there is one. **The escape hold, by contrast, is public to everyone, Seeker included — the door's *position* stays hidden, but a hold nobody can see is a delay rather than a rule, and the ruleset says so. It rides the snapshot's per-entity byte (the old `Health`, which this game never spent) because 0.8 s cannot be drawn from a 2 Hz bulletin.

**Asymmetric visibility is two culling layers, not two copies of the world.** `RunnerVision` (10) carries the door, `SeekerVision` (11) carries the blood trail, and `MatchLayers.ApplyRoleVisibility` points each camera at the half its owner may see. Toggling renderers per role leaks the moment a new object forgets the rule; a culling mask cannot leak because the camera never renders the layer. The Seeker's HUD is also told nothing about key progress — only the escape count.

**One of those layers is chosen per client, and that is what makes "your own blood" work.** A trail is laid on every machine that can see the body, so `MatchLayers.BloodLayer` puts *your* marks on the Default layer on *your* machine and everybody else's on `SeekerVision` — the Seeker sees all of it, a Runner sees only their own, and no second layer was needed. It was `SeekerVision` for every mark once, which hid a Runner's blood from the Runner bleeding it: the pool that grows while you stand still is the whole cost of standing still, and the person paying it could not see it. The ruleset carries this now (`game-rules/references/ruleset.md`, Combat table) — it is a rule, not a rendering detail.

- **The Seeker runs on a gauge**: 4 seconds at full, 1.6× a player's run speed, 10 seconds to refill, usable at any charge above zero. Three pieces had to stay apart. The **speed** is in `SimConstants.SeekerSprintMultiplier`, written as `SprintMultiplier * 1.6` so changing how fast people run moves both. **Whether you may run** is a judgement and lives in `Room.TickSprintCharge`, which clears the `Sprint` bit before movement sees it — putting the gauge inside `PlayerMovement` would make it an input to the deterministic surface for no gain. The **gauge itself** counts in integers (600 units, 5 per sprinting tick, 2 per recovering tick) because a per-second float accumulates differently on two machines and this number is drawn on screen. `RealtimeConstants.Validation.MaxHorizontalSpeed` follows the Seeker's multiplier — that check does not know roles, so it has to admit the fastest one or a legitimately sprinting Seeker gets clamped every tick.
- **This is the first wire growth in a while: `MatchParticipant` went 5 → 6 bytes and the protocol 4 → 5.** The project's habit is to reuse a dead byte instead (`Ammo` took `Flags`' place), but all five were carrying values. A gauge the Seeker cannot see is not a gauge. It is blanked in Runner copies by the same filter as ammo — "can that thing sprint right now" is read from sound and distance, not from a number.
- **The door needs fewer keys in a smaller match** — 3 / 5 / 8 / 10 for 2 / 3 / 4 / 5 players, from `MatchConstants.KeysRequiredWith`. It is a **table, not a formula**: the per-head share is not constant (1.5 / 1.67 / 2 / 2), because more players can cover each other, and a formula would erase that intent. The count comes from the roster **at match start** and is frozen for the match — recompute it from the living and the door gets easier as the team falls apart. The client latches its own copy once from `MatchStateHeader.ParticipantCount` for the HUD's denominator; a disagreement there is cosmetic, because whether the door opens is the server's answer and arrives in `ObjectiveState`. The **scattered** count stays at 10 — a smaller match should not also be a barer map.

**The door has no collider**, and neither do the keys. A door the Seeker cannot see but *can* walk into would be found by bumping into thin air.

**Combat counts hits, not health.** `Bullet` still calls `SendMessageUpwards("OnHit", damage)`; `PlayerAgent.OnHit` throws the number away. First hit → bleeding + teleport to a random standable cell; second → death, dropping carried keys where they fell. `hitImmunity` (0.75 s) exists because three rounds can be in the air at once — without it one burst kills through the teleport by hitting the place the victim just left.

Networked, all of that happens on the server instead (`Room.ApplyHit`) and this client is told. The rules are the same by construction — the numbers live in `MatchConstants`, which both sides read — but the server counts the immunity window in **ticks** (23, not 22.5: rounding it down would reopen the burst-through-teleport case the window exists to close). A value that has to survive being converted to ticks is a value worth writing as ticks in one place, not dividing at each use.

**Bleeding is enforced by the trail, not by a timer.** Running lays a thin dotted line; standing still past `bleedStillGrace` pools blood on the spot, bigger and lasting `bleedPoolLifetimeScale`× longer. Hiding while wounded paints a sign over the hiding place, which is what "must keep moving" means here.

**The chain-drag is the Seeker's whole cost, and it is anchored to one place.** Emptying the 3-round magazine hands the empty to `ChainDrag` via `WeaponController.onMagazineEmpty`, which *replaces* the reload: a chain comes out of the ring on the `ChainAltar` in the middle of the ground floor, hauls the Seeker back to it along the shortest walkable route, holds them `chainWait` 3 s, and only then reloads. Anchoring to a fixed altar rather than the nearest wall is what gives the penalty teeth: it costs three seconds *and everything you walked to reach*, and the Seeker always knows where the third shot sends them. `MovementLocked` blocks movement while leaving the look free — `InputEnabled` would release the cursor, which mid-match reads as the game losing focus.

- **Networked, the empty magazine does not raise the chain — `EntityFlags.Frozen` does.** `onMagazineEmpty` fires from the local `Fire` seeing `_ammo` hit 0, and under server authority `AcceptAmmo` overwrites that count from the 2 Hz bulletin *every frame* (`MatchSync.ApplyParticipants` polls). Three rounds leave in 0.3 s, well inside one bulletin period, so the local count never reached 0 and `ChainDrag.Trigger` was simply never called: the server hauled the Seeker to the altar with no chain drawn anywhere, and the console said nothing. The server has always carried the fact in the snapshot's `Frozen` bit (it folds the chain and the match-wide movement lock into one — a body not moving under its own will), and `MatchSync.ApplyBody` now hands it to `MatchManager.AcceptChained` → `ChainDrag.SetServerChained`. Because it rides the snapshot rather than a local magazine, **remote bodies get the chain too** (`RemotePlayerPuppet` carries a `ChainDrag`), which is how you watch someone else be dragged off. Two things that look optional and are not: the applier gates on `MatchPhase.Playing` (the same bit means "role reveal" and "match over", when *everyone* is frozen) and on the agent being the Seeker; and `SetServerChained` acts on the *change*, since a poll acting on the level restarts the whole chain every frame once its safety deadline expires.
- **The chain takes the shortest walkable route, not a straight line.** `NavMesh.CalculatePath` gives the corners; the chain is drawn as one stretched link per remaining segment and loses a bend each time the Seeker is pulled round one, and the haul is paced by *route* length (`chainDragSpeed` 45 m/s, `chainDragMaxTime` 3.5 s). Measured from the far corner upstairs: 31 corners, 399 m of route against 55 m of straight line, down the stairwell, and mid-haul the chain was 305 m of snaking metal against a 33 m straight line. Unity's path solve *is* A\* over the navmesh polygons, and it already knows the floors are joined by a staircase and not by a hole in the ceiling — a hand-rolled grid A\* would have to be taught that.
- **Sample the navmesh at 1.5 m, never 4.** The bake leaves a walkable strip along the tops of the top-floor walls, 3.1 m above the upper floor; a 4 m sample radius snapped a Seeker standing upstairs onto that roof and every route came back `PathPartial` and wandered around up there.
- The altar is placed **before** the door, keys and devices, because it is the only fixed thing in the objective set and everything random has to work around it.
- **`FirstPersonController.Phasing` holds collision off for the whole haul.** Calling `Teleport` per frame re-enables the CharacterController inside walls dozens of times on the way, and Unity depenetrates the capsule wherever it likes — measured landing 3.8 m off target and half a metre up. The loop also always stops a fraction short, so the drag ends with an explicit snap onto the spot. `HandleMove` returns early while the controller is disabled, or `Move()` logs an error every frame.
- **The landing spot is verified with a capsule, not with the grid.** The stairwell's cells are walkable *in the grid* while being full of staircase, so the first version dropped the Seeker onto a step every single time. `MatchManager.IsFreeFloor` does `Physics.CheckCapsule` at player size.
- `ClearObjectives` **deactivates** the old objective root before destroying it. `Destroy` is deferred to the end of the frame, so the previous altar was still solid to that capsule test and the altar walked to a new cell on every restart.

**Agents are never deactivated when they die or escape** — `SetPresent(false)` hides them instead. `SetActive(false)` fires `OnDisable`, which unregisters the agent in the middle of the manager's own loop over the roster, and the win conditions still need to count them.

**Two Unity traps this layer paid for, both the domain-reload family** (a script edit during play wipes managed state without re-running `Awake`):
- `MatchManager.Instance` / `DeviceSystem.Instance` re-find themselves lazily, and every `System.Random` is behind a lazy `Rng` property. Each of these was a live NullReference every frame first.
- **`BackroomsMapGenerator.EnsureGrid()` is called by every public level query**, not just at match start. It re-solves the wiped grid from the same seed without rebuilding geometry. Leaving it to callers failed quietly rather than loudly — a compass with no storey arrow, a blank map overlay — because the queries return "there is no level" rather than throwing.
- **A `bool` survives a domain reload; a `VisualElement` does not.** `GameHudController` therefore asks `TreeIsLive` (are the elements there and still attached to a panel?) instead of keeping a "built" flag. The flag came back `true` describing elements that were all null, so the HUD never rebuilt and threw once a frame at an empty screen for the rest of the session.
- **Win conditions are evaluated in `Update`, never on unregister.** Leaving play mode disables agents one at a time, which read as the Seeker having wiped them out and wrote a fictional result into the log on every exit.

**Networked, the devices are the server's too, and the split is by whether the effect shows on anyone else's screen.** `Room.TryUseDevice` judges: teleport moves the body, stop-bleeding clears `BleedingCleared`, add-time extends the clock, and the freeze locks everyone — those four all mutate state the server owns, so the old client-side versions were overwritten by the next snapshot or bulletin ("the portal bounces me back", "I stopped the bleeding and it came straight back"). Spent and cooldown ride the device's state byte in `ObjectiveState`, which is what stops a one-shot device being spent once *per player*. The two that only ever draw on the user's own screen — full-map and seeker-cam — stay local and are predicted on the press, because a round trip would only add latency to something no one else can see. The E press itself needs no new message: it is the same `Interact` bit the door already uses, and a press the door refuses now falls through to a device.

**Destroying a device is server-side too, and the console's dimensions are now a shared constant.** `Room.TryFindDeviceHit` tests the same swept segment that already looks for walls and bodies — people win ties, because a Runner in front of a console must be what a shot at them hits. Four hits (`MatchConstants.DeviceDestroyHits`) and it is `Destroyed`, which is a different wire bit from `Spent` because the two look and read differently. The hit count rides the **top four bits of the same state byte** so the Seeker's "2/4" prompt is the server's number and the wire did not have to grow. `MapDevice.OnHit` refuses to count under `ServerOwnsCombat`, for the same reason `ReportHit` does: the local `Bullet` only flies on the shooter's machine, so a device it destroyed would be wreckage only that player could see. The box comes from `MatchConstants.Device{Width,Height,Depth}` on both sides — the server judges the shot with it and `MapDevice.Build` draws it, and two copies of that number is a device you can see but not hit. It is judged **square in plan** (the wider dimension both ways) so a rotated console cannot be hittable from one side and not the other.

**The freeze device is why `EntityFlags.Frozen` is no longer enough on its own.** That bit already meant both "the match is locked" and "this body is on the chain"; the freeze makes it mean a third thing, and since the flags are full, `MatchSync` disambiguates with `MatchDeviceState.Active` off the objective bulletin — without it a frozen Seeker gets a chain drawn to the altar.

**A runtime `new Material(...)` is destroyed by whoever made it — `Destroy(gameObject)` does not do it.** A Material is a native asset, so the GC never reclaims it either, and the symptom is a session that degrades the longer it runs with nothing in the console. `BloodTrail` paid for this: one material per blood mark, ~3.6 minted a second per bleeding Runner, none ever destroyed. The marks are particles now — one ParticleSystem per trail, one shared material, per-mark lifetime on `EmitParams` and the fade on the Color over Lifetime curve — which also collapsed ~90 GameObjects and draw calls per Runner into one. Its shader (`NV/Blood Mark`) lives under `Assets/Resources/` **on purpose**: particle tint arrives as vertex colour, which `URP/Unlit` ignores, and the URP particle shaders are referenced by no material here so a build strips them — `Shader.Find` then returns null only in players, never in the editor. Shaders under `Resources/` are always included; keep it there.

`MapDevice` registers *itself* in `OnEnable` and `DeviceSystem.Start` sweeps once for stragglers: the first match is started from `MatchBootstrap.Start`, too early to assume the system it wants is awake — measured as nine devices in the level and none of them registered.

**The HUD is UI Toolkit** (`Assets/Resources/UI/GameHUD.uxml` + `game-hud.uss` + `GameHudPanelSettings`, driven by `GameHudController`), and it is the one part of this project that is *not* built in code — a stylesheet is the only sane way to get flickering signage. It lives under `Resources/` so the controller can load it without anything wired in the scene. The **crosshair stays uGUI**: its canvas sits at `sortingOrder` 100 and the panel at 0, so the reticle draws over the HUD.

- **Role gating is structural, not cosmetic.** On `RolesAssigned` the tree is rebuilt from the UXML and the other side's panel is `RemoveFromHierarchy()`'d. A Runner's HUD contains no ammo counter; a Seeker's contains no key slots, no carried count and no door marker — verified by querying the live tree, not by reading the code. Hiding them instead would be one `display: flex` away from handing the Seeker the objective.
- Everything role-exclusive must therefore live *inside* `#runner-panel` or `#seeker-panel`. An element parked outside them is an element both sides get.
- The **door compass** is drawn on a ring around screen centre from the yaw between the camera and the door (verified to 0.09° against the true bearing, with a ↑/↓ when the door is on another storey). It makes a hidden door easy to find — `GameConfig.showDoorCompass` turns it off if locating the door should be most of the job.
- **A body that stops being a body comes apart.** `PlayerAgent.Kill` calls `BlockGibs.Burst` *before* `SetPresent(false)` — the pose the body is standing in is the burst's starting pose, and after the hide there is nothing left to copy. The pieces are **clones**, not the rig: detaching the real blocks would fight the animator (which poses those joints every LateUpdate), the cached renderer array `SetPresent` hides the body through, and the next match, which needs the body back. They are integrated by hand for the same reason `Bullet` is — a Rigidbody brings colliders, and colliders here would shove the local `CharacterController` and put it somewhere the server disagrees with. Two details that are not optional: the gibs go on layer 0 rather than inheriting the body's, because a local player's body is on `PlayerBody` which **their own camera culls** — inherit it and the one person who cannot see their own death is the person who died; and the tumble is seeded from the body's name, so two people watching the same death watch the same pieces land in the same places.
- **Dying drains the colour out of the screen** — a neutral grey `dead-wash` over the world, ~42% of the chroma gone, faded in over 0.8 s. It is *not* post-processing: the camera has `m_RenderPostProcessing` off, and switching it on would bring the scene volume's Bloom, Vignette and Tonemapping with it and change the whole game's look for one death effect. A flat grey does the job here precisely because the room has one colour in it — take the yellow out and there is nothing left to be colourful. It sits below the role panels in the tree so the HUD stays crisp on top of it, and it runs in the shared update rather than the Runner's, which is removed from the tree for a Seeker. Escaping is not death and does not trigger it: winning and losing must not look the same. In practice only Runners ever see it — the Seeker cannot be shot.
- **The result card is a bulletin, not a notification.** It is drawn from `MatchManager.Phase`/`Outcome` every frame rather than only from the `MatchEnded` event, because a client whose HUD tree was not live on that one frame would never draw it — and "no card" is indistinguishable from "straight to the lobby without a result". `_resultClosed` keeps a card the player already dismissed from coming back, and is cleared when the room leaves `Ended`. The body-burst stays on the event, because it is a one-shot effect and repeating it every frame would re-explode the same corpse.
- **Anything that hands input back to the player has to ask whether a result screen is up first.** The escape menu re-enables `InputEnabled` unconditionally when it closes, which over a result screen re-locks the cursor: the 나가기 button is on screen, the mouse is driving the aim, and there is no way to press it. Opening ESC as you die is enough to get there. Both directions are now guarded by the same pair — the menu checks `MatchResultGate.Standing` before giving control back, and the HUD checks `EscapeMenuController.AnyOpen` before doing the same at the next match. A result screen is UI; it just happens to be the second layer of it.
- **The result screen hands input to the UI the way the escape menu does, and freeing the cursor by hand does not work.** `FirstPersonController.HandleCursor` runs every frame while input is enabled and **re-locks the cursor on any left click made while it is free** — that is how you get back to playing after ESC. So a result screen that only sets `Cursor.lockState` puts a button on screen whose every click is eaten by that re-lock before it reaches the button. Setting `InputEnabled = false` is what actually works: it stops the controller's cursor, look and move handling together, and the weapon reads the same flag so the click that presses a button cannot also fire a round. Input is **not** handed back when the player leaves — the waiting room is made of buttons — but at the next match's phase change, and never underneath an open escape menu (`EscapeMenuController.AnyOpen`), which would re-lock the cursor behind a menu nobody can then click.
- The crosshair canvas is `ScreenSpaceOverlay` at sorting 100 and the HUD panel is 0, so **uGUI draws over UI Toolkit here**: it is hidden while the match is `Ended` or the winner reads their result through a set of crosshairs. Picking is a separate question and is fine — that canvas has no `GraphicRaycaster` and its images are not raycast targets, which is why a button in the HUD panel can be clicked at all.
- **Whoever holds a scene transition has to run before the router does, and the HUD does not.** `SessionSceneRouter` is execution order 0; `GameHudController` is 60. On the frame the room reports `Ended`, the router cuts to the waiting room *before the HUD's Update runs at all* — so anything the HUD arms is armed after the scene it lives in is already going. **Two fixes failed on this**, both of which looked right in isolation: first arming the hold when the card appeared (1.6 s too late), then arming it at the top of the HUD's `Update` (still 60 vs 0). Moving the call earlier inside the HUD can never work.

  The router asks for itself instead. `ResultStillOnScreen()` reads `MatchManager.Phase`, which `MatchSync` (-75) has already written this frame, and `MatchResultGate.Dismissed`, a latch that is **only ever cleared, never set** — its default is hold, so there is no arming step to lose a race. `SceneTransitionHold` could not be reused: it is a deadline by design, and a result screen waits for a person. The latch is rearmed in the router's `InGame` branch rather than only in `ResultStillOnScreen`, because that method never runs while a match is playing — put it only there and the *second* match of a session loses its result screen while the first works.

  The gate is genuinely indefinite: a client whose HUD never draws a card will sit in the finished match until someone presses ESC ▸ LEAVE. That is the requested behaviour, and ESC is the way out.
- **The scene is held from the moment the match ends, not from the moment the card appears.** Those are 1.6 seconds apart (`EndCardDelaySeconds`, a beat so the last thing that happened stays visible) and the router cuts on the very frame the room reports `Ended` — so a hold armed by the card is a hold armed after the scene is already gone. The first attempt at this made exactly that mistake and fixed nothing; the symptom that exposed it was a Seeker winning by wiping the Runners and getting no result at all. `HoldWhileResultStands` now runs at the top of `Update`, **before** the live-tree guard, and reads only `MatchManager.Phase` — so it holds whether or not this client has a HUD tree yet, and whether or not the card has been drawn.
- **The result screen holds the scene until someone closes it.** The end card existed all along, but `SessionSceneRouter` loaded the waiting room on the frame the room reached `Ended` — the card's own scene was unloaded under it, so a side that lost on the clock never saw that it had lost. The card now carries a 나가기 button, and while it is up `GameHudController` re-arms `SceneTransitionHold` **every frame**. That reuses the departure-animation mechanism deliberately, keeping its one safety property: a hold is a deadline, so a HUD that dies mid-result costs half a second instead of stranding everyone in a room the match has left. The card is re-asserted on the same frame as the hold, or a tree rebuild would leave the client waiting on a card nobody can see; and the hold is dropped if the room leaves `Ended`, because the room moving on outranks one person still reading. The cursor is freed to make the button clickable and re-locked when the next match's phase arrives — without that second half, one result screen leaves every later match running with a loose cursor.
- **Losing at the whistle bursts the bodies that were still standing** — `PlayerAgent.Shatter`, which is `Kill` minus everything that means something. `Kill` drops `Alive`, which the wipe check and the spectator both read, and rewriting the roster *after* the result was computed from it is how a decided match gets re-decided. A timeout ends with nobody down, so without this the screen shows a number reaching zero and nothing else happening.
- **`NetworkClient` outlives the match scene, so anything the scene hands it has to be taken back.** `NetworkBootstrap` installs `client.InputSource = new LocalInputSource(localPlayer)` and used to unsubscribe its three events on destroy but leave that. The session object is `DontDestroyOnLoad`; the player is not — so from the frame the match scene unloads, `SendInput` sampled a destroyed `FirstPersonController` every frame and the player log filled with `NullReferenceException` at `LocalInputSource.Sample → FirstPersonController.Yaw → transform`. It only became routine once returning to the lobby and playing again worked. `OnDestroy` now clears it, but **only if it is still the one this scene installed** — `OnDestroy` can run after the next scene's `Awake`, and clearing then would blank a source someone else just set. `Sample` also returns a neutral frame on a null controller, as a second line so a forgotten hand-back is silent rather than a flood.
- **After a match the room stays `Ended`, and the waiting room is inert in that state** — `GameLobbyHud` derives `waiting` from `SessionState.InLobby`, so START, READY, character select and the host actions are all *removed* while a finished room sits there, and the server refuses `SetReady` outside `Waiting` anyway. The only control that reset the room lived in the **match scene's** escape menu, which is gone by then. `GameLobbyBootstrap.ReopenFinishedRoom` closes it: the host, on arriving in the waiting room, quietly asks the room back to `Waiting` — once, latched, because the request takes a few frames to come back and the state reads `Ended` throughout. What the players see is the same staging room as before the match, which is what "play again" should look like.
- **A dead Runner watches a living one.** `MatchSpectator` parks a second camera at a teammate's eyes; left-click steps to the next, right-click to the previous. It is a **second camera on purpose** — the local one hangs off the rig's head and `FirstPersonController` rewrites its local rotation every LateUpdate, so anything parked on top of it fights a script whose execution order is not ours to fix. It follows in `LateUpdate` because remote bodies are placed in `Update`; follow in `Update` and the view jitters against its own subject. The eye comes from `HeadPosition` and the aim from body yaw + `controller.Pitch`, because **a remote puppet's `head` is null** (the rig's joints are built in an `Awake` that has not run when the component is attached) — reading `head.rotation` like `SeekerFeed` does would put the camera on the floor. The **AudioListener moves with it**, and the local one is switched off first: two live ears is a Unity warning and an undefined answer to which one you hear. Targets are **living Runners only, never the Seeker** — seeing the Seeker's view is what the security-camera device costs a walk across the level to buy, and giving it to every corpse for free empties that device. They are sorted by name because registration order is arrival order, which differs per client, and a "next player" that shuffles cannot be learned.
- **The server stops an out-of-play body, and that is a separate rule from hiding it.** `Room.IsOutOfPlay` neutralizes movement input for anyone `Downed` or `Escaped`. The client already refuses to walk (`PlayerAgent.ApplyLock` reads `!InPlay`) but that is a request, not a rule: the body is never deleted (the wipe check counts it) and its position keeps going out, so an edited client could scout the level invisibly — and once spectating exists, do it while watching through someone else's eyes. It deliberately does **not** raise `EntityFlags.Frozen`: the client draws the chain from that one bit, and every corpse would grow a chain to the altar.
- **There is no sky indoors, and deleting the skybox was not enough to stop one appearing.** Both maps set `RenderSettings.skybox = null`, but the camera's clear flags still said *Skybox*, and with no skybox material that falls through to the camera's **background colour** — which was Unity's factory blue-grey. Every gap in a dark level opened onto daylight. The camera now clears to a solid colour, and `RoleVision` paints it with the **fog's** colour rather than black, so distance dissolves into the background instead of ending at a visible edge — exponential fog blends towards `fogColor`, so any other background draws a line exactly where sight should just run out. It is painted after the role's fog is chosen, never before. `BlockPlayerSetup` sets a dark solid colour too, for the frames before a role exists.
- **How dark the level is, is answered per role — `RoleVision`.** It is `MatchLayers`' idea with the lever moved from *what is rendered* to *how much of it you can make out*: a Runner is a person in a dead building with a torch, the Seeker is the thing that lives there and carries none. **The map's own numbers are the Runner's**, and the Seeker's are multipliers on them (ambient ×4, fog density ×0.78, tinted cold so the advantage reads as not-human eyes rather than a brightened monitor) — multipliers rather than a second palette, so `backrooms`' ochre and `backrooms-v2`' grey-green each stay themselves. **The base is captured once and the capture is dropped by whoever writes the atmosphere** (`ApplyAtmosphere`, `BackroomsV2Ambience`): roles are re-announced every match start and the debug side-swap can fire mid-match, so multiplying an already-multiplied value would put a twice-swapped Seeker in daylight, and carrying one map's base into another lights the Seeker's screen in the wrong map's colour. Unlike the escape door, this is **not a secret** — the door was closed by removing the input a client would need to compute it, and brightness cannot be closed that way because the client has to draw the room. It buys the feel of the two sides, not a guarantee about them.
- **A fifth of the ceiling panels are dead and a fifth flicker, and both come out of one random draw.** Rolling twice would let a panel be dead *and* flickering, which is neither, and would shrink both shares below the fifth they were asked for. A dead panel loses its emissive material as well as its light — leave the glow on and it reads as a rendering fault rather than a fixture that stopped working. On `backrooms` the draw is safe to add because `ComputeCollision` **stops before the lighting pass**, so the map hash cannot move; on `backrooms-v2` the draw comes from `flickerSeed`, which is kept away from the level seed on purpose, and the panels there are baked meshes so a dead lamp is only a missing light.
- **The halls are dark and every Runner carries a torch.** Three things had to move together. The ceiling lights dropped to a third of their old intensity, the flat ambient to about a quarter, and the fog colour from a bright ochre to near-black — **fog colour matters more than fog density here**, because exponential fog blends *towards its colour*, so a bright fog in a dark room makes distance glow instead of vanish. The values live in two places each and both must change: the C# default *and* the serialized copy (`SampleScene.unity` for `backrooms`, `Prefabs/Maps/backrooms-v2.prefab` for v2). Editing only the default changes nothing, because the scene's stored value wins.
- **The URP asset had `Additional Lights: Per Vertex`, which silently makes a spotlight do nothing.** Walls here are single boxes with eight vertices, so a per-vertex cone has nowhere to land. Both RP assets are now Per Pixel with a per-object limit of 8. On PC that setting is moot — `PC_Renderer` is Forward+ (`m_RenderingMode: 2`), which clusters lights and ignores the per-object limit entirely — but `Mobile_Renderer` is plain Forward, and WebGL is excluded from neither quality level, so the low path has to be able to draw the beam too. It is the expensive half of this change: hundreds of ceiling point lights are per-pixel now.
- **The torch is aimed by the look and held by the hand, and those are two different transforms.** The Seeker never gets one — seeing in the dark is that side's ability, and handing it a torch as well empties the ability. The prop hangs off `ArmL` and swings with the walk — that swing is what makes an approaching light read as a person — but the beam direction comes from body yaw + `controller.Pitch`, so the holder's aim is steady while the *origin* rides the hand. One formula covers local and remote bodies because neither reads a camera: a puppet has no camera transform to read a forward vector from. Two settings are load-bearing: shadows are **on** (without them a beam lights the room through the wall it is pointed at, which in a maze gives away the corner), and `shadowNearPlane` is pushed to 0.4 m so the arm holding the lamp does not cast a black slab into the middle of its own pool. The prop's own blocks cast no shadow at all — they sit at the light's origin, so anything they occlude is the whole beam.
- Scanlines and the wound vignette are **generated textures**, not art. The scanline texture is rebuilt at the screen's pixel height so the lines land one pixel apart; stretched, it degrades into a grey wash and the effect is lost.
- **Ceiling tiles carry no collider; what stops a jump from below is the storey above — and the storey above is mostly not there.** Only 90 of the first floor's 284 walkable cells have a second floor over them, so above the other 194 there was nothing between a jumping head and the sky. The old code treated the top floor as the one special case; it was really just the case where the hole covered a whole storey and so got noticed. `BuildCeilingLids` now lays one invisible slab per floor, with the stairwell rect cut out of every lid below the top — five colliders instead of 194, and the cut is the same hole the ceiling tiles already skip, because that hole is the stairs. **It changes the exported box list (736 → 740) and therefore the map hash, so `backrooms.json` had to be re-exported; client and server must ship together.** The walkability grid is untouched (`Standable` 583, `FreeFloor` 574 before and after) — which is the thing worth checking, because a solid surface at a storey's standing plane is exactly what would put keys and the escape door on the roof. It does not, because `Standable` is authored from the layout by the generator and `FreeFloor` is only ever computed on cells that already carry it.
- **Which storey a position is on comes from `BackroomsMapGenerator.FloorIndexAt`, which floors the division and never rounds it.** Rounding put a jumping player on the floor above: the jump apex is 1.2 m and the storeys are 3.2 m apart, so the *nearest* floor level to a jumping player is the one overhead, and the map overlay flicked their dot upstairs every time they pressed space. The tolerance is one-sided (0.35 m below, none above) because a CharacterController rests its skin width low. The storey arrow on the compass compares floor *indices* for the same reason — the door's origin is on its floor while the eye is 1.62 m up, so comparing metres called every same-floor door "one storey down".
- The full-map overlay is drawn from the level grid into a `Texture2D` (358×175 for the 35×35 two-floor map), not rendered by a second camera — a top-down camera here photographs ceiling tiles. The Seeker camera feed *is* a real camera, and it renders with the Seeker's own culling mask so the Runners' device cannot leak the door back to them.

**The in-game guide (H).** `GuideOverlayController` + `GuideCatalog` (`Assets/Scripts/Game/UI/`), UXML/USS in `Resources/UI/GuideOverlay.uxml` / `guide-overlay.uss`. The overlay explains the objective, both roles, controls, objects/devices and the match flow; while closed it leaves only a corner hint ("H — 게임 방법"). **All content lives in `GuideCatalog`** — a pure static topic/section/line list, so a new map, role, device or key is a data edit, never a UI edit; `Assets/Editor/Tests/GuideCatalogTests.cs` holds the data's integrity (non-empty, unique ids, role→topic mapping resolves). The controller copies `EscapeMenuController`'s pattern exactly: own `UIDocument`, runtime clone of `GameHudPanelSettings` at sorting **110** (HUD 0 < guide 110 < ESC menu 120), lazy-alive check instead of a bool, and the same `InputEnabled` handoff guarded by `MatchResultGate.Standing` **and** `EscapeMenuController.AnyOpen`. Opened in a match it lands on your role's tab (asked from `MatchManager.LocalAgent` on every open, never cached). It is created by `MatchBootstrap` in every match scene and by `GameLobbyBootstrap` in the waiting room — the lobby has no player, so the input handoff simply finds nobody. **In the waiting room it opens by itself** (`autoOpenOnStart`): a first-time player does not know H exists, and the wait before START is exactly when the rules get read. It stops auto-opening once the player has *closed* it once (`PlayerPrefs` `nv.guide.dismissed`) — dismissal is stamped on close, not on open, so someone dragged into a match under an unread auto-opened guide is not recorded as having read it. The flag is deliberately not per-environment: the rules are the same on every server. Two coordination rules with the ESC menu: the menu's **게임 방법** button opens the guide via `CloseVisualOnly()` (a `SetOpen(false)` would re-lock the cursor for a frame), and ESC closing the guide stamps `ConsumedEscThisFrame` so the menu — which runs later, order 60 vs 70 — does not open off the same key press. The key is **H**, not F1: F1 is the debug side-swap and a browser's own help key, and this ships to WebGL. **The match-start brief** is the in-game half: when the phase reaches `Playing` and the local role exists (both *polled* — the game-scene rule, read the bulletin), `GuideCatalog.BriefFor(role)` is drawn on the **left edge** (mid-height, max-width 27% — the centre belongs to the crosshair and the door compass, the bottom corners and right edge to the HUD panels) for `briefSeconds` (15) and then goes away — no input lock, picking Ignore, and it yields to an open guide or ESC menu rather than stacking words on words. Arming resets whenever the phase leaves `Playing`, which is what makes the debug restarts (F1/F2) re-brief with the new role. `Role.Unassigned` briefs empty and empty never arms, so a match whose role has not arrived yet just waits a frame.

**Offline testing.** `practiceRunners` is **0** — no bots spawn. `PracticeRunner` is still there and raising the count brings back NavMeshAgent dummies so the Seeker's half of the ruleset (hits, bleeding, the trail, hunting by ear) can be exercised solo; they deliberately **do not collect keys** (`PlayerAgent.collectsKeys`) or the objective is swept clean in a minute. Note the count lives in **`GameConfig.asset`, which carries its own copy of every default** — changing the field in the `.cs` alone does nothing. With no bots the roster is one agent: as a Runner there is simply no Seeker (the camera-feed device reads NO SIGNAL), and as a Seeker `_runnersAtStart` is 0 so the wipe check stays off rather than declaring an instant win. Debug keys: **F1** swap side and restart, **F2** restart, **F5** take a hit. Turn `debugKeys` off for a real match.
